# DSH v0.5 Telemetry and Offline Learning Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Collect bounded, privacy-minimized run evidence and produce offline failure patterns, versioned lessons, model calibration reports, and traceable Skill/Prompt/Routing candidates backed by repeated tasks.

**Architecture:** Add `@ds-plugins/dsh-telemetry` as the fourth runtime plugin, with a pure `./contracts` export and a passive Harness event adapter. Extend the existing offline `dsh-eval` package for metrics, mining, lessons, calibration, and candidate generation; it never feeds changes back into a running scheduler. Preserve canonical Session events and existing profiles; validate activation through a keyless Loader overlay.

**Tech Stack:** TypeScript 5.9.3, Node.js `^22.19.0 || >=24`, pnpm 11.7.0, Vitest 4.0.18, Cordis 4.0.1, DeepSeek Harness 0.1.1-rc.2, Node filesystem/crypto, local JSONL/JSON artifacts.

**Spec:** `README.md` sections “Telemetry”, “受控演进闭环”, “仓库、Package 与插件边界”, and “v0.5：Telemetry 与学习”. No dedicated v0.5 design specification exists at planning time. The decision record below supplies proposed implementation defaults, not previously approved requirements. Also read the v0.4 boundary in `docs/superpowers/specs/2026-09-02-dsh-v0.4-economical-multi-agent-design.md` and deferred isolation record alongside this plan.

### Proposed defaults and explicit non-goals

1. Runtime collection is opt-in, local, and passive. No new default profile, model tool, network exporter, third-party telemetry dependency, or provider credential access. A new package is justified by the roadmap's explicit runtime lifecycle boundary; no package renames.
2. Redaction means strict field selection, enum mapping, and domain-scoped pseudonyms. Do not persist source text, prompts, task descriptions, Handoff prose, filesystem paths, command arguments/output, provider error messages, or raw session/model identifiers. Regex-only secret scrubbing is not an adequate storage boundary.
3. The unit of runtime collection is one root Session, including correlated child events. Multiple user turns in a Session are not assumed to be independent tasks. Offline annotations must identify task family and outcome; Session disposal alone never means task success.
4. Default storage ceilings: 8 KiB per JSONL record including newline, 256 queued records, 64 tracked root sessions, 2,048 projected events per root session, eight 1 MiB segments per store. Maximum age 30 days. Stop collecting a session when its event ceiling is reached; retain bounded loss counters and mark it incomplete. No eviction that silently turns a partial run into a complete sample.
5. Repeated evidence means at least three distinct root-run references, at least two distinct task-instance references, and one identical task family/config/prompt cohort. Replays/retries of the same run do not increase support. These thresholds are conservative proposed defaults, not statistical proof of improvement.
6. Candidates are immutable proposals only. No active policy writer, scheduler import of lessons, automatic promotion, online A/B, rollback implementation, LLM judge, or runtime self-evolution. Those are v0.6 work. Candidate templates express hypotheses and required future evaluation, never claims of measured improvement.
7. Do not reopen v0.4 isolation, worker pooling, hysteresis, quota adapters, or provider integration. Token usage, physical worker reuse, true task success, and model quality remain unknown unless supported by explicit evidence.
8. Persist only sanitized copies. Existing canonical Harness logs are outside this plugin's redaction/retention guarantee and remain untouched. A killed process can lose its bounded queue; next offline analysis must report incomplete evidence rather than infer successful completion.

## Shared v1 contract decisions

Implement these interfaces in Task 1. All persisted types reject unknown keys and validate finite nonnegative safe integers; nonempty digests are 64 lowercase hex characters. Bounds apply to UTF-8 serialized JSON, not JavaScript character count. Use recursively key-sorted canonical JSON for hashes; sort set-like evidence arrays before hashing.

```ts
export const FAILURE_CLASSES = [
  'context_loss', 'insufficient_context', 'context_bloat', 'bad_reasoning',
  'wrong_model', 'prompt_incompatibility', 'tool_misuse', 'premature_edit',
  'implementation_error', 'verification_gap', 'scope_creep', 'bad_handoff',
  'bad_routing', 'provider_failure', 'budget_exhaustion',
] as const
export type FailureClassV1 = typeof FAILURE_CLASSES[number]
export type RefV1 = string // parser enforces 64 lowercase hex characters
export type EvidenceRefV1 = { runRef: RefV1; seq: number }
export type EventKindV1 = 'run-started' | 'schedule-selected' |
  'worker-requested' | 'worker-finished' | 'budget-rejected' |
  'verification-finished' | 'parallel-started' | 'parallel-finished'
export type ObservationV1 = {
  schemaVersion: 1; domainRef: RefV1; runRef: RefV1; sessionRef: RefV1
  seq: number; kind: EventKindV1; observedAtMs: number
  facts: {
    routeRef?: RefV1; requestRef?: RefV1; fanoutRef?: RefV1; nodeRef?: RefV1
    scope?: 'root' | 'worker' | 'level' | 'dag'
    status?: 'completed' | 'blocked' | 'failed' | 'passed' | 'timed-out' |
      'spawn-error' | 'verification-failed' | 'budget-rejected'
    durationMs?: number
  }
}
export type RunSealV1 = {
  schemaVersion: 1; kind: 'run-seal'; domainRef: RefV1; runRef: RefV1
  observationCount: number; lostCount: number; complete: boolean
}
export type TelemetryRecordV1 = ObservationV1 | RunSealV1
export type RunAnnotationV1 = {
  schemaVersion: 1; domainRef: RefV1; runRef: RefV1
  taskInstanceRef: RefV1; taskFamilyRef: RefV1
  configHash: RefV1; promptHash: RefV1
  outcome: 'success' | 'failure' | 'unknown'; accepted: boolean | null
  failure: { category: FailureClassV1; evidence: EvidenceRefV1[];
    attribution: 'observed' | 'reviewed' } | null
  evidence: EvidenceRefV1[]
}
export type MetricV1 = {
  value: number | null; numerator: number; denominator: number
  observedRuns: number; eligibleRuns: number
  basis: 'observed' | 'estimated' | 'unavailable'
}
export type DatasetV1 = {
  records: TelemetryRecordV1[]; annotations: RunAnnotationV1[]
}
export type PatternV1 = {
  schemaVersion: 1; id: RefV1; category: FailureClassV1
  domainRef: RefV1; taskFamilyRef: RefV1; configHash: RefV1; promptHash: RefV1
  runRefs: RefV1[]; taskInstanceRefs: RefV1[]; evidence: EvidenceRefV1[]
}
export type LessonV1 = {
  schemaVersion: 1; id: RefV1; revision: 1; pattern: PatternV1
  rule: 'review-context-boundary' | 'review-verification-scope' |
    'review-route-fit' | 'review-failure-evidence'
}
export type CandidateV1 = {
  schemaVersion: 1; id: RefV1; revision: 1
  kind: 'skill' | 'prompt' | 'routing'; status: 'proposed'
  lessonId: RefV1; baseConfigHash: RefV1; basePromptHash: RefV1
  hypothesis: LessonV1['rule']; evidence: EvidenceRefV1[]
  evaluationRequired: true; autoPromote: false
}
```

`EvidenceRefV1.seq` is the root-run collector's monotonically increasing projection ordinal, not the Harness session-local sequence. Retain `sessionRef` for provenance; keep a bounded in-memory `(sessionRef, canonical seq) → projection ordinal` map so replayed events are not counted again. Offline references always resolve to exactly one stored observation. Storage deduplication uses `(domainRef, runRef, seq)` plus exact canonical bytes; conflicting duplicates fail import.

Allowed fact keys are event-specific, not merely optional on every event: run-started → routeRef/scope=root; schedule-selected → routeRef/scope/requestRef/fanoutRef/nodeRef; worker-requested → scope=worker and correlation refs; worker-finished → scope=worker/status and correlation refs; budget-rejected → status=budget-rejected; verification-finished → status/durationMs; parallel-started → fanoutRef/scope=dag; parallel-finished → fanoutRef/scope/status. Require core status/route/scope fields when applicable; absent correlation remains absent for legacy records. Validate correlated triples as all-present or all-absent before pseudonymizing. Source mapping is exact: routeRef hashes `[data.provider, data.model]`; schedule scope comes from `data.target`; worker status comes from `data.handoff.status`; verification status/duration come from `data.status`/`data.durationMs`; parallel-started fanoutRef hashes `data.dagId`; parallel-finished fanoutRef/scope/status come from `data.fanoutId`/`data.scope`/`data.aggregateStatus`. The last mapping accepts completed, blocked, failed and verification-failed; never read a nonexistent aggregate `status` field. Project only explicitly recognized canonical statuses; incompatible payloads are rejected and counted as loss, never coerced into success.
