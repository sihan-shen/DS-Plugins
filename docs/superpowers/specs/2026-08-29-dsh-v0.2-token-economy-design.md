# DSH v0.2 Token Economy Design

**Date:** 2026-08-29

**Status:** Revised after `gpt-5.6-sol` / `high` review

## Goal

Extend the v0.1 keyless DSH plugin foundation with measurable source-context reduction. v0.2 is deliberately split into three independently gated milestones: v0.2a establishes the evaluation protocol, baseline corpus, versioned interfaces, and plugin compatibility result; v0.2b implements read-only code intelligence; v0.2c adds immutable context blocks, progressive disclosure, bounded caching, and orchestrator integration. The first implementation targets TypeScript/JavaScript repositories while keeping the public interfaces language-neutral.

## Baseline and constraints

- Keep DeepSeek Harness pinned at `0.1.1-rc.2` until a separate compatibility review proves an upgrade.
- Preserve Direct mode, Single Worker mode, `HandoffV1`, plugin-owned budgets, targeted verification, and canonical `dsh-plugin/` events.
- Keep `pnpm test:provider` permanently keyless and disabled. No v0.2 test may require credentials, an OAuth session, a paid provider, or a network call.
- Do not fork or modify `upstream/deepseek-harness` or replace its agent loop.
- Treat all community plugins as host-level third-party code. Pin a commit or reviewed tarball; never install an unpinned branch into the default profile.
- Keep all model-visible outputs bounded, provenance-carrying, and safe to replay.
- A cache hit is an optimization, not evidence of correctness. The source remains authoritative and verification remains independent.

## Non-goals

v0.2 does not implement adaptive provider routing, quota-aware scheduling, parallel workers, worker affinity, long-term experience learning, automatic policy evolution, or real-provider acceptance. It also does not expose write-capable LSP actions by default.

## Milestones and exit gates

### v0.2a: Measurement and compatibility foundation

Deliver the deterministic evaluation protocol, baseline corpus, public data contracts, safe path policy, and a pinned compatibility report for candidate plugins. No persistent cache and no default-profile plugin integration are included.

Exit only when the baseline corpus, tokenizer, oracle, metric definitions, and promotion thresholds are executable without a provider; the contracts distinguish internal indexes from bounded model-visible projections; and the `dsh-lsp-actions` result is explicitly recorded as direct-compatible, patch-required, or rejected. The baseline-only v0.2a gate does not claim an optimized-path reduction.

### v0.2b: Read-only code intelligence

Deliver the TypeScript/JavaScript snapshot, read-only LSP adapter, deterministic fallback symbol extractor, internal symbol index, and bounded Repo Map / symbol query projections. Do not add persistent cache or orchestrator behavior.

Exit only when isolated Loader/replay tests prove deployment-root containment, fixed server argv/environment, bounded subprocess cleanup, read-only tool registration, provenance, stale-snapshot rejection, and baseline-versus-optimized retrieval metrics at the v0.2a thresholds.

### v0.2c: Context and reuse integration

Deliver `ContextBlockV1`, progressive disclosure, content-addressed cache entries, dependency-aware lookup invalidation, and explicit orchestrator integration. This milestone owns all persistent cache storage, concurrency, eviction, and HMR behavior.

Exit only when cache corruption, concurrent writers, workspace/revision/policy separation, UTF-8 truncation, stale block expansion, and complete v0.1 regression are covered by keyless tests. v0.2c receives its own implementation plan after v0.2b review.

## Reuse strategy

The repository's existing reuse boundary is retained in [`README.md`](../../README.md#复用边界). Reuse is split into three outcomes:

1. **Direct dependency:** an independent capability with a compatible DSH ABI, a reviewed permission surface, reproducible artifacts, and passing isolated Loader/replay checks.
2. **Adapted design:** useful algorithms or schemas are reimplemented behind our own versioned interfaces when the upstream storage, lifecycle, or security model does not fit.
3. **Reference only:** ideas and tests may inform design, but the runtime dependency is not accepted.

### Candidate decisions

#### `dsh-lsp-actions`: ABI candidate; direct integration blocked pending compatibility proof

The reviewed commit `ea0354ca444075b37b791bd8638fecdbc40fb5d0` (package version `0.4.0` at review time) uses DSH `0.1.1-rc.2` in its development setup, but its declared DSH peer range is `>=0.1.0-rc.8 <0.2.0`. npm prerelease semantics do not make that range accept `0.1.1-rc.2`; it is therefore an ABI candidate, not a presently compatible direct dependency. The project provides diagnostics, symbols, completion, signature help, inlay hints, formatting, code actions, and rename over language servers, with bounded result limits and real TypeScript language-server tests. The package declares filesystem read/write and subprocess permissions but no network permission; metadata does not prove that a child language-server process cannot reach the network.

Source: [reviewed README.zh.md](https://github.com/PerryLink/dsh-lsp-actions/blob/ea0354ca444075b37b791bd8638fecdbc40fb5d0/README.zh.md), [reviewed package.json](https://github.com/PerryLink/dsh-lsp-actions/blob/ea0354ca444075b37b791bd8638fecdbc40fb5d0/package.json).

Direct integration requires one of three explicit outcomes before v0.2b: an upstream release whose peer range explicitly accepts `0.1.1-rc.2`, an audited fixed tarball/patch with integrity, or a small adapter that registers only the approved read tools. The current plugin registers all eight tools unconditionally, so a read-only session alone is insufficient to claim that write tools are not exposed. Loader tests must assert that `lsp_format`, `lsp_code_action`, and `lsp_rename` are absent from the adapter's model-visible tool set; execution-time read-only rejection is an additional defense, not a substitute.

#### `dsh-project-memory`: adapted design, not a core dependency

The project supplies content-hash refresh, a lightweight symbol table, BM25 retrieval, citations, lazy indexing, and a per-workspace store. Those ideas are relevant to Repo Map and Context Compiler, but its persistent store, in-process locking, absolute-path citations, and optional LLM summarization do not become v0.2 contracts. We will adapt only the bounded indexing and provenance ideas into our own `RepoMapV1`, `SymbolMatchV1`, and `ContextBlockV1` interfaces.

The reviewed upstream reference is commit `31722851b8d5370914e8c21a5f133bd39ec41e00` (package version `0.3.1` at review time). Only content-hash incremental indexing, bounded symbol extraction, BM25 ranking where needed, and relative-path provenance may be adapted. Explicitly excluded are its runtime dependency, disk format, watcher, `fs/observed` auto-memory behavior, PDF indexing, experience notes, LLM document summaries, and LLM query expansion.

Source: [reviewed README](https://github.com/00080000/dsh-project-memory/blob/31722851b8d5370914e8c21a5f133bd39ec41e00/README.md), [project description and installation notes](https://dshmarket.com/p/00080000/dsh-project-memory/).

#### `dsh-telemetry-redactor`: optional deployment-layer candidate

This plugin redacts outbound telemetry copies without rewriting canonical session logs. It is useful when a deployment enables a telemetry backend, but it is not a substitute for our event projection rules and is not required for the v0.2 context loop. It requires a separate `dsh-session-telemetry` compatibility check.

Source: [README](https://github.com/030611/dsh-telemetry-redactor), [package.json](https://raw.githubusercontent.com/030611/dsh-telemetry-redactor/main/package.json).

#### `dsh-verification-receipt`: deferred

The current package manifest's `dsh-session` peer range does not accept the repository's pinned `0.1.1-rc.2`; its receipt is also redundant with the existing canonical `verification-finished` event. It is not admitted into the v0.2 runtime without an upstream compatibility correction and a demonstrated gap in our evidence schema.

Source: [package.json](https://raw.githubusercontent.com/030611/dsh-verification-receipt/main/package.json).

## Architecture

The v0.2 path has four bounded layers, delivered across the three milestones:

```text
repository files
      |
      v
snapshot + language adapters  --->  internal RepositorySnapshot / SymbolIndex
                                             |
                                             v
                              bounded RepoMapPage / SymbolQueryResult
                                             |
                                             v
                              ContextBlockV1 with provenance + hashes
                                             |
                                             v
                              compiler + disclosure policy + cache
                                             |
                                             v
                                bounded model-visible tool result
```

The plugin boundary remains separate from the orchestrator boundary. A reused LSP plugin may provide tool capabilities, but it does not own our context-block schema, cache keys, budget accounting, or evidence events.

### Repository snapshot

Every index operation is rooted at the deployment-controlled workspace root. The adapter must canonicalize and compare the request root to that deployment root; a session `cwd` cannot replace it. The snapshot records normalized repository-relative paths, file content hashes, file size, language, and revision metadata. It rejects absolute paths, traversal, NUL bytes, symlink escapes, and files above the configured byte limit. The default file selector excludes `.git`, `.dsh`, `.env*`, private-key extensions, `node_modules`, nested checkouts, binary files, and any path ignored by the repository's ignore rules unless an explicit future policy opts in. Every source-window read repeats containment, regular-file, size, and content-hash checks to close the snapshot/read TOCTOU gap. A snapshot is immutable after construction.

### Language adapter

The first adapter supports TypeScript/JavaScript through an approved LSP integration or a deterministic fallback parser for fixture tests. The server executable, fixed argv, cwd, and environment allowlist are deployment-controlled values validated at load time; arbitrary server commands and inherited secrets are not accepted. The subprocess receives an explicit network policy where the host supports one, and `network:none` metadata alone is not treated as proof. The adapter returns symbols and relationships; it does not return raw unbounded source. A future language adapter must implement the same public projection and its own bounded fixture suite.

### Repo map and symbol index

The internal index is never exposed as a model-visible DTO. The v0.2b contract is:

```ts
type RepositorySnapshotV1 = {
  schemaVersion: 1
  snapshotId: string
  workspaceFingerprint: string
  revision: string
  files: readonly RepoFileSummaryV1[]
}

type SymbolIndexV1 = {
  schemaVersion: 1
  snapshotId: string
  adapterId: string
  adapterVersion: string
  entries: readonly InternalSymbolEntryV1[]
}

type RepoMapPageV1 = {
  schemaVersion: 1
  snapshotId: string
  items: readonly RepoMapItemV1[]
  totalItems: number
  truncated: boolean
  nextCursor?: string
}

type SymbolQueryResultV1 = {
  schemaVersion: 1
  snapshotId: string
  matches: readonly SymbolMatchV1[]
  totalMatches: number
  truncated: boolean
  nextCursor?: string
}

type SymbolMatchV1 = {
  symbolId: string
  path: string
  sourceHash: string
  start: { line: number; column: number }
  end: { line: number; column: number }
  kind: string
  name: string
  container?: string
  score: number
}

function buildRepoMap(snapshot: RepositorySnapshotV1, index: SymbolIndexV1, options: RepoMapOptionsV1): Promise<RepoMapPageV1>
function querySymbols(index: SymbolIndexV1, query: SymbolQueryV1): SymbolQueryResultV1
```

All returned paths are repository-relative with `/` separators. `SymbolIndexV1` may be complete and internal; every model-visible page and query result is bounded and cursor-based. The index never stores credentials, raw tool transcripts, or model output.

Runtime JSON entering a model-visible path must pass `parseRepoMapPageV1` or `parseSymbolQueryResultV1`. The v0.2a contract parser validates the Context Block hash and byte-length fields structurally; recomputing them against block text is reserved for the v0.2c construction/cache gate.

### Immutable context blocks

```ts
type ContextBlockV1 = {
  schemaVersion: 1
  blockId: string
  kind: 'repo-map' | 'symbol' | 'source-window' | 'tool-result'
  workspaceFingerprint: string
  snapshotId: string
  adapterId: string
  adapterVersion: string
  compilerPolicyVersion: string
  sources: readonly { path: string; contentHash: string }[]
  contentHash: string
  text: string
  byteLength: number
  truncated: boolean
}
```

`blockId` is the SHA-256 content address of canonical JSON containing every field except `blockId`, `contentHash`, `byteLength`, and `truncated`; `contentHash` is the SHA-256 hash of UTF-8 `text`; canonical JSON uses sorted object keys, array order as emitted, and no insignificant whitespace. The compiler may compose blocks, but it may not mutate a published block. A block is cacheable only when all identity and dependency fields match.

### Progressive disclosure

The first response contains the smallest useful representation: directory/file summaries and symbol matches. A follow-up request may expand a bounded source window around an identified symbol. The compiler must reject expansion without a provenance-bearing `blockId` and must enforce per-block, per-tool, and per-session byte budgets.

### Cache policy

The cache is local, bounded, and content-addressed. v0.2c stores entries below the deployment-controlled workspace's excluded `.dsh-context-cache/v1/` directory, with a POSIX mode of `0700` where supported; the path is configurable only through trusted deployment configuration. It stores serialized context blocks and bounded tool results, never credentials or raw model transcripts. Immutable entries are keyed by canonical block content and dependency hashes; a separate lookup index is keyed by workspace fingerprint, normalized query, adapter/server configuration fingerprint, compiler policy version, and DSH capability version. A single-writer lock or equivalent atomic commit protocol is required; writes use temporary files plus atomic rename. The store is capped at 10,000 entries or 256 MiB, whichever comes first, with bounded LRU eviction. Corrupt entries move to a quarantine area capped at 32 files or 10 MiB and are never returned.

Repository revision is metadata and a lookup hint, not a global invalidation key. A file change invalidates only entries whose dependency hashes include that file; dependency closure changes invalidate dependent symbol and map entries. If dependency information is incomplete, the lookup misses closed and recomputes.

## Plugin integration and safety gates

The v0.2a compatibility experiment uses a separate profile overlay, not `profiles/v0.1/cordis.patch.yml`. The current `dsh-lsp-actions` candidate is not installed as a direct dependency while its peer range remains incompatible. The overlay may load an audited fixed tarball or adapter only after the compatibility gate passes; the default profile remains unchanged.

The adapter must register only the approved read tools. A read-only session that registers write tools is not sufficient. Until an upstream allowlist, audited patch, or self-owned adapter provides registration-level filtering, the candidate is a compatibility subject and not an accepted runtime dependency.

Each candidate must pass:

1. License and provenance review.
2. Exact DSH and Node compatibility check against the pinned runtime.
3. Dependency and lifecycle-script review; native or network dependencies require explicit justification.
4. Permission review for filesystem, subprocess, network, credentials, and writes.
5. Clean install from a pinned tarball with integrity, or an explicitly reviewed Git commit whose `prepare` lifecycle is allowed by the repository's pnpm build policy. An unpinned branch is never accepted.
6. Deployment-root equality, fixed server executable/argv/cwd, explicit environment allowlist, and the host's subprocess network policy.
7. Registration-level tool allowlist: `lsp_format`, `lsp_code_action`, and `lsp_rename` must be absent from the model-visible tool set.
8. Real Loader composition with profile-root disposal and HMR/remount coverage.
9. Keyless replay coverage for success, timeout, malformed output, bounded truncation, and budget rejection where applicable.
10. Removal test proving the default profile can run without the candidate.

The plugin evaluation fixture must not call a provider. A language server subprocess is allowed only as a local, declared verification dependency and must be bounded by timeout, output, and process-tree cleanup rules.

## Measurement and evaluation

The evaluation corpus is versioned and small enough for deterministic CI. v0.2a contains at least 12 TypeScript/JavaScript fixture tasks across at least 3 repository shapes. Tasks require symbol location, dependency tracing, and bounded source inspection. Each task has a human-checked target set, a fixed repository revision, a fixed query, and a closed-set verification descriptor. v0.2a executes only the deterministic fixture verifier; v0.2b may add a fixed-argv local verifier, never an arbitrary shell string.

Every run records a keyless, bounded evaluation record using these canonical snake_case JSON fields:

- `schema_version`
- `run_mode` (`baseline` or `optimized`)
- `task_id`
- `cache_condition` (`none`, `cold`, or `warm`)
- `run_index` (`1`, `2`, or `3`)
- `tokenizer_name`, `tokenizer_encoding`, and `tokenizer_version`
- `source_token_estimate`
- `uncached_source_tokens`
- `context_blocks_requested`
- `cache_hits` and `cache_misses`
- `symbol_query_precision`
- `symbol_query_recall_at_5`
- `symbol_query_mrr`
- `target_coverage`
- `oracle_success`
- `verification_status`
- `failure_class`
- `duration_ms`

The per-run `uncached_source_tokens` is the token count of source blocks that would be sent without a valid cache hit; in baseline mode it equals `source_token_estimate`. The aggregate-only `uncached_tokens_per_success` is defined by `PromotionReportV1` below and is never a field on an individual run.

`source_token_estimate` uses the pinned `@dqbd/tiktoken` encoding `cl100k_base` and records the tokenizer identifier and version. It measures only model-visible source text, excluding tool schemas, prompts, diagnostics, and serialized metadata. The metric is a deterministic comparison proxy, not a claim about any provider's billing tokenizer.

The baseline path is a fixed in-process `rg`-equivalent filename/symbol search followed by full reads of the files selected by the task fixture. The exact query, selection order, file revision, byte budget, tokenization, and closed-set verifier descriptor are recorded in the corpus manifest. v0.2a runs only this baseline path; v0.2b runs the optimized path against the same task and oracle. Each applicable cold-cache and prescribed warm-cache run is executed three times; medians are reported. Per-run `uncached_source_tokens` equals the source token estimate in baseline mode and counts only cache-miss block tokens in optimized mode. Aggregate `uncached_tokens_per_success` is the median successful optimized-run `uncached_source_tokens`, with `null` when optimized records are absent or none succeeds. `oracle_success` means every required target symbol/file is returned with valid provenance and the built-in fixture verifier returns true. Synthetic replay proves accounting and invalidation; it does not claim real-provider quality.

The v0.2a corpus manifest uses this verifier shape and never accepts a shell string:

```ts
type FixtureVerifierV1 = {
  id: 'fixture-integrity-v1'
  expected_revision: string
  required_paths: readonly string[]
}
```

The verifier reads only the checked-in fixture, validates its expected hashes and target oracle, and does not spawn a process. Any future process verifier must use a separate versioned descriptor containing an executable, fixed arguments, an allowed-argument policy, a deployment-controlled cwd, and a timeout.

The shared evaluation contracts (`FixtureVerifierV1`, `EvaluationTaskV1`, `EvaluationRecordV1`, `PromotionAggregateV1`, and `PromotionReportV1`) have one authoritative definition in the `@han_05/dsh-context` contract package. `@han_05/dsh-eval` imports them through the workspace dependency and may define only evaluation-specific runtime input types; it must not redeclare or serialize a camelCase variant. The context package also owns the runtime parsers for these contracts, including replay validation for promotion reports.

The serialized evaluation record is versioned and uses snake_case so replay files from v0.2a, v0.2b, and v0.2c share one contract:

```ts
type EvaluationRecordV1 = {
  schema_version: 1
  run_mode: 'baseline' | 'optimized'
  task_id: string
  cache_condition: 'none' | 'cold' | 'warm'
  run_index: 1 | 2 | 3
  tokenizer_name: '@dqbd/tiktoken'
  tokenizer_encoding: 'cl100k_base'
  tokenizer_version: '1.0.22'
  source_token_estimate: number
  uncached_source_tokens: number
  context_blocks_requested: number
  cache_hits: number
  cache_misses: number
  symbol_query_precision: number
  symbol_query_recall_at_5: number
  symbol_query_mrr: number
  target_coverage: number
  oracle_success: boolean
  verification_status: 'passed' | 'failed' | 'not-run'
  failure_class?: string
  duration_ms: number
}

`parseEvaluationRecordV1` accepts only the three protocol combinations `baseline/none`, `optimized/cold`, and `optimized/warm`; it rejects `baseline/cold`, `baseline/warm`, `optimized/none`, and any other mismatch. It also requires `run_index` to be exactly `1`, `2`, or `3`.

type PromotionReportV1 = {
  schema_version: 1
  corpus_id: string
  task_count: number
  repository_shape_count: number
  thresholds: {
    min_median_source_token_reduction: 0.25
    min_mean_symbol_query_recall_at_5: 0.95
    min_mean_target_coverage: 0.95
    min_mean_oracle_success: 0.95
  }
  aggregates: {
    cold: PromotionAggregateV1 | null
    warm: PromotionAggregateV1 | null
  }
  passes: boolean
  status: 'not-ready' | 'passed' | 'failed'
  failure_class?: 'optimized_records_missing' | 'threshold_failed' | 'invalid_pairing' | 'baseline_zero'
}

type PromotionAggregateV1 = {
  median_source_token_reduction: number | null
  uncached_tokens_per_success: number | null
  mean_symbol_query_recall_at_5: number | null
  mean_target_coverage: number | null
  mean_oracle_success: number | null
}
```

`evaluatePromotion(records: readonly EvaluationRecordV1[])` groups by `task_id`, `run_mode`, and `cache_condition`. A complete v0.2b input has exactly three `baseline/none` records, three `optimized/cold` records, and three `optimized/warm` records per task; duplicate mode/condition/run entries or missing pairs produce `status: 'failed'` with `failure_class: 'invalid_pairing'`. For each cache condition, it computes the median source token estimate per task and `reduction = (baseline_median_source_token_estimate - optimized_median_source_token_estimate) / baseline_median_source_token_estimate`; a zero baseline median produces `failure_class: 'baseline_zero'`. Corpus token reduction is the median of per-task reductions for that condition; recall, target coverage, and oracle success are arithmetic means of per-task medians/rates for that condition; `uncached_tokens_per_success` is the median successful optimized-run `uncached_source_tokens` for that condition. With no optimized records, both aggregates are null and the report is `passes: false`, `status: 'not-ready'`, and `failure_class: 'optimized_records_missing'`; otherwise it passes only when both cold and warm aggregates meet every threshold.

## Error handling

- Missing or incompatible language-server capability returns a structured unavailable result and may use the deterministic fallback adapter.
- Invalid paths, stale block IDs, hash mismatches, and oversized expansions fail closed without spending an LLM budget.
- Cache corruption is treated as a miss; the corrupted entry is isolated for later cleanup and never returned.
- A subprocess timeout records bounded evidence and terminates the owned process tree.
- An LSP write request is rejected before any write when the session is read-only or the tool is outside the approved allowlist.

## Acceptance criteria

Each milestone has its own acceptance gate:

### v0.2a gate

1. The evaluation corpus contains at least 12 tasks across at least 3 repository shapes with fixed revisions and target oracles.
2. The baseline protocol encodes the pinned tokenizer, fixed selection algorithm, equal byte limits, closed-set verifier, and promotion thresholds; optimized-vs-baseline comparison is a v0.2b gate.
3. The contract package separates internal snapshot/index data from bounded, cursor-based model-visible projections.
4. The `dsh-lsp-actions` review records its exact commit, peer-range result, permissions, lifecycle scripts, and whether an adapter/patch is required. It is not admitted to the default profile merely because its README claims compatibility.
5. v0.2a is keyless and passes its focused tests, typecheck, build, and `git diff --check`.

### v0.2b gate

6. The default v0.1 profile remains unchanged and passes its existing keyless Loader/replay checks.
7. The isolated read-only LSP adapter and deterministic fallback pass deployment-root, fixed-command, subprocess cleanup, registration allowlist, provenance, and stale-snapshot tests.
8. Across the v0.2a corpus, the optimized path achieves median `source_token_estimate` reduction of at least 25% versus baseline, `symbol_query_recall_at_5` of at least 0.95, `target_coverage` of at least 0.95, and `oracle_success` of at least 0.95. These are keyless retrieval-oracle thresholds, not real coding-task acceptance.

### v0.2c gate

9. Read-only LSP results and adapted Repo Map/Symbol Index results are bounded, provenance-carrying, and replayable.
10. Context blocks and cache entries cannot cross workspace, snapshot, adapter, policy, or capability boundaries.
11. Cache invalidation and progressive disclosure have focused tests for stale, malformed, oversized, concurrent, quarantined, and UTF-8-truncated data.
12. Cold and prescribed warm cache results report cache hit/miss counts and retain the v0.2b retrieval thresholds.
13. `pnpm typecheck`, targeted tests, build, Loader/replay checks, profile checks, and `git diff --check` pass. Provider smoke remains the fixed keyless `DISABLED` check.

## Rollout order

1. v0.2a: plugin evaluation gate, contract package, measurement harness, and baseline corpus.
2. v0.2b: read-only LSP adapter, Repo Map, Symbol Index, and deterministic fallback.
3. v0.2c: immutable context blocks, progressive disclosure, bounded cache, and orchestrator integration.

Each milestone is reviewed independently. No later milestone may silently broaden the default profile's permissions or enable provider execution.
