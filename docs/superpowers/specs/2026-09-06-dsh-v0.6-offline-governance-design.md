# DSH v0.6 Offline Governance Design

## Status

Proposed first v0.6 slice. This design starts controlled Self-Evolution as an offline governance capability; it does not activate runtime policy mutation.

## Goal

Turn the inert v0.5 candidate hypotheses into versioned, independently evaluated, human-approved promotion and rollback records while preserving the existing keyless and provider-disabled boundary.

## Scope

v0.6 first implements a pure governance layer in `@ds-plugins/dsh-eval`:

- a bounded policy-artifact reference and version schema;
- a candidate evaluation record that binds base and variant artifacts to fixed-fixture evidence;
- explicit `proposed`, `approved`, `rejected`, `promoted`, and `rolled-back` ledger states;
- an immutable human approval record;
- a last-known-good pointer and explicit rollback target;
- deterministic state-transition validation and canonical serialization;
- offline tests over checked-in fixtures and replay evidence.

The first governed surface is `template`, because v0.5 already produces prompt/template hypotheses while its routing and verification metrics remain partially unavailable. The schema remains extensible to `routing`, `verification`, and `kernel`, but those surfaces are rejected by the first evaluator unless their evidence contract is explicitly supplied.

## Non-goals

- No resident Self-Evolution plugin.
- No provider calls, credentials, network access, quota endpoint, or cost endpoint.
- No automatic runtime Profile, prompt, route, permission, sandbox, or verification-policy mutation.
- No online A/B assignment or exposure measurement; the first A/B comparison is paired offline replay over identical fixture inputs.
- No physical worker isolation, trusted write capture, or transactional workspace integration.
- No raw prompts, source text, model output, secrets, or private telemetry payloads in governance records.
- No reuse of the existing v0.2 `PromotionReportV1` as the complete v0.6 governance contract. It remains evaluation evidence for its original fixed corpus.

## Design choices

### 1. Pure ledger in `dsh-eval`

The governance layer belongs in `dsh-eval`, beside the existing offline metrics and candidate generation. It consumes validated `CandidateV1` values and immutable evaluation evidence, returns new values, and has no Cordis lifecycle or runtime import. This keeps the v0.5 dependency direction intact:

```text
dsh-telemetry/contracts  ->  dsh-eval/telemetry  ->  dsh-eval/governance
                                      |                    |
                                      +-- offline evidence +-- no runtime writer
```

The ledger is an in-memory pure value for this slice. File publication, signatures, and an artifact store are later concerns and must consume the same validated contracts rather than bypassing them.

### 2. Artifact references, not executable policy bodies

The first slice records opaque content-addressed artifact references. A reference contains a governed surface, semantic version, and SHA-256 digest of the canonical artifact supplied by an external authoring step. The ledger never interprets or executes the body. This makes promotion auditable without creating an automatic policy writer.

### 3. Evidence must bind base, variant, and corpus

An evaluation is eligible only when it identifies:

- the same corpus and fixture revision for base and variant;
- exactly one base artifact and one variant artifact;
- complete, validated run evidence for both arms;
- metric observations with explicit numerator, denominator, observed-run count, eligible-run count, and availability basis;
- threshold decisions and a deterministic pass/fail result;
- no unavailable metric treated as zero or success.

The initial paired offline A/B record is not an online exposure claim. It means both artifacts were evaluated against the same prescribed inputs under the same keyless harness.

### 4. Approval and transition rules

Every state transition creates a new immutable ledger entry; prior entries are never rewritten. The allowed sequence is:

```text
proposed -> approved -> promoted -> rolled-back
         \-> rejected
```

Rules:

- A proposal must contain a valid candidate, base/variant artifact references, and an evaluation record.
- Approval requires a non-empty human approval ID, approver ID, timestamp, rationale digest, and an evaluation that passes all required available thresholds.
- Rejection records a human decision and may target any proposal not already promoted.
- Promotion requires `approved`, records the prior active artifact as the rollback target, and updates only the pure ledger state. It does not edit a Profile or runtime configuration.
- Rollback requires a `promoted` entry and an explicit target equal to its recorded last-known-good artifact. It restores the pointer in the returned value and records why; it cannot silently choose a different artifact.
- A surface has at most one active artifact in a ledger state. Promotion of an already-active artifact is idempotent; promotion of a second artifact requires an explicit rollback-capable prior pointer.
- An evaluation with incomplete evidence, unavailable required metrics, mismatched corpus revisions, or unresolved references cannot be approved.

### 5. Version governance

Each artifact reference has `surface`, `version`, and `digest`. A governance bundle has a `bundleVersion` and a `policyGeneration` that are opaque values recorded for provenance only. The ledger does not infer compatibility between kernel, template, routing, and verification surfaces; a later multi-surface bundle must declare all component references explicitly and be evaluated as one immutable bundle.

## Contracts

The implementation should add strict v1 contracts under `packages/dsh-eval/src/governance/` and export them from `packages/dsh-eval/src/index.ts`.

```ts
type GovernanceSurfaceV1 = 'template' | 'routing' | 'verification' | 'kernel'

type ArtifactRefV1 = {
  schemaVersion: 1
  surface: GovernanceSurfaceV1
  version: string
  digest: string // 64 lowercase hexadecimal SHA-256 digest
}

type MetricObservationV1 = {
  name: string
  value: number | null
  numerator: number
  denominator: number
  observedRuns: number
  eligibleRuns: number
  basis: 'observed' | 'estimated' | 'unavailable'
  required: boolean
  threshold: { direction: 'at-least' | 'at-most'; value: number } | null
  passes: boolean | null
}

type EvaluationEvidenceV1 = {
  schemaVersion: 1
  corpusId: string
  corpusRevision: string
  base: ArtifactRefV1
  variant: ArtifactRefV1
  metrics: MetricObservationV1[]
  completeRuns: number
  excludedRuns: number
  evidenceRefs: { runRef: string; seq: number }[]
  result: 'passed' | 'failed' | 'incomplete'
}

type ApprovalRecordV1 = {
  schemaVersion: 1
  approvalId: string
  approverId: string
  approvedAtMs: number
  rationaleDigest: string
}

type GovernanceProposalV1 = {
  schemaVersion: 1
  proposalId: string
  candidateId: string
  candidateRevision: 1
  bundleVersion: string
  policyGeneration: string
  surface: GovernanceSurfaceV1
  base: ArtifactRefV1
  variant: ArtifactRefV1
  evaluation: EvaluationEvidenceV1
  status: 'proposed' | 'approved' | 'rejected' | 'promoted' | 'rolled-back'
  approval: ApprovalRecordV1 | null
  rejectionReasonDigest: string | null
  rollbackTarget: ArtifactRefV1 | null
}

type GovernanceLedgerV1 = {
  schemaVersion: 1
  entries: GovernanceProposalV1[]
  active: Partial<Record<GovernanceSurfaceV1, ArtifactRefV1>>
  lastKnownGood: Partial<Record<GovernanceSurfaceV1, ArtifactRefV1>>
}
```

The concrete parser may use narrower bounded string and array limits than this conceptual contract, but it must reject unknown keys, malformed digests/references, duplicate metric names, mismatched surface fields, negative/non-finite counts, invalid state/approval combinations, and non-canonical JSON exceeding the package's established byte ceilings.

## Data flow

1. `buildCandidates` emits an inert v0.5 hypothesis.
2. An offline evaluator resolves a fixed corpus and produces base/variant metric observations plus retained telemetry evidence references.
3. `proposeGovernance` validates that the candidate, artifacts, and evaluation describe the same surface and corpus.
4. `approveGovernance`, `rejectGovernance`, `promoteGovernance`, and `rollbackGovernance` return new validated ledger values and append immutable state entries.
5. CLI or future artifact storage may serialize the ledger, but no current path writes a Profile, changes routing, or changes permissions.

## Error handling

Invalid inputs fail closed with bounded, path-oriented validation errors that contain no raw prompt, source, provider, model, filesystem path, or private payload. State transitions reject rather than repair malformed history. Missing or unavailable evidence remains incomplete; it is never converted to a passing metric. Rollback failure leaves the input ledger unchanged.

## Acceptance criteria

1. Strict round-trip parsing and canonical serialization reject malformed, oversized, unknown-key, and inconsistent governance records.
2. A passing paired offline fixture evaluation can move `proposed -> approved -> promoted` and records the prior active artifact as the explicit rollback target.
3. A promoted proposal can move to `rolled-back` only to its recorded target; wrong-target, missing-target, duplicate, and stale-state transitions fail closed.
4. Failed, incomplete, unavailable, mismatched, and duplicate evidence cannot be approved.
5. Repeated serialization and transition application are deterministic and idempotent where specified.
6. Tests prove no runtime package is imported by governance code and no governed operation writes profiles, routes, permissions, credentials, network state, or provider data.
7. Existing v0.5 and v0.4 gates remain green, and the provider smoke remains the exact disabled keyless check.

## Deferred follow-up

After this slice is accepted, separately design: artifact publication and signatures, independent online A/B exposure accounting, quota/cost facts, coordinated multi-surface generations, runtime activation, and physical worker isolation. Each requires its own evidence and approval boundary.
