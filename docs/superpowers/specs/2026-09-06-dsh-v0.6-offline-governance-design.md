# DSH v0.6 Offline Governance Design

## Status

Proposed first v0.6 slice, revised after Sol/high review. This design starts controlled Self-Evolution as an offline governance capability; it does not activate runtime policy mutation.

## Goal

Turn the inert v0.5 candidate hypotheses into versioned, independently evaluated, human-approved promotion and rollback records while preserving the existing keyless and provider-disabled boundary.

## Scope

v0.6 first implements a pure governance layer in `@ds-plugins/dsh-eval`:

- a bounded policy-artifact reference and version schema;
- an authoritative evaluator policy for the first governed surface;
- explicit paired base/variant fixture evidence with domain-qualified run references;
- a full candidate snapshot whose identity and surface are independently verified;
- explicit `proposed`, `approved`, `rejected`, `promoted`, and `rolled-back` ledger states;
- immutable human decision records;
- deterministic hash-chained history with derived active and last-known-good pointers;
- offline tests over checked-in fixtures and replay evidence.

The first governed surface is `template`, mapped only from `CandidateV1.kind === 'prompt'`. The schema remains extensible to `routing`, `verification`, and `kernel`, but those surfaces are rejected by the first evaluator unless a separately versioned evidence policy is supplied.

## Non-goals

- No resident Self-Evolution plugin.
- No provider calls, credentials, network access, quota endpoint, or cost endpoint.
- No automatic runtime Profile, prompt, route, permission, sandbox, or verification-policy mutation.
- No online A/B assignment or exposure measurement; the first A/B comparison is paired offline replay over identical fixture inputs.
- No physical worker isolation, trusted write capture, or transactional workspace integration.
- No raw prompts, source text, model output, secrets, or private telemetry payloads in governance records.
- No reuse of the existing v0.2 `PromotionReportV1` as the complete v0.6 governance contract. It remains evaluation evidence for its original fixed corpus.

## Design choices

### 1. Pure governance subpath

The governance layer belongs beside the existing offline metrics and candidate generation, but it is exposed through a dedicated `@ds-plugins/dsh-eval/governance` subpath. The subpath imports only pure governance modules, canonical serialization, and the validated telemetry contract types it needs; it must not import the main `dsh-eval` entry, runtime evaluators, Cordis, code-intelligence runtime code, filesystem writers, or provider adapters.

The ledger consumes validated `CandidateV1` values and immutable evaluation evidence, returns new values, and has no Cordis lifecycle. File publication, signatures, and an artifact store are later concerns and must consume the same validated contracts rather than bypassing them.

```text
dsh-telemetry/contracts  ->  dsh-eval/governance
                                      |
                                      +-- pure contracts, evaluator policy, ledger
                                      +-- no runtime writer or provider import
```

### 2. Artifact references, not executable policy bodies

The first slice records opaque content-addressed artifact references. A reference contains a governed surface, semantic version, and SHA-256 digest of the canonical artifact supplied by an external authoring step. The ledger never interprets or executes the body.

### 3. Evaluator-owned policy

The first policy is the checked-in `template-offline-v1` evaluator policy. Its metric inventory, requiredness, availability rules, comparison formulas, directions, and thresholds are compiled constants identified by `(policyId, policyRevision, policyDigest)`. An input record carries only that policy identity; it cannot supply `required`, `threshold`, `passes`, or the overall result.

The evaluator derives all comparison statuses from the policy and arm observations. The parser rejects unknown policy identities and rejects any serialized derived field that does not equal recomputation under the known policy. An unavailable required metric produces `incomplete`, never `passed`.

### 4. Explicit paired arms

An evaluation contains a base arm and a variant arm. Each arm names its artifact, fixture revision, complete/excluded counts, metrics, and domain-qualified run references. A separate pair list binds one base run to one variant run by fixture ID, fixture revision, and deterministic pairing key. The evaluator requires identical fixture sets and revisions for both arms and verifies every pair reference resolves to the corresponding arm.

The initial paired offline A/B record is not an online exposure claim. It means both artifacts were evaluated against the same prescribed inputs under the same keyless harness.

### 5. Candidate snapshot and surface mapping

The proposal embeds the complete canonical `CandidateV1` snapshot, not only its ID. The first evaluator accepts only `kind: 'prompt'`, maps it to `surface: 'template'`, requires `status: 'proposed'`, and recomputes the candidate ID from its canonical body. The candidate lesson, hashes, evidence, and `autoPromote: false` invariant are therefore independently checked before a proposal enters the ledger.

### 6. Seeded, hash-chained ledger

The ledger is initialized with an explicit active artifact for every governed surface. Every later entry contains a sequence number, entry ID, predecessor digest, transition kind, immutable decision metadata, and a complete proposal snapshot. The head digest is recomputed from canonical entry bytes. Active and last-known-good pointers are derived from the initial state plus the validated history; serialized pointers are not trusted as independent inputs.

The allowed transitions are:

```text
proposed -> approved -> promoted -> rolled-back
         \\-> rejected
approved  -> rejected
```

`rejected` and `rolled-back` are terminal. Rejection is allowed only from `proposed` or `approved`; it is never allowed after promotion. Promotion requires that the proposal base exactly equal the currently derived active artifact for its surface, preventing stale approved proposals from replacing a newer active artifact. Promotion derives and records the prior active artifact as the rollback target. Rollback is allowed only for the latest promoted proposal and only to its recorded target.

Exact duplicate transitions with the same decision ID and canonical content are idempotent. A duplicate decision ID with different content, a sequence gap, a predecessor mismatch, a stale base, an inconsistent derived pointer, or a wrong rollback target fails closed.

## Contracts

The implementation should add strict v1 contracts under `packages/dsh-eval/src/governance/`, export the pure subpath from `packages/dsh-eval/package.json`, and avoid re-exporting governance through the runtime-heavy main `packages/dsh-eval/src/index.ts` entry.

```ts
type GovernanceSurfaceV1 = 'template' | 'routing' | 'verification' | 'kernel'

type ArtifactRefV1 = {
  schemaVersion: 1
  surface: GovernanceSurfaceV1
  version: string
  digest: string // 64 lowercase hexadecimal SHA-256 digest
}

type EvaluationRunRefV1 = {
  domainRef: string
  runRef: string
  fixtureId: string
  fixtureRevision: string
  pairingKey: string
}

type EvaluationArmV1 = {
  artifact: ArtifactRefV1
  fixtureRevision: string
  runs: EvaluationRunRefV1[]
  completeRuns: number
  excludedRuns: number
  metrics: ArmMetricObservationV1[]
}

type ArmMetricObservationV1 = {
  name: string
  value: number | null
  numerator: number
  denominator: number
  observedRuns: number
  eligibleRuns: number
  basis: 'observed' | 'estimated' | 'unavailable'
}

type EvaluationPairV1 = {
  fixtureId: string
  fixtureRevision: string
  pairingKey: string
  baseRun: EvaluationRunRefV1
  variantRun: EvaluationRunRefV1
}

type EvaluatorPolicyRefV1 = {
  policyId: 'template-offline-v1'
  policyRevision: 1
  policyDigest: string
}

type MetricComparisonV1 = {
  name: string
  baseValue: number | null
  variantValue: number | null
  delta: number | null
  result: 'pass' | 'fail' | 'unavailable'
}

type EvaluationEvidenceV1 = {
  schemaVersion: 1
  policy: EvaluatorPolicyRefV1
  corpusId: string
  corpusRevision: string
  baseArm: EvaluationArmV1
  variantArm: EvaluationArmV1
  pairs: EvaluationPairV1[]
  comparisons: MetricComparisonV1[]
  result: 'passed' | 'failed' | 'incomplete'
}

type DecisionRecordV1 = {
  decisionId: string
  actorId: string
  occurredAtMs: number
  reasonDigest: string
}

type GovernanceProposalV1 = {
  schemaVersion: 1
  proposalId: string
  candidate: CandidateV1
  bundleVersion: string
  policyGeneration: string
  surface: 'template'
  base: ArtifactRefV1
  variant: ArtifactRefV1
  evaluation: EvaluationEvidenceV1
  status: 'proposed' | 'approved' | 'rejected' | 'promoted' | 'rolled-back'
  approval: DecisionRecordV1 | null
  rejection: DecisionRecordV1 | null
  promotion: DecisionRecordV1 | null
  rollback: DecisionRecordV1 | null
  rollbackTarget: ArtifactRefV1 | null
}

type GovernanceEntryV1 = {
  schemaVersion: 1
  sequence: number
  entryId: string
  predecessorDigest: string | null
  transition: 'propose' | 'approve' | 'reject' | 'promote' | 'rollback'
  decision: DecisionRecordV1 | null
  proposal: GovernanceProposalV1
}

type GovernanceLedgerV1 = {
  schemaVersion: 1
  initialActive: Partial<Record<GovernanceSurfaceV1, ArtifactRefV1>>
  entries: GovernanceEntryV1[]
  headDigest: string | null
}
```

The concrete parser must use the package's established byte ceilings and reject unknown keys, malformed digests/references, unsupported candidate kinds, mismatched surface fields, duplicate metric names, duplicate run/pair keys, negative or non-finite counts, invalid state/decision combinations, and non-canonical JSON. `deriveGovernanceState` must return the recomputed active and last-known-good maps and reject any inconsistent history.

The authoritative `template-offline-v1` policy is code-owned. Its checked-in fixture specifies the exact metric rules and thresholds; serialized evidence contains policy identity and derived comparisons only. `evaluateGovernanceEvidence` must recompute arm completeness, pair coverage, metric comparisons, and the overall result before proposal or approval.

## Data flow

1. `buildCandidates` emits an inert v0.5 hypothesis.
2. A pure governance fixture builder creates a seeded template artifact, a prompt candidate snapshot, paired base/variant runs, and evidence under `template-offline-v1`.
3. `evaluateGovernanceEvidence` validates both arms, pairing, policy identity, metric counts, and derived results.
4. `proposeGovernance` validates the candidate snapshot, surface mapping, artifact/evaluation agreement, and current active base.
5. `approveGovernance`, `rejectGovernance`, `promoteGovernance`, and `rollbackGovernance` append validated hash-chained entries and return new ledger values.
6. The dedicated governance subpath can serialize the ledger, but no current path writes a Profile, changes routing, changes permissions, accesses providers, or performs network I/O.

## Error handling

Invalid inputs fail closed with bounded, path-oriented validation errors that contain no raw prompt, source, provider, model, filesystem path, or private payload. State transitions reject rather than repair malformed history. Missing or unavailable evidence remains incomplete; it is never converted to a passing metric. Rollback failure leaves the input ledger unchanged.

## Acceptance criteria

1. Strict round-trip parsing and canonical serialization reject malformed, oversized, unknown-key, and inconsistent governance records.
2. A passing paired offline fixture evaluation proves equal fixture sets, domain-qualified arm references, valid pairing keys, complete runs, and evaluator-derived comparisons.
3. A prompt candidate snapshot can move `proposed -> approved -> promoted` only when its recomputed identity, surface, evidence, and current active base are valid.
4. A promoted proposal can move to `rolled-back` only to its derived recorded target; wrong-target, missing-target, duplicate, stale-state, and predecessor-mismatch transitions fail closed.
5. Failed, incomplete, unavailable, mismatched, self-declared-policy, and duplicate evidence cannot be approved.
6. Repeated serialization and exact duplicate transitions are deterministic and idempotent where specified.
7. The built `@ds-plugins/dsh-eval/governance` subpath has no runtime/provider/filesystem imports and no dependency on the main eval entry.
8. Tests prove no governed operation writes profiles, routes, permissions, credentials, network state, or provider data.
9. Existing v0.5 and v0.4 gates remain green, and the provider smoke remains the exact disabled keyless check.

## Required fixture matrix

The checked-in governance fixture must include:

- a seeded active template artifact and a valid prompt candidate;
- paired base/variant runs with matching fixture IDs/revisions and domain-qualified references;
- a passing evaluation under the fixed policy;
- a failed threshold evaluation;
- an unavailable required metric and an incomplete arm;
- a candidate ID mismatch, surface mismatch, duplicate pair, and mismatched corpus revision;
- two approved proposals sharing a stale base;
- wrong-target, stale-state, predecessor-digest, duplicate-decision, and idempotent replay transitions.

## Deferred follow-up

After this slice is accepted, separately design: artifact publication and signatures, independent online A/B exposure accounting, quota/cost facts, coordinated multi-surface generations, runtime activation, and physical worker isolation. Each requires its own evidence and approval boundary.
