# DSH 0.1.2-rc.1 Compatibility Design

## Goal

Upgrade every runtime plugin and checked-in profile in DS-Plugins from the
currently pinned DeepSeek Harness `0.1.1-rc.2` line to the official
`dsh-v0.1.2-rc.1` line, while preserving the existing plugin contracts,
profile behavior, keyless verification boundary, and user-owned worktree
changes.

The target release is `0.1.2-rc.1` at upstream commit
`a66e4702047846cdaa10c66c9d3df3951f5ea70d`. `0.1.3-alpha.2` is explicitly
out of scope.

## Context and constraints

- The parent repository branch is `codex-deepseek-harness-latest`.
- The parent repository currently pins DSH `0.1.1-rc.2` in the root manifest,
  runtime plugin manifests, profiles, lockfile, and compatibility documents.
- The runtime packages are Git submodules. Changes to a submodule must be
  isolated from and must not overwrite the existing uncommitted edits in
  `dsh-code-intelligence`, `dsh-context`, or `dsh-context-cache`.
- The upstream release contains more than a version-number change: Agent,
  Session, LLM, Tools, Subagent, Subprocess, App Boot, storage, and workspace
  packages changed their public or type-level surfaces between the pinned
  commit and the target release.
- Node.js and pnpm remain unchanged. Cordis is part of the target runtime
  baseline and moves to the target release's required `4.0.2` version.
  Provider behavior, credentials, network access, and real coding-task
  acceptance remain outside this compatibility upgrade.
- Historical LSP candidate evidence remains historical. Its reviewed DSH
  version and artifact facts must not be silently rewritten to claim that the
  old candidate was tested against the new release.

## Recommended approach

Use a dependency-first compatibility migration with one repository-level
version manifest and explicit adapter changes at the DSH boundary.

1. Define the target DSH version and upstream commit once for current
   compatibility checks. Keep historical candidate fixtures immutable.
2. Align every direct DSH dependency, peer dependency, profile dependency,
   Cordis dependency, and lockfile entry to the versions required by
   `0.1.2-rc.1`. DSH packages remain exact `0.1.2-rc.1` pins; Cordis is
   updated to exact `4.0.2` where the target package metadata requires it.
3. Compile the plugins against the target declarations and adapt only the
   affected DSH boundary code. The DS-Plugins contracts—handoffs, budgets,
   scheduling decisions, verification evidence, telemetry records, and
   context blocks—remain unchanged unless a compiler or Loader test proves a
   required boundary correction.
4. Validate package entries and real profile composition before claiming
   compatibility. Preserve the existing disabled-provider and keyless test
   boundary.

This approach keeps the migration reviewable and makes failures attributable
to a specific upstream surface. A direct bulk replacement of version strings
is insufficient because the target release changes type and Loader surfaces;
maintaining two parallel DSH implementations is also rejected because it
would multiply profile and replay coverage without preserving a supported
runtime contract.

## Compatibility units

### Dependency and profile unit

The root workspace, all runtime plugin manifests, and `profiles/v0.1`,
`profiles/v0.2b-readonly`, `profiles/v0.2c-context`, and
`profiles/v0.3-adaptive` use the same DSH release line. The migration keeps
the existing bundle composition and Cordis configuration semantics. The
Cordis baseline is upgraded from `4.0.1` to the target-compatible `4.0.2`
line, including direct peer/dev declarations and the resolved lockfile. No
profile gains provider credentials, network permission, or write capability
merely because the host runtime is upgraded.

The shared package submodules remain semver-compatible package dependencies;
their existing user changes are preserved. If a submodule's public metadata
must change for the target DSH line, the change is made in that submodule and
recorded by the parent as a submodule pointer update only after its focused
package checks pass.

### Orchestrator unit

The orchestrator is the highest-risk adapter because it imports Agent, LLM,
Session, Subagent, Subprocess, and Tools contracts. Adapt its worker,
parallel-worker, direct, scheduling, context, event, and verification seams
to the target declarations. Preserve the existing behavior:

- direct and single-worker modes remain mutually exclusive;
- worker requests still publish only bounded `WorkerSpecV1` data;
- child results still normalize into `HandoffV1` rather than transcripts;
- scheduler routes remain validated against configured routes;
- targeted verification remains budgeted and allowlisted; and
- session event projections remain bounded and credential-free.

The migration must explicitly account for the target API changes already
observed in the upstream diff:

| Surface | Target-release change to verify | Required acceptance |
| --- | --- | --- |
| Subagent capability negotiation | `SubagentCapabilities` exposes whether child `agentOptions` are supported. | Worker and parallel-worker requests preserve the configured provider/model/reasoning route and reject unsupported capabilities without consuming an invalid child. |
| Session sequence types | Session sequence and log offsets are branded types such as `SessionSeq` and `SessionLogOffset`, not interchangeable plain numbers. | Event append, replay, child seeding, and verification projections preserve ordering and inherited offsets without unsafe casts hiding a mismatch. |
| Seed metadata | Session headers and child restore metadata use `isSeeded` and `inheritedEventCount`. | Single-worker and parallel fixtures cover seeded and unseeded sessions, including cancellation and cleanup. |

Any additional compiler-reported API change is recorded against its owning
boundary and gets a focused regression test before the migration is marked
complete.

### Code-intelligence unit

Adapt the read-only tools, session runtime resolver, LSP adapter, and Loader
entry to the target Tools, Subprocess, Session, Storage, and Workspace
declarations. Preserve bounded repository reads, fallback symbol extraction,
session-scoped context compilation, cache disposal, and the absence of
model-visible write/LSP action tools in the read-only profile.

### Telemetry and evaluation unit

The telemetry plugin remains passive and opt-in. Adapt only event/session
typing or lifecycle registration required by the target runtime. Do not
change the versioned telemetry contracts, privacy projection, storage format,
governance evaluator, or offline CLI semantics as part of this host upgrade.
The evaluator remains a DSH-independent offline package, with its README
compatibility note updated to the new code-intelligence target.

### Loader and replay unit

Update the actual profile Loader fixtures and runtime shims for App Boot and
target package resolution. Add a current-version compatibility assertion that
the loaded DSH manifests resolve to `0.1.2-rc.1` and Cordis resolves to
`4.0.2`. Each of `v0.1`, `v0.2b-readonly`, `v0.2c-context`, and
`v0.3-adaptive` must be booted from its own copied profile/install context,
with its required services asserted and disposed cleanly. Reusing another
profile's module links is not sufficient evidence. Any profile Loader failure
blocks full compatibility acceptance. Existing replay fixtures continue to
assert DS-Plugins event contracts and must remain deterministic.

## Validation strategy

Validation runs in increasing scope:

1. Static manifest scan: no current runtime manifest or profile may retain
   `0.1.1-rc.2`; historical candidate fixtures are explicitly excluded.
2. Package-entry and focused unit tests for each changed plugin.
3. TypeScript project build and root typecheck.
4. Actual Loader/profile tests for `v0.1`, `v0.2b-readonly`,
   `v0.2c-context`, and `v0.3-adaptive`, each using its own dependency
   resolution context. Every profile must boot, expose its required plugin
   entries/services, exercise its key path, and dispose without leaked
   listeners or processes.
5. Replay, evaluation, and telemetry suites.
6. `git diff --check`, profile-preservation checks, and the intentionally
   disabled provider smoke command.

The migration is successful only when the target DSH line is resolved by the
real Loader and all keyless gates pass. Passing TypeScript alone is not
evidence of Loader compatibility. No validation may access provider
credentials or perform a live network/provider call.

## Error handling and rollback

- A target API mismatch is fixed at the smallest DSH boundary that owns it;
  DS-Plugins domain contracts are not widened speculatively.
- A profile that cannot compose against `0.1.2-rc.1` remains disabled in the
  migration branch until its concrete failure is resolved; the old profile
  is not silently relabeled as compatible.
- If the target package or Cordis version cannot be resolved reproducibly from
  the configured package source, stop before changing the lockfile and record
  the source blocker. A temporary source override is acceptable only when it
  is pinned to the target commit and carries an integrity check; it must not
  be mistaken for a registry-published dependency.
- Before changing any submodule, record its HEAD and exact user diff in the
  handoff. Only migration changes may be committed in a submodule; existing
  user edits remain outside the migration commit. The migration is
  independently revertible by reverting the parent manifests/lockfile and
  migration-only submodule pointers, without destructive reset or rewrite of
  existing user changes.
- Add a non-workspace package-consumption check so `pnpm-workspace.yaml`
  overrides cannot hide missing standalone peer/dependency metadata. The
  check must use the same target pins and a frozen lockfile.

## Expected affected areas

- `package.json`, `pnpm-lock.yaml`, and `profiles/*/package.json`
- Exact Cordis `4.0.2` peer/dev declarations and their resolved lockfile
  entries
- A repository-level current compatibility version/commit manifest and its
  static consistency test
- DSH-dependent manifests and READMEs under `packages/*`
- DSH boundary source under `packages/dsh-orchestrator/src`,
  `packages/dsh-code-intelligence/src`, and `packages/dsh-telemetry/src`
- Loader, replay, package-entry, and compatibility tests
- Current compatibility documentation and `HANDOFF.md`

Historical specs, historical release evidence, and the upstream checkout are
not rewritten as part of this migration.
