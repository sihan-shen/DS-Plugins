# DSH v0.1 Foundation Design

## Purpose

Build the smallest runnable DS-Plugins loop on DeepSeek Harness `0.1.1-rc.2` that can execute a real coding task directly or through one worker, preserve a bounded structured handoff, and report targeted verification evidence. The implementation extends documented Harness APIs and does not fork or modify the upstream agent loop.

## Scope

v0.1 delivers one repository-local profile bundle and one orchestrator plugin. The bundle composes the official Harness capabilities required by the plugin. The plugin owns the Direct and Single Worker modes, versioned worker and handoff data, deterministic resource limits, targeted verification, and the durable events needed to reconstruct model-visible behavior.

v0.1 does not implement parallel workers, a task DAG, file ownership arbitration, dynamic provider routing, provider fallback, a repository index, prompt-cache compilation, long-term memory, proactive execution, external trace storage, or automatic policy evolution.

## Upstream Baseline

The implementation pins DeepSeek Harness commit `b150a551b8d465e31e418e1b2eaf5e79bbb7d28e`, version `0.1.1-rc.2`. Harness is pre-release software and does not promise a stable long-term ABI, so every upstream update requires profile composition, typecheck, loader, replay, and provider smoke validation before the pin moves.

The design uses these official APIs:

- Harness profile and bundle loading for out-of-tree composition.
- `ctx.llm` and the official `dsh-llm-pi-ai` `openai-codex` authorization and adapter path.
- `ctx.subagents.start()` for a one-shot child session.
- `ctx.systemPrompt` for bounded, ordered prompt sections.
- `ctx.tools` or a plugin-owned service for explicit actions.
- `SessionEventMap` declaration merging and canonical session events for durable records.
- `session-telemetry/record` as an export-copy policy point, without mutating canonical history.

The implementation does not treat Harness workflow, schedule, experimental Agent Teams, or the internal tool runtime scheduler as an orchestration or resource-scheduling API.

`types.ts` owns public data definitions, `events.ts` owns declaration merging and append helpers, `budgets.ts` owns deterministic admission decisions, `handoff.ts` owns validation and projection, each mode module owns one execution path, and `verification.ts` owns command admission and evidence normalization. `index.ts` only validates configuration and composes those units.

## Configuration

The plugin validates configuration at load time. v0.1 exposes only deployment choices that must vary:

```ts
interface OrchestratorConfig {
  mode: "direct" | "single-worker";
  worker: {
    provider: string;
    model: string;
    reasoningEffort?: string;
    maxTokens: number;
  };
  budgets: {
    maxWorkers: 0 | 1;
    maxPluginToolActions: number;
    toolTimeoutMs: number;
  };
  verification: {
    commands: readonly VerificationCommand[];
    timeoutMs: number;
    maxOutputBytes: number;
  };
}
```

Single Worker mode requires `maxWorkers: 1`; Direct mode requires `maxWorkers: 0`. Positive integer bounds reject zero, negative, non-integral, or excessive values at load time. The implementation documents and tests finite maximum values instead of silently clamping invalid input.

`VerificationCommand` is a named command with an executable and fixed argument prefix. A model may select the name and provide only arguments permitted by that entry. It cannot submit a shell string, redirection, command substitution, environment override, or an arbitrary executable.

## Data Contracts

All plugin-owned durable records carry `schemaVersion: 1` and use JSON-only fields.

```ts
interface WorkerSpecV1 {
  schemaVersion: 1;
  task: string;
  provider: string;
  model: string;
  reasoningEffort?: string;
  maxTokens: number;
  allowedTools: readonly string[];
  expectedOutput: "handoff-v1";
}

interface VerificationEvidenceV1 {
  schemaVersion: 1;
  commandName: string;
  args: readonly string[];
  exitCode: number | null;
  status: "passed" | "failed" | "timed-out" | "spawn-error";
  stdout: string;
  stderr: string;
  truncated: boolean;
  durationMs: number;
}

interface HandoffV1 {
  schemaVersion: 1;
  status: "completed" | "blocked" | "failed";
  summary: string;
  changedFiles: readonly string[];
  decisions: readonly string[];
  verification: readonly VerificationEvidenceV1[];
  blockers: readonly string[];
}
```

Strings and arrays have explicit length and item-count bounds. Paths are repository-relative, normalized, and cannot escape the workspace. A completed handoff may contain failed verification evidence but must describe the discrepancy in `summary`; status describes task execution, not automatic proof of correctness.

The parent receives the validated handoff only. It does not receive the child transcript, raw child session events, or unbounded tool output. The child session remains available through normal Harness persistence for diagnostics.

## Durable Events

The plugin extends `SessionEventMap` with a `dsh-plugin/` namespace:

- `dsh-plugin/run-started` records the selected mode and resolved configuration identifiers.
- `dsh-plugin/worker-requested` records the bounded `WorkerSpecV1`.
- `dsh-plugin/worker-finished` records the child session identifier and validated `HandoffV1`.
- `dsh-plugin/budget-rejected` records the limit, observed value, and deterministic reason.
- `dsh-plugin/verification-finished` records `VerificationEvidenceV1`.

Events required to rebuild model-visible behavior are non-ignorable. Pure export or diagnostic additions may be ignorable only when an older reader can safely omit them. Handoff content enters the parent model context through a bounded `agent.inject()` summary only when the parent must continue reasoning after worker completion.

## Execution Modes

### Direct

Direct mode records `run-started`, installs the minimal Worker Prompt ABI sections needed for structured completion and evidence reporting, and executes within the root session. It does not start a child or expose delegation tools. Plugin-owned action counts and verification execution are checked by the same budget service used by Single Worker mode.

### Single Worker

Single Worker mode resolves a `WorkerSpecV1`, records `worker-requested`, and starts exactly one one-shot child through `ctx.subagents.start()`. The child uses the configured provider, model, reasoning effort, token limit, tool allowlist, and maximum depth of one. The parent and child do not write concurrently; the parent waits for the child result before resuming any write-capable work.

The child must return a `HandoffV1`. Invalid output produces a failed normalized handoff containing a bounded validation message; the implementation never substitutes the raw transcript. Cancellation propagates to the child. A timeout, provider error, or cancellation records a failed or blocked handoff according to the observable condition and retains the child session identifier when available.

## Resource Limits

v0.1 implements deterministic hard limits, not an adaptive scheduler:

- Direct mode admits no child; Single Worker mode admits one child.
- Each child has a configured LLM `maxTokens` value.
- Plugin-owned tool actions are counted against `maxPluginToolActions`.
- Every plugin-owned external action has a finite timeout.
- Verification admits only configured command names and argument forms.
- Captured verification output is truncated deterministically to `maxOutputBytes` and marks `truncated: true`.

Each rejection returns a stable machine-readable reason and records `dsh-plugin/budget-rejected`. Harness-native tool calls outside the plugin cannot be represented as a complete run-level tool budget in v0.1; the README and user-facing output must not imply otherwise.

## Targeted Verification

Verification is an explicit plugin-owned service or action. It executes a configured program directly without a shell, uses the repository root as its working directory, propagates cancellation, applies the configured timeout, and captures bounded stdout and stderr. Exit code zero maps to `passed`; a non-zero code maps to `failed`; timeout and process-start failure have distinct statuses.

Every attempted verification produces `VerificationEvidenceV1` and a durable event. Neither a verification receipt nor command execution alone proves task correctness. Final responses identify the exact commands run and distinguish failed, skipped, and unavailable checks.

## Provider Strategy

v0.1 first validates the upstream `dsh-llm-pi-ai` `openai-codex` OAuth path and one supported model route. DS-Plugins selects a provider and model through the official LLM runtime; it does not own OAuth, persist tokens, proxy Responses API traffic, or implement provider fallback.

The provider smoke test is opt-in because it requires interactive authorization and may consume account quota. Unit, loader, and replay tests remain keyless. Failure of the official route blocks the real-model acceptance criterion and is reported as an upstream or account integration blocker; it does not authorize adding the third-party OAuth plugin without a separate design review.

## Community Plugin Decisions

No community plugin is installed in v0.1. Candidate manifests commonly use prerelease peer ranges that do not accept Harness `0.1.1-rc.2` under npm semver rules, even when their documentation mentions nearby release candidates.

- `dsh-lsp-actions` remains the strongest v0.2 reuse candidate after a corrected peer range, a pinned artifact, and a real language-server smoke test.
- `dsh-telemetry-redactor` may be adopted after current-version integration tests prove canonical logs remain unchanged and export copies are redacted.
- `dsh-verification-receipt` is execution telemetry, not verification proof, and is not required for v0.1.
- `dsh-engineering-workflow` is a source of workflow and skill ideas; its global prompt and preset file mutation require separate review.
- `dsh-openai-oauth` is rejected for v0.1 because the official provider path exists, Windows is unsupported, and credentials are stored in a plaintext plugin file.
- Project-memory, relay, router, Codex shim, proactive, and trace candidates remain extraction or design references rather than runtime dependencies.

Every future adoption must pin a commit and package artifact, verify its license and peer range, inspect installation scripts and host permissions, and run Linux and Windows profile composition tests.

## Failure Handling

Configuration errors fail plugin loading with a precise field path. Missing provider or model routes fail before starting a worker. Budget rejection is not retried. Worker validation failure never leaks raw output into the parent context. Verification timeouts terminate the owned process tree through the Harness subprocess capability where available and otherwise fail closed with a recorded limitation.

Canonical session logging remains authoritative. Telemetry export failure does not mutate or remove canonical events. Secrets, authorization values, full transcripts, and unrestricted command output are excluded from plugin-owned events and handoffs.

## Testing and Acceptance

Development follows test-driven implementation. Each capability has focused unit tests and HMR disposal coverage where it registers effects. A real Loader test composes the v0.1 profile from `cordis.yml`; direct `ctx.plugin()` tests alone are insufficient.

Keyless replay fixtures cover:

- Direct completion with structured verification evidence.
- Single Worker request, independent child session, valid handoff, and bounded parent injection.
- Invalid child output normalized without transcript leakage.
- Worker cancellation, provider failure, and deterministic budget rejection.
- Verification pass, non-zero exit, timeout, spawn error, and output truncation.

The optional provider smoke validates interactive `openai-codex` authorization, route resolution, one Direct request, and one Single Worker request without printing or committing credentials.

v0.1 exits when a real coding task can complete in both modes, the parent can continue using only `HandoffV1`, every claimed verification result points to recorded evidence, limits fail deterministically, and the profile passes targeted typecheck, unit, Loader, and keyless replay checks. The real-provider acceptance item remains explicitly unverified when authorization is unavailable.
