# DSH v0.3 Adaptive Scheduling Design

## Goal

Add a separate Adaptive Scheduler plugin that selects `provider + model + prompt profile + reasoning effort` for the Orchestrator's capability requests, with deterministic Model Stickiness, logical Worker Affinity, bounded Adaptive Escalation, and per-task-type model performance history, while preserving the keyless v0.2 safety boundary. The Orchestrator submits capability requests and consumes routing decisions; when the Scheduler is absent, the system degrades safely to the Profile's fixed route.

## Scope and non-goals

v0.3 covers the scheduling contracts package, the independent Adaptive Scheduler Cordis plugin, optional Orchestrator integration, session-scoped route selection, deterministic escalation, and bounded performance history. It does not implement learning-based routing (LLM Judge, EXP3/UCB/k-NN), real provider quota/cost adapters, raw transcript retention, parallel workers, cross-session affinity reuse, or any provider/network/real coding-task acceptance. It does not modify `profiles/v0.1`, the Direct or Single Worker semantics, `HandoffV1`, `BudgetController` admission, or the `run-started` actual-route projection.

## Baseline and constraints

- Keep DeepSeek Harness pinned at `0.1.1-rc.2` until a separate compatibility review proves an upgrade.
- Preserve Direct mode, Single Worker mode, `HandoffV1`, plugin-owned budgets, targeted verification, canonical `dsh-plugin/` events, and the keyless `DISABLED` provider smoke.
- The Orchestrator owns task/worker lifecycle, final budget admission, Handoff normalization, and event recording. The Scheduler only provides capability-to-schedule decisions.
- Do not fork or modify `upstream/deepseek-harness` or replace its agent loop.
- All model-visible outputs and all scheduling evidence stay bounded, provenance-carrying, and safe to replay.
- No scheduling decision may bypass the Orchestrator's hard constraints (`maxWorkers`, `maxPluginToolActions`, tool allowlist, workspace/verification policy).
- Unknown quota, price, or health values are never invented or silently estimated into hard routing decisions.

## Architecture

The repository gains one pure contracts package and one independent runtime plugin:

```text
packages/
  dsh-scheduling-contracts/   # pure types, JSON schema, parsers; no Cordis runtime
  dsh-adaptive-scheduler/     # independent Cordis plugin, provides adaptiveScheduler
```

`dsh-scheduling-contracts` defines `CapabilityRequestV1`, `RouteDecisionV1`, `ScheduleDecisionV1`, `BudgetViewV1`, `ScheduleFeedbackV1`, and `ScheduleSelectedV1` with strict parsers, bounded JSON-only payloads, and no reference to Session, Agent, credentials, transcripts, or raw output. `dsh-adaptive-scheduler` implements the decision service and provides it under the `adaptiveScheduler` service name. The Orchestrator adds a thin `scheduling.ts` adapter that submits capability requests and consumes bounded decisions without importing the Scheduler package.

The decision flow is:

```text
delegate_worker / root request
  -> CapabilityRequestV1 (JSON-only)
  -> adaptiveScheduler.schedule(request, BudgetViewV1, signal)
       or fixedProfileSchedule(config.worker) when absent
  -> Orchestrator hard validation
  -> BudgetController final admission
  -> dsh-plugin/schedule-selected (provenance)
  -> WorkerSpecV1 / worker-requested
  -> subagents.start('spawn', ...) or DSH root request/header
```

## Contracts

### Capability request

```ts
type SchedulingTargetV1 = 'root' | 'worker'

interface CapabilityProfileV1 {
  readonly coding: number
  readonly reasoning: number
  readonly toolUse: number
  readonly repoContext: number
  readonly risk: number
  readonly difficulty: number
}

interface SchedulingConstraintsV1 {
  readonly maxWorkers: 0 | 1
  readonly maxOutputTokens: number
  readonly maxLatencyMs: number
  readonly allowPaidFallback: boolean
  readonly allowedProviders?: readonly string[]
  readonly requiredTools: readonly string[]
}

interface CapabilityRequestV1 {
  readonly schemaVersion: 1
  readonly target: SchedulingTargetV1
  readonly taskId: string
  readonly objective: string
  readonly profile: CapabilityProfileV1
  readonly constraints: SchedulingConstraintsV1
  readonly workspaceFingerprint?: string
  readonly repoRevision?: string
  readonly affinity?: {
    readonly workerId?: string
    readonly modelFamily?: string
    readonly snapshotId?: string
  }
  readonly priorHandoff?: HandoffV1
}
```

The request separates "what capability is needed" from "which provider/model to use". `priorHandoff` only carries an already-parsed bounded `HandoffV1` projection. No credential, authorization, transcript, or raw output ever enters the request.

### Schedule decision

```ts
interface RouteDecisionV1 {
  readonly provider: string
  readonly model: string
  readonly maxTokens: number
  readonly reasoningEffort?: string
  readonly promptProfile?: string
  readonly modelFamily?: string
}

interface ScheduleDecisionV1 {
  readonly schemaVersion: 1
  readonly mode: 'direct' | 'single-worker'
  readonly route: RouteDecisionV1
  readonly workerCount: 0 | 1
  readonly source: 'scheduler' | 'profile-fallback'
  readonly policyVersion: string
  readonly affinityKey?: string
  readonly explanationCode?: string
}
```

The Orchestrator rejects any decision that returns `mode: 'parallel-workers'`, `workerCount > 1`, an unconfigured provider, an over-limit token count, or an empty route. `source` distinguishes a Scheduler decision from a Profile-fallback decision for replay provenance.

### Service contract

```ts
interface BudgetViewV1 {
  readonly maxWorkers: number
  readonly admittedWorkers: number
  readonly maxPluginToolActions: number
  readonly admittedPluginToolActions: number
  readonly remainingWorkers: number
  readonly remainingPluginToolActions: number
}

interface AdaptiveSchedulerService {
  schedule(request: CapabilityRequestV1, budget: BudgetViewV1, signal: AbortSignal): Promise<ScheduleDecisionV1>
  observe?(feedback: ScheduleFeedbackV1): void
  dispose?(): Promise<void>
}
```

`BudgetController` gains a read-only snapshot view but never exposes `admitWorker()` or `admitPluginTool()` to the Scheduler. The Scheduler cannot register tools, start workers, append session events, or own budget counters.

### Feedback

```ts
interface ScheduleFeedbackV1 {
  readonly schemaVersion: 1
  readonly requestId: string
  readonly outcome: 'completed' | 'blocked' | 'failed' | 'budget-rejected' | 'verification-failed'
  readonly handoff?: HandoffV1
  readonly verification?: readonly VerificationEvidenceV1[]
  readonly budgetRejection?: {
    readonly code: 'WORKER_LIMIT' | 'PLUGIN_TOOL_LIMIT' | 'DISPOSED'
    readonly limit: number
    readonly observed: number
  }
  readonly actual?: {
    readonly provider?: string
    readonly model?: string
    readonly durationMs?: number
    readonly toolCalls?: number
  }
}
```

Feedback drives stickiness, escalation, and history without carrying raw model output, transcripts, authorization, or credentials. The Orchestrator decides whether to continue after each feedback.

### Durable event

```ts
interface ScheduleSelectedV1 {
  readonly schemaVersion: 1
  readonly target: 'root' | 'worker'
  readonly source: 'scheduler' | 'profile-fallback'
  readonly provider: string
  readonly model: string
  readonly maxTokens: number
  readonly reasoningEffort?: string
  readonly promptProfile?: string
  readonly policyVersion?: string
}
```

The event name is `dsh-plugin/schedule-selected`, appended by the Orchestrator (never by the Scheduler directly). The existing `run-started` v1 payload keeps only `schemaVersion`, `mode`, `provider`, and `model`, and continues to record the actual route from `request/header` only. Root ordering is `schedule-selected -> DSH request/header -> run-started`; worker ordering is `schedule-selected(target=worker) -> worker-requested -> child start -> worker-finished`.

## Decision precedence

The scheduler applies a deterministic, pure-function precedence:

```text
1. safety hard gate / tool permission
2. local quota / session budget admission (BudgetViewV1)
3. explicit worker profile or user route override
4. active adaptive escalation state
5. session sticky route (with TTL / idle boundary)
6. taskType baseline (explainable, zero-shot)
7. provider/model catalog candidate resolution
```

Every selection produces a bounded `RouteDecisionV1` with `source`, `reasonCode`, `policyVersion`, and `generation`. The actual model selection is written into the DSH `request/header` by the official seam; `agent/request` is the enforcement point. The scheduler never treats `agent/request` waterfall return values as the final route without verifying the resulting `request/header`.

## Model Stickiness

- Default route sticks to the current phase/worker profile; no per-step reclassification.
- Sticky state is isolated by `sessionId + phase + routeGeneration`.
- A switch happens only on: explicit override, provider error/cooldown, quota admission, high-impact gate, phase boundary, or TTL/idle expiry.
- Every switch records `reason` and `previousRoute`; a Session reload restores from the durable projection, and HMR/dispose uses generation to prevent stale-state pollution.
- v0.3 implements fixed TTL + idle TTL. Sliding-window majority/hysteresis is deferred to v0.4.

## Worker Affinity

v0.3 restricts affinity to logical profiles, not physical workers:

- `routeAlias`: stable alias; the model never composes provider/model directly.
- `toolFilter`: minimal allowed tool set.
- `maxDepth`: 1; no recursive delegation in v0.3.
- `outputSchema`: the structured Handoff contract.
- `maxTokens` / budget slice: frozen at creation; actual usage is recorded on completion.
- `background=false`: one-shot foreground only.

A worker's route is frozen at creation and invalidated on completion, failure, cancellation, or parent dispose. A same-id worker never reuses stale mutable route state across tasks.

## Adaptive Escalation

v0.3 uses only a deterministic state machine:

- First transient provider error: one same-tier fallback and cooldown the original route.
- Repeated failures within a bounded error window: escalate to a strong/high-reliability route, with a TTL after which it returns to sticky/default.
- High-impact action: hard deny first, then require a strong route; the model cannot self-skip.
- Quota exhausted: hard reject the current call with an actionable message; never mask the quota problem as "escalation".
- Non-transient schema/auth/config error: no retry, no escalation, return a clear error.
- `maxEscalationsPerTask`, `maxRounds`, `cooldown`, and `escalationTTL` all have explicit upper bounds.

No LLM Judge in v0.3: each Judge is a new cost and failure surface. If the rule baseline proves insufficient, a shadow Judge comparison comes in v0.4.

## Performance history

Initial task types are 5-7 stable buckets (`code-fix`, `code-new`, `research`, `summarize`, `review`, `tool-heavy`, `unknown`). Each bucket maintains:

- `n`, `success`, `failure`, `retry`, `escalation`;
- latency bucket and input/output/cache token buckets;
- latest timestamp and config/prompt/profile hash;
- `evidenceLevel`: `observed` | `heuristic` | `verified`, never a single boolean `good`.

Updates use a simple EMA or fixed window; insufficient samples fall back to baseline. History only influences candidate ordering/thresholds, never bypasses safety, quota, explicit route, or capability validation. The store is bounded with retention/rotation; BM25/experience notes are deferred and never enter the synchronous routing critical path.

## Quota awareness

The Harness exposes quota/rate-limit only as failure facts (`LlmFailure.code`, `status`, `providerRetryAfterMs`), not as queryable remaining quota, reset time, price, or cost. v0.3 therefore implements:

- Local session budget admission via `BudgetViewV1` (a read-only snapshot of `BudgetController`).
- Quota failure-code awareness: `QUOTA`, `RATE_LIMIT`, `AUTH`, `SERVER`, `TIMEOUT`, `TRANSPORT` drive deterministic cooldown/fallback.
- An explicit `unknown` state for any provider/model without priced/quota data; never invented 0 or silently estimated values.

Real provider quota/cost adapters are a v0.4+ contract with `remaining`, `resetAt`, `scope`, `observedAt`, `confidence`, and `source` fields; v0.3 only declares the gap.

## Orchestrator integration

`packages/dsh-orchestrator` adds `src/scheduling.ts` as a thin adapter:

1. `index.ts` keeps the four required injections (`systemPrompt`, `tools`, `sessions`, `subprocess`); `adaptiveScheduler` is an optional injection resolved with the same pattern as the optional `contextCompiler`, never blocking `apply()`.
2. `worker.ts` replaces `workerSpec(input, config)` with `workerSpec(input, resolvedRoute)`; the route is resolved scheduler-first, profile-fallback.
3. `delegate_worker.execute` validates input, resolves a side-effect-free schedule, performs final admission, appends `worker-requested`, then starts the child. A scheduling failure never consumes budget.
4. `direct.ts` continues to observe the real `request/header` and record `run-started`. Dynamic root selection would require a DSH pre-request extension point; v0.3 does not rewrite a committed header.
5. `events.ts` adds the `schedule-selected` append helper with the same detached-snapshot, no-reentry, and sensitive-key omission rules as the existing five events.
6. `budgets.ts` adds a read-only `snapshot()` / `BudgetViewV1` assembly; admission remains exclusive to the Orchestrator.

The new `profiles/v0.3-adaptive` composes the pinned DSH base, Orchestrator, and Adaptive Scheduler bundles with explicit hard bounds and scheduler policy. It is not included by `profiles/v0.1` and does not enable a provider or a write-capable tool.

## Safe degradation

- The Scheduler service is optional: not in the required `inject` list, and `apply()` never waits for it.
- When absent, `fixedProfileSchedule(config.worker)` uses the Profile fixed route with no environment reads, provider search, or network calls.
- When present but returning invalid/out-of-bound decisions, the Orchestrator treats it as a validation failure, stops dynamic selection, and records the reason. It falls back to the same Profile route only when the Profile explicitly allows safe fallback; it never silently expands into a paid provider or unenabled route.
- Provider auth/quota/rate-limit errors never trigger a silent paid fallback.
- Every decision passes the Orchestrator's final hard-constraint check; the Scheduler cannot raise `maxWorkers` or `maxPluginToolActions`.
- `run-started` keeps actual-route semantics: malformed/missing provider/model produces no event and never falls back to `config.worker`.

## Evaluation and error handling

Keyless replay covers:

- Profile-fallback path (no Scheduler) producing the fixed route;
- Scheduler-present path producing a bounded decision;
- invalid/out-of-bound decision rejection without budget consumption;
- quota/timeout/cooldown fallback policy;
- Handoff-driven escalation;
- event provenance and `schedule-selected` ordering;
- Direct root actual-route consistency (no Worker fallback in `run-started`);
- `BudgetViewV1` read-only snapshot correctness.

Missing optional services, invalid decisions, quota failures, and unknown provider/model values fail closed or degrade deterministically without provider access. Every timeout/cancellation path releases owned resources. The provider smoke command remains the exact keyless `DISABLED` check.

## Acceptance criteria

1. The Scheduler is an independent plugin providing a bounded `adaptiveScheduler` service; the Orchestrator submits capability requests and consumes decisions.
2. Scheduler absence degrades safely to the Profile fixed route with no environment/network reads.
3. Invalid or out-of-bound decisions are rejected before budget consumption; hard constraints cannot be raised by the Scheduler.
4. Model Stickiness is session-scoped with TTL/idle boundary and generation-safe HMR/dispose.
5. Worker Affinity is a frozen logical profile with no cross-task mutable reuse.
6. Adaptive Escalation is a deterministic bounded state machine with no LLM Judge.
7. Performance history is bounded, per-task-type, evidence-leveled, and never bypasses safety/quota/capability checks.
8. Quota awareness uses local session budget and failure-code facts only; unknown values are never invented.
9. `dsh-plugin/schedule-selected` provides replayable provenance without changing `run-started` v1 semantics.
10. Targeted tests, typecheck, build, Loader/profile/replay checks, provider-disabled check, and `git diff --check` pass.
