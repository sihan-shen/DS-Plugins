# DSH v0.4a Isolated Workspace — Deferred Scope Record

## Status

Deferred. This document records why per-worker file isolation is not implemented in the v0.4 cycle and what the future seam should look like. No v0.4a package or implementation is planned in this cycle. The v0.4 spec (docs/superpowers/specs/2026-09-02-dsh-v0.4-economical-multi-agent-design.md) enforces ownership at the declaration layer only.

## Why v0.4 does not implement isolation

The pinned DeepSeek Harness 0.1.1-rc.2 does not expose a per-child workspace/cwd on SubagentStartRequest; the in-process spawn provider derives the child workspace from the parent and copies the parent cwd unchanged (child-agent.ts), and filesystem tools resolve against the child session cwd. Three candidate mechanisms were evaluated during design review:

1. Per-worker execution cwd binding (each spawned child's process cwd/fs root points at its own isolated copy). Requires a Harness upgrade or a DSH-owned custom subagent provider that stamps child session cwd. Not implementable against the pinned Harness without upstream coupling or an unverified custom provider.
2. Trusted per-worker write capture (an Orchestrator-side journal of actual writes derived from the Harness fs/write-intent and fs/edit-intent event gates, attributed per child session). Requires a spike proving child-session attribution before it can be specified.
3. Actual-diff containment and transactional integration over isolated copies (prepare N copies, diff each against an immutable manifest, integrate only ownership-valid accepted changes as an all-or-nothing transaction). This was found to be mechanically incoherent while workers execute in the shared tree: workers never touch their copies (so the diff is empty), and integration preconditions contradict the shared-tree mutations already made. It only becomes coherent on top of mechanism 1 or 2.

An intermediate design combining shared-tree execution with isolated-copy diff checking was reviewed twice and rejected both times for this incoherence.

## What v0.4 delivers instead

Declaration-layer ownership enforcement: each worker self-reports changedFiles in its Handoff; the Orchestrator validates (via the authoritative path grammar in dsh-scheduling-contracts) that every self-reported changed file is contained by the node's declared writePaths. Out-of-ownership self-reports fail closed (node marked ownership-violation, Handoff not aggregated). This detects dishonest-but-reporting workers but cannot detect unreported shared-tree mutations and does not physically prevent writes; the spec states this limit explicitly.

## Future seam (when isolation becomes implementable)

When mechanism 1 or 2 is verified, the future work should reintroduce a seam with these contracts (kept here for continuity; not normative in v0.4):

- prepareLevel(nodes): create one isolated workspace per worker under a trusted isolation root, capturing an immutable snapshot manifest (path/type/mode/content hash; in-scope = tracked + allowed untracked; excluded = node_modules, lib, .git, .dsh, .dsh-context-cache, upstream, .worktrees).
- diffAndCheck(workerId, declaredWritePaths): actual changed paths in that worker's isolated copy vs the manifest; report out-of-ownership paths as violations.
- integrateAccepted(workerIds): all-or-nothing per level with a deployment-root lock; on conflict/failure the integrated/applied sets are empty and the tree is rolled back to the transaction's pre-commit receipts.
- disposeLevel(): remove copies, release git worktree registrations, idempotent.
- Both a git-worktree backend and a file-copy backend must satisfy the same conformance suite (temporary Git repo + non-Git directory).

Preconditions for re-opening: (a) a verified Harness capability (upgrade or custom provider) that binds a child session cwd or attributes fs writes per child; (b) a spike proving it against the actual pinned runtime; (c) an updated v0.4 spec that makes the isolation seam normative and removes the declaration-layer limitation note.
