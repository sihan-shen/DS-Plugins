# DSH v0.4 Economical Multi-Agent Design

## Goal

Extend the Orchestrator so it can decompose a root task into bounded, independent sub-tasks and run them as parallel Workers whose declared file ownership is enforced at the declaration layer (each worker's self-reported changedFiles must fall inside its declared writePaths; violations fail closed and are never aggregated), then aggregate their Handoffs and verify the integrated result — while preserving the keyless v0.3 safety boundary, deterministic replay, and the single-monorepo plugin ownership model. v0.4 introduces a declarative Task DAG and independence/ownership validation as deterministic pure logic in the Orchestrator, a bounded parallel-worker execution path, declaration-layer ownership enforcement, Handoff aggregation into a strict ParallelAggregateV1, and an integrated-result verification gate. Worker processes run in the shared working tree exactly as today's Single Worker path. Physical execution isolation and trusted write capture are deferred milestones (see Deferred isolation work). No new runtime plugin beyond the Orchestrator is created; the Adaptive Scheduler continues to own resource/affinity selection.

## Scope and non-goals

v0.4 covers: the contracts needed for bounded parallel workers and task graphs; a deterministic, replayable Task DAG representation with file-ownership sets and dependency edges; a parallel fan-out path; declaration-layer ownership enforcement (self-reported changedFiles validated against declared writePaths via the authoritative path grammar in dsh-scheduling-contracts); per-worker Handoff normalization plus a strict ParallelAggregateV1 result; integrated-result verification; and a deterministic keyless replay gate over the v0.3-adaptive profile with a test-only overlay. It does not implement filesystem isolation, per-worker execution cwd binding, trusted per-worker write capture, actual-diff containment, or transactional file integration — all deferred (see below). It does not implement learning-based decomposition, LLM Judge independence approval, mutable warm worker reuse across tasks, cross-session physical worker pooling, recursive worker delegation beyond subagentMaxDepth 1, or any provider/network/real coding-task acceptance. Context-locality/prefix-compatible reuse and all deferred v0.3 roadmap items (hysteresis, shadow Judge, quota adapters) are explicitly deferred beyond v0.4. It does not modify profiles/v0.1, the Direct or Single Worker semantics, HandoffV1 projection semantics, BudgetController admission exclusivity, or the run-started actual-route projection.

## Deferred isolation work (explicitly out of v0.4 scope)

Ownership is enforced at the declaration layer in v0.4: a worker's self-reported changedFiles must be contained by its declared writePaths. This detects a worker that reports an out-of-scope mutation, but it cannot detect a worker that mutates the shared tree without reporting it, and it cannot physically prevent writes. Three stronger mechanisms are deferred to future milestones gated on verified Harness capability (the pinned Harness 0.1.1-rc.2 SubagentStartRequest has no cwd/workspace field, in-process spawn inherits the parent cwd, and per-child fs write attribution is unverified):

1. Per-worker execution cwd binding: each spawned child's process cwd/fs root points at its own isolated copy. Requires a Harness upgrade or a DSH-owned custom subagent provider that stamps child session cwd; a compatibility spike must precede it.
2. Trusted per-worker write capture: an Orchestrator-side journal of actual writes derived from the Harness fs/write-intent and fs/edit-intent event gates, attributed per child session, so ownership can be checked against real writes rather than self-reports. Requires a spike proving child-session attribution.
3. Actual-diff containment and transactional integration over isolated copies. Depends on 1 or 2.

A one-page record of these deferred items is kept in docs/superpowers/specs/2026-09-02-dsh-v0.4a-isolated-workspace-design.md so the boundary and the future seam (prepare/diff/integrate over isolated workspaces) remain documented; no v0.4a implementation is planned in this cycle.

## Baseline and constraints

- Keep DeepSeek Harness pinned at 0.1.1-rc.2 until a separate compatibility review proves an upgrade.
- Preserve Direct mode, Single Worker mode, HandoffV1, plugin-owned budgets, targeted verification, canonical dsh-plugin/ events, and the keyless DISABLED provider smoke (pnpm test:provider always prints the exact DISABLED line).
- The Orchestrator owns task DAG, independence/ownership validation, worker lifecycle, final budget admission, Handoff normalization/aggregation, and event recording. The Scheduler only provides capability-to-schedule decisions.
- Do not fork or modify upstream/deepseek-harness or replace its agent loop.
- All model-visible outputs and all orchestration evidence stay bounded, provenance-carrying, and safe to replay. In particular, every durable event payload v0.4 adds or extends for parallel runs is bounded under an exact byte ceiling, and arbitrary-length Harness child session ids never enter parallel durable payloads; the byte-compatible legacy non-parallel worker-finished shape (which retains its raw childSessionId) is the sole explicit exception.
- No orchestration decision may bypass the Orchestrator's hard constraints (maxWorkers, maxPluginToolActions, tool allowlist, workspace/verification policy, disjoint ownership).
- Workers run in the shared working tree and self-report changedFiles. Declaration-layer ownership means: self-reported changedFiles outside declared writePaths fail closed (node invalid, not aggregated). Physical containment is not claimed in v0.4.
- Per-node TaskNodeV1 constraints may only NARROW the deployment limits. The effective capability request is a deterministic field-by-field intersection defined in the Constraints intersection table; required capabilities fail closed on empty intersection rather than silently disappearing.
- Unknown quota, price, or health values are never invented or silently estimated into hard routing decisions.
- No v0.4 profile is added. The parallel path is activated only through a validated test-only overlay over the v0.3-adaptive profile (loader-convention-compatible) plus replay fixtures in tests/replay. Real deployments enabling parallel mode are deferred until execution isolation exists.
- "Reload-safe" in this spec means same-process service-generation/HMR reload over a live session (persistence is write-behind in the pinned Harness); process-restart/crash durability is out of scope.

## Architecture

The repository keeps the existing packages and adds no new runtime plugin:

```text
packages/
  | "failed-result"               // worker returned a failed handoff
  | "handoff-payload-too-large"   // admitted Handoff exceeds MAX_PARALLEL_WORKER_FINISHED_PAYLOAD_BYTES; status failed, workerRef present, no worker-finished event
dsh-scheduling-contracts/   # pure types, JSON schema, parsers; no Cordis runtime. Authority for DAG, aggregate, path grammar, bounds, and worker scheduling constraints
  dsh-orchestrator/           # gains task DAG, independence/ownership validation, parallel fan-out, declaration-layer ownership, aggregation, ParallelExecutionService
```

dsh-scheduling-contracts already defines CapabilityRequestV1, RouteDecisionV1, ScheduleDecisionV1, BudgetViewV1, ScheduleFeedbackV1, and ScheduleSelectedV1. v0.4 widens SchedulingConstraintsV1.maxWorkers and BudgetViewV1 bounds, adds the Task DAG, ParallelAggregateV1, ParallelVerificationPolicyV1, and the authoritative path grammar/types/bounds, and keeps the no-Cordis boundary. Worker-event types (WorkerSpecV1, WorkerFinishedV1), their parsers, and append helpers remain Orchestrator-local; v0.4 ADDS strict Orchestrator-local parsers for worker-requested and worker-finished (they do not exist today) so old/new shape compatibility is actually enforced, and scheduling-contracts does NOT gain worker-event types or parsers.

dsh-orchestrator adds a deterministic pure dag.ts module (DAG parsing/validation, cycle rejection via SCC, level/topological ordering, independence check, disjoint ownership validation), a declaration-layer ownership check (changedFiles containment), a ParallelExecutionService seam, and extends the worker path so the parallel fan-out admits and runs N bounded workers with per-worker route selection, enforces declaration-layer ownership, aggregates normalized Handoffs into ParallelAggregateV1 emissions plus a cumulative DAG final aggregate, and runs integrated-result verification. Root route selection remains under the existing Adaptive Scheduler seam.

The execution flow:

```text
root task
  -> caller parses TaskDagV1 (parseTaskDagV1) then invokes ParallelExecutionService.run({ dag, parent, signal })   // Orchestrator-internal; only the test overlay invokes it; policy comes from config.parallel.verification
  -> run() validates the already-parsed DAG (validateTaskDagV1) and the strict request envelope (rejects unknown keys, incl. a stray policy key)
  -> per-ready-level: dependency-readiness pass (every dependency completed & ownership-valid, else recursive not-run/dependency-not-run) -> classify nodes -> form the executable set -> per-worker schedule -> hard validation -> BudgetController.admitFanout(executableSet.length) only when non-empty
  -> parallel subagents.start('spawn') per executable worker in the shared working tree (same execution model as Single Worker)
  -> per-worker Handoff normalization (self-reported changedFiles)
  -> declaration-layer ownership check: changedFiles ⊆ declared writePaths (grammar containment); violation => node ownership-violation, not aggregated
  -> deterministic aggregate builder: one ParallelAggregateV1 emission per policy scope boundary, plus one cumulative scope-dag final aggregate
  -> dsh-plugin durable events per worker and per emitted aggregate
```

## Contracts

### Constants (authoritative, in dsh-scheduling-contracts)

MAX_PARALLEL_WORKERS = 8 (max ready-level width); MAX_DAG_NODES = 16 (total nodes in one DAG; the cumulative per-session worker budget ceiling); MAX_DAG_LEVELS = 4; MAX_DAG_PATHS = 32 per node (readPaths and writePaths each); MAX_DAG_DEPS = 8 per node; MAX_DAG_CHANGED_FILES = 16 (parallel-specific cap on the number of changedFiles the builder retains per node as sample paths); MAX_AGGREGATE_PAYLOAD_BYTES = 131072 (total UTF-8 serialized payload of one ParallelAggregateV1); MAX_AGGREGATE_VERIFICATION_TOTAL_BYTES = 49152 (hard serialized-section cap for the verification evidence section of one aggregate; output retains fewer raw bytes when JSON escaping expands); MAX_AGGREGATE_VERIFICATION_METADATA_SERIALIZED_BYTES = 4096 (per command: the JSON.stringify UTF-8 size of name + args + exitCode + status + durationMs + keys/delimiters; enforced by building metadata first and measuring); MAX_AGGREGATE_VERIFICATION_OUTPUT_BYTES = 8192 (per command: combined stdout+stderr output ceiling measured on the shortened fragment's raw string length, where the fragment is shortened until the complete serialized record fits the per-command serialized cap and the section cap); MAX_AGGREGATE_VIOLATION_BYTES = 24576 (total serialized bytes for the ownership-violation summary section of one aggregate); MAX_AGGREGATE_PATH_BYTES = 1024 (per sample display path; whole-path retention only); MAX_AGGREGATE_PROJECTED_HANDOFF_BYTES = 24576 (total serialized bytes for projectedHandoff); MAX_VERIFICATION_COMMANDS = 4; MAX_VERIFICATION_ARGS = 8 (per parallel verification command, enforced at parseConfig); MAX_VERIFICATION_ARG_BYTES = 256 (per arg, enforced at parseConfig); MAX_DAG_ID_ORDINAL = 999; MAX_PARALLEL_WORKER_REF_BYTES = 34 (workerRef = "w:" + 32 hex); MAX_PARALLEL_WORKER_FINISHED_PAYLOAD_BYTES = 262144 (256 KiB total serialized ceiling for one parallel worker-finished event carrying the complete admitted parallel HandoffV1 plus correlation triple plus workerRef). The complete admitted Handoff is retained losslessly in worker-finished when it fits this ceiling; a Handoff that is valid as HandoffV1 under the existing per-field bounds but whose serialized worker-finished payload would exceed this ceiling is deterministically downgraded to a bounded failed node result (reason failed-result, summary [handoff exceeds parallel worker-finished payload ceiling], no worker-finished event is emitted for it) — the ceiling is NOT the theoretical HandoffV1 maximum (which can reach hundreds of MB) but an economical parallel-event limit with exact-bound and one-over tests. Quantitative rationale: 256 KiB is twice the 131072-byte aggregate cap, bounding the per-DAG worst-case worker-finished storage to roughly 4 MiB across 16 workers (16 x 256 KiB) before other events, which is acceptable relative to the aggregate cap; a test asserts a realistic large-but-under-ceiling Handoff remains lossless. MAX_PARALLEL_STARTED_PAYLOAD_BYTES = 65536 (total serialized ceiling for one parallel-started event carrying dagId plus the bounded planned request manifest of up to 16 entries of requestId + nodeId + fanoutId, each under its identifier byte ceiling; exact-bound and one-over tests incl. a 16-maximum-width-identifier manifest worst case). MAX_PARALLEL_WORKER_REQUESTED_PAYLOAD_BYTES = 262144 (256 KiB total serialized ceiling for one parallel worker-requested event carrying the full WorkerSpecV1 plus the correlation triple; measured over the full JSON.stringify payload by the append helper and parser). Identifiers are bounded in UTF-8 bytes (see Identifier grammar). Each constant has exact-bound and one-over-bound tests. These are the ONLY aggregate-size authorities.

DAG field bounds (normative, exact-bound/one-over-bound tests): rootTaskId uses the scheduling identifier grammar (well-formed Unicode, ≤ 256 UTF-8 bytes); objective ≤ 4096 UTF-8 bytes; each nodeId ≤ 32 UTF-8 bytes (Identifier grammar); each dependsOn entry must satisfy the nodeId grammar; readPaths/writePaths ≤ MAX_DAG_PATHS entries each, each path ≤ 1024 UTF-8 bytes raw (grammar-valid); profile/constraints reuse the existing scheduling bounds.

### Path grammar and identifiers

Authoritative in dsh-scheduling-contracts. RepoFilePath: canonical POSIX repository-relative path, no trailing slash. RepoDirectoryPrefix: ends in /. No glob metacharacters, no . or .., drive roots, empty segments, NULs, or backslash. Case-sensitive lexical containment: RepoDirectoryPrefix p/ contains path q when q starts with p/; RepoFilePath p contains only itself. No whole-repository sentinel. write-outside-root is not a pure-validator concern in v0.4: every grammar-valid path is lexically repository-relative, and any deployment subroot restriction is enforced by the declaration-layer ownership check against declared writePaths (the write set itself is the boundary). A normative containment examples table ships with the grammar.

Identifier grammar (all limits in UTF-8 bytes). The pinned Harness SessionId is a compile-time brand over an arbitrary string with no length/ASCII validation, and SubagentRun.id is a SessionId that remote providers may mint; therefore v0.4 does NOT assume a Harness-enforced ceiling. Instead the parallel service enforces its own compatibility grammar: the root session id actually used at run() time must be ASCII ≤ 48 bytes (otherwise ParallelRunValidationError code INVALID_ROOT_SESSION_ID), and dagId = <rootSessionId>:dag:<n> is then ≤ 48 + 5 + 3 = 56 bytes (n in 1..MAX_DAG_ID_ORDINAL). nodeId grammar (exact, normative): nodeId must be well-formed Unicode (no lone surrogates), ≤ 32 UTF-8 bytes, and MUST NOT contain any of the following code points: U+003A (colon), U+0022 (double quote), U+005C (backslash), U+0000–U+001F (C0 controls), U+007F (DEL); all other code points are permitted (including letters, digits, underscore, hyphen, dot, and other punctuation). A normative regex is /^[^\u0000-\u001F\u007F\u003A\u0022\u005C]+$/u combined with a well-formed-Unicode check and the 32-byte length cap. Derived identifiers: requestId = dagId + ":node:" + nodeId ≤ 56 + 6 + 32 = 94 bytes; levelId = dagId + ":level:" + levelIndex ≤ 67 bytes; fanoutId = levelId for level scope, dagId + ":aggregate" for dag scope ≤ 67 bytes. workerRef = "w:" + sha256(workerId).slice(0,32) (34 bytes: 2 + 32 hex), derived from the full SubagentRun.id. All aggregate identifiers satisfy the existing 256-UTF-8-byte scheduling identifier ceiling by construction. workerRef uniqueness: the PRODUCER keeps a DAG-run-wide workerRef-to-full-worker-id map and raises ParallelRunValidationError code WORKER_REF_COLLISION as soon as the second distinct full worker id maps to an already-seen workerRef (after that worker committed events, before its level aggregate); each aggregate PARSER independently enforces uniqueness among the workerRefs visible in its own payload. Reuse of the same full worker id across nodes is also invalid (the Harness parent namespace is not relied on for cross-level uniqueness): the first publication wins and a later publication of the same full id also raises WORKER_REF_COLLISION. The run fails closed and the caller receives the error; no partial aggregate is produced for the affected level.

Parallel durable events stay bounded even though Harness may mint arbitrary-length SubagentRun.id values: SubagentRun.id becomes available only after subagents.start() fulfills and publishes the run, so worker-requested (appended before start) CANNOT carry workerRef. Event shapes are therefore event-specific. Parallel worker-requested is WorkerSpecV1 AND CorrelationTripleV1 (the triple is its only extension; the full WorkerSpecV1 remains, no workerRef, no childSessionId). Parallel worker-finished is { schemaVersion, workerRef, handoff } AND CorrelationTripleV1 (no childSessionId). The raw child session id is never written to any v0.4 parallel durable payload. The legacy non-parallel worker-finished v1 record retains its existing childSessionId semantics unchanged for backward compatibility; the new parallel parsers accept the old shape (childSessionId present, no correlation triple) and the new shape (correlation triple present, no childSessionId), and reject a shape carrying both.

### Task DAG

```ts
interface TaskNodeV1 {
  readonly schemaVersion: 1
  readonly nodeId: string              // unique within the graph; identifier grammar above
  readonly objective: string
  readonly profile: CapabilityProfileV1
  readonly constraints: SchedulingConstraintsV1   // sole authority for requiredTools and per-node limits; may only narrow deployment limits
  readonly readPaths: readonly (RepoFilePath | RepoDirectoryPrefix)[]   // repository-relative read declarations
  readonly writePaths: readonly (RepoFilePath | RepoDirectoryPrefix)[]  // repository-relative ownership declarations
  readonly dependsOn: readonly string[]     // nodeIds that must complete first
}

interface TaskDagV1 {
  readonly schemaVersion: 1
  readonly rootTaskId: string
  readonly nodes: readonly TaskNodeV1[]   // length >= 1 (empty DAG is a structural TypeError)
}

interface DagValidationLimitsV1 {
  readonly schemaVersion: 1
  readonly maxNodes: number        // <= MAX_DAG_NODES; deployment/runtime limit, default MAX_DAG_NODES
  readonly maxLevels: number       // <= MAX_DAG_LEVELS; default MAX_DAG_LEVELS
  readonly maxWidth: number        // <= MAX_PARALLEL_WORKERS; default MAX_PARALLEL_WORKERS
  readonly maxCumulativeWorkers: number   // <= MAX_DAG_NODES; derived from the session cumulative worker budget (budgets.maxWorkers)
}
```

parseTaskDagV1(value) is strict and bounded: it validates JSON shape, path grammar, identifier grammar (including the exact nodeId code-point rule), the DAG field bounds table, empty-DAG rejection, and deep-freezes. It throws TypeError on structural violations only (invalid JSON shape, invalid path/identifier syntax, empty nodes, over-limit per-node arrays/strings/field bytes, unknown fields). Duplicate nodeIds, self-dependency, unknown dependency references, cycle, overlap, and graph-wide limit violations are SEMANTIC issues returned by validateTaskDagV1, never thrown by the parser. validateTaskDagV1(dag: TaskDagV1, limits: DagValidationLimitsV1) accepts only already-parsed TaskDagV1 and returns DagValidationV1; valid === true only when issues is empty. Dependency chains across levels are allowed; subagentMaxDepth = 1 means each spawned worker is a leaf that never recursively delegates — it is not a graph-depth limit.

```ts
type DagValidationIssueV1 =
  | { code: 'duplicate-node'; nodeId: string }
  | { code: 'self-dependency'; nodeId: string }
  | { code: 'missing-dependency'; nodeId: string; dependsOn: string }
  | { code: 'cycle'; nodeId: string }
  | { code: 'overlapping-access'; nodeA: string; nodeB: string; mode: 'ww' | 'wr' | 'rw' }
  | { code: 'too-many-nodes'; count: number; limit: number }
  | { code: 'too-many-levels'; levelCount: number; limit: number }
  | { code: 'level-width-exceeded'; level: number; width: number; limit: number }
  | { code: 'cumulative-worker-limit-exceeded'; count: number; limit: number }

interface DagValidationV1 {
  readonly schemaVersion: 1
  readonly valid: boolean
  readonly issues: readonly DagValidationIssueV1[]   // deterministic order, see comparator below
  readonly levels: readonly (readonly string[])[]
  readonly levelCount: number                        // 0 when any cycle or malformed node blocks a full acyclic ordering; otherwise max dependency depth + 1; a non-empty graph with no edges has levelCount 1
}
```

Node eligibility before topological layering: duplicate-ID declarations are all omitted from levels (each duplicated id emits one duplicate-node issue); missing-dependency is emitted ONLY for direct references to a nodeId that does not exist (each direct missing reference emits one issue carrying its own dependsOn), and every node downstream of a missing reference — direct or transitive — is omitted WITHOUT additional missing-dependency issues (deterministic: a node reachable from multiple missing roots is omitted once and emits no extra issue); a self-dependent node emits exactly one self-dependency issue and is omitted (it does not additionally emit cycle); nodes in a non-trivial strongly connected component (SCC) each emit one cycle issue (all cycle issues ordered lexically by nodeId after rank) and are omitted along with every node downstream of the SCC. levels then contains each eligible unique node exactly once in topological order; when no eligible node remains, levels is empty and levelCount is 0. levelCount is 0 whenever any cycle or malformed-node exclusion occurred; otherwise max dependency depth + 1.

Deterministic issue ordering uses a per-code numeric rank in this order: duplicate-node(1), self-dependency(2), missing-dependency(3), cycle(4), overlapping-access(5), too-many-nodes(6), too-many-levels(7), level-width-exceeded(8), cumulative-worker-limit-exceeded(9), then a full comparator key per issue variant: (rank, nodeId, dependsOn) for missing-dependency; (rank, nodeId) for duplicate-node/self-dependency/cycle; (rank, nodeA, nodeB, mode) for overlapping-access with nodeA and nodeB canonicalized lexically; (rank, limit, count) for too-many-nodes/cumulative-worker-limit-exceeded; (rank, limit, levelCount) for too-many-levels; (rank, level, limit, width) for level-width-exceeded. overlapping-access carries no path.

Overlap generation: only nodes in the same COMPUTED ready level (and therefore eligible to execute in the same fan-out) are compared; two dependency-incomparable nodes that land in different computed levels because one has a longer dependency chain never run concurrently and are not compared. For each unordered pair the read/write declarations are intersected under the grammar: a write-write, write-read, or read-write overlap on any path emits at most one issue per pair with mode precedence ww < wr < rw (the most severe present mode wins); nodeA/nodeB are canonicalized lexically. Sequential producer-consumer access across dependency-ordered levels is allowed and never emits overlap. An ownership violation blocks only dependent descendants; independent eligible branches in the same or later levels continue unless verification scope, budget, or an execution-stopping rejection stops the DAG.

### Dependency readiness and propagation (normative)

A node is EXECUTABLE only when every dependency has status completed with an ownership-valid Handoff. If any dependency has ANY other outcome — failed, blocked, ownership-violation, or ANY not-run reason (dependency-not-run, zero-worker-constraint, no-route, tool-unauthorized, admission-rejected, level-verification-stopped, cancelled-before-start) — the node becomes not-run with reason dependency-not-run, recursively and deterministically, BEFORE constraint classification or admission. Propagation runs over the validated DAG in level order: once a node is marked not-run for any reason, every node downstream of it in the same or later levels is marked not-run/dependency-not-run (a node reachable from multiple non-ready prerequisites is marked once). Example: A(no-route) → B → C yields A = not-run/no-route, B = not-run/dependency-not-run, C = not-run/dependency-not-run; only A retains its own reason.

Reason-assignment precedence vs global stops (normative): (1) while the DAG remains active, dependency readiness runs before classification and ordinary non-ready descendants receive dependency-not-run; (2) once a fan-out admission rejection occurs, readiness is NOT run on remaining levels and every not-yet-published node — direct descendants and independent branches alike — receives admission-rejected (never dependency-not-run, never rewritten from an earlier classification); (3) once a level verification outcome stops execution, every remaining not-yet-published node receives level-verification-stopped (never dependency-not-run, never admission-rejected); (4) already-published or already-classified outcomes are never rewritten. A node that was already classified not-run for its own reason before a global stop (for example zero-worker-constraint in an earlier level) keeps its own reason.

### Constraints intersection (deployment ∩ node), field by field

The effective capability request per node is computed deterministically after the dependency-readiness pass. Node constraints may only narrow deployment limits; each field's operation and empty-result behavior:

| Field | Operation | Empty / invalid result |
| --- | --- | --- |
| maxWorkers | ignored for fan-out width (width comes from the validated level, bounded by parallel.maxParallelWorkers); node maxWorkers 0 remains structurally valid and makes the node not-run with reason zero-worker-constraint | not-run node, no admission |
| maxOutputTokens | min(deployment fixed worker ceiling, node value) | n/a (min is total) |
| maxLatencyMs | min(deployment ceiling, node value) | n/a |
| allowPaidFallback | AND (deployment must allow and node must allow) | false → no paid fallback, deterministic |
| allowedProviders | intersection of deployment allowed routes' providers and node list; if empty → no catalog route, fail closed | fail closed: node not-run (reason no-route), no worker admitted |
| requiredTools | every node-required tool must be in the deployment worker-tool allowlist AND in the selected route's tool filter (scheduler catalog entry when the Scheduler is present; the configured route-to-tool-filter map when absent); otherwise fail closed | fail closed: node not-run (reason tool-unauthorized), no worker admitted |
| string/item/token ceilings | min with scheduling contract ceilings | n/a |

Empty intersections fail closed with the node reported not-run and a typed reason, never by silently dropping the requirement. Scheduler-absent tool authorization: the deployment parallel config owns a worker-tool allowlist and a route-to-tool-filter map (validated in parseConfig), so both the Scheduler-present and Scheduler-absent (fixed-route fallback) paths apply the same tool intersection; the worker allowlist (SubagentStartRequest.toolFilter) is exactly the effective requiredTools of the accepted route in both paths.

### Widened worker model, budgets, and parallel config

SchedulingConstraintsV1.maxWorkers becomes 0..MAX_PARALLEL_WORKERS (per-request worker width). ScheduleDecisionV1 is unchanged: each worker keeps mode single-worker, workerCount 1, and its own route. Parallel execution is an Orchestrator-level execution mode driven by the validated DAG; the Scheduler never emits a batch decision and cannot change the DAG, write sets, or worker count. Existing single-worker/direct fixtures/tests remain valid.

Two distinct limits exist, with distinct bounds:
- maxParallelWorkers (max ready-level width): 0..MAX_PARALLEL_WORKERS (8). This is parallel.maxParallelWorkers.
- budgets.maxWorkers (cumulative per-session worker budget) and every worker counter in BudgetViewV1: 0..MAX_DAG_NODES (16). This is the ceiling a whole multi-level DAG runs under.

DAG validation checks max ready-level width (≤ maxWidth), total node count (≤ maxCumulativeWorkers via cumulative-worker-limit-exceeded, and ≤ maxNodes via too-many-nodes). Runtime admission: per ready level the Orchestrator FIRST runs the dependency-readiness pass, then classifies every remaining ready node through the constraint intersection (nodes that become not-run consume nothing), then forms the executable set; admitFanout(executableSet.length) is called ONLY when that set is non-empty, charging one internal delegate_worker action per executed level and exactly executableSet.length cumulative worker admissions; a level with zero executable nodes performs no fan-out admission and consumes no action or worker budget, and emits NO level aggregate (a level aggregate is emitted only for a level in which at least one worker was admitted). Each verification command actually run consumes one targeted_verify action. Atomic algorithm: take a pre-admission snapshot, compute requested {workers: N, actions: 1}, and evaluate each counter's post-request slack = limit - (current + requested); if both would overflow, report the rejection with the more negative slack first (tie: worker rejection first); DISPOSED takes precedence over both; exactly one durable budget-rejected event is emitted for an atomic fan-out failure; commit all counters or none through a single internal atomic mutation path (never by composing the side-effecting scalar admit methods, which would double-record rejections). admitFanout is never exposed to the Scheduler. A preflight DAG/ownership failure consumes no budget. A runtime declaration-layer ownership violation consumes the admitted execution budget but blocks aggregation. Fan-out admission rejection STOPS THE WHOLE DAG: every executable node in the rejected set becomes not-run with reason admission-rejected, and every later node that does not already have a published or classified outcome (in all later levels, including independent branches that do NOT continue) also becomes not-run with reason admission-rejected; every previously assigned outcome retains its own reason (never rewritten). The cumulative aggregate reports blocked (never completed).

Strict Orchestrator config gains an optional parallel block with this exact shape (added to types/parser under dsh-orchestrator):

```ts
interface ParallelConfigV1 {
  readonly maxParallelWorkers: number       // 0..min(MAX_PARALLEL_WORKERS, budgets.maxWorkers); no coupling to DAG shape
  readonly verification: ParallelVerificationPolicyV1
  readonly workerToolAllowlist: readonly string[]          // deployment-authorized worker tools (never includes targeted_verify)
  readonly routeToolFilters: Record<string, readonly string[]>   // route key -> tool filter, used by the Scheduler-absent fixed-route fallback
}
```

parseConfig accepts an optional top-level parallel key with only these fields. Conditional mode/budget semantics: without parallel, mode single-worker requires budgets.maxWorkers === 1 and mode direct requires budgets.maxWorkers === 0 exactly as today; with parallel, the model-facing delegate_worker under mode single-worker remains one-shot while the root controller may carry cumulative budgets.maxWorkers up to MAX_DAG_NODES for the internal parallel service, and mode direct remains incompatible with parallel (parseConfig rejects parallel alongside direct). A profile without parallel stays direct/single-worker exactly as today.

### Declaration-layer ownership

Parallel-only two-stage ownership projection (preserves existing public parseHandoff behavior unchanged): stage 1 strictly validates the Handoff envelope and the bounded raw changedFiles strings WITHOUT path normalization or slash-dot-segment rewriting, preserving each raw string exactly; stage 2 feeds those raw strings into checkOwnership. checkOwnership: a changed file is valid iff it parses as RepoFilePath AND is contained by some writePath; every raw changed file that cannot parse as RepoFilePath under the repository path grammar (glob characters, control characters, lone surrogates, over-length, traversal, backslash or dot-segment remnants) is itself an ownership violation — never an uncaught exception. For each invalid or over-1,024-byte path the digest commits over an exact tagged token: a record containing the invalidity class and the sha256 hex of the raw UTF-8 bytes of the path, which is bounded and deterministic; grammar-invalid and over-1,024-byte paths both contribute to count and digest but are omitted from samplePaths, which only ever carry whole grammar-valid display paths. Returns the sorted unique set of violating canonical paths (sorted-unique: duplicates collapse in count and digest). Only grammar-valid paths are converted to canonical RepoFilePath values for accepted Handoffs; normalization never runs before ownership checking. A worker whose Handoff changedFiles contains any path outside its declared writePaths is marked ownership-violation; its Handoff is not aggregated and its changes are not reported as accepted. Because workers self-report changedFiles, this cannot detect unreported shared-tree mutations (deferred isolation work), and v0.4 never claims otherwise. The builder records, per ownership-violation node, the exact violation count and a sha256 digest commitment over a canonical byte preimage (see Ownership digest), plus up to MAX_DAG_CHANGED_FILES sample display paths retained whole.

### ParallelAggregateV1, builder/parser guarantees, and aggregate-size budget

```ts
type VerificationOutcomeV1 =
  | 'not-run-no-commands'       // policy has zero commands (producer guarantee: the payload does not carry the policy)
  | 'not-run-no-accepted-nodes' // no accepted node existed, so verification was skipped
  | 'passed'                    // all admitted commands passed
  | 'command-failed'            // an admitted command produced non-passing evidence (failed | timed-out | spawn-error), stop-on-first-failure
  | 'admission-rejected'        // a targeted_verify admission was rejected before that command ran

type NodeOutcomeReasonV1 =
  | 'dependency-not-run'          // a dependency failed/blocked/violated or is ANY form of not-run
  | 'zero-worker-constraint'      // node constraints.maxWorkers === 0
  | 'no-route'                    // empty allowedProviders/route intersection
  | 'tool-unauthorized'           // required tool not in allowlist/route filter
  | 'admission-rejected'          // level admitFanout rejected (whole DAG stops)
  | 'level-verification-stopped'  // a non-passing level verification outcome (failure OR admission rejection) stopped the DAG
  | 'cancelled-before-start'      // parent signal aborted before a child published
  | 'cancelled-after-start'       // parent signal aborted after a child published; maps to status blocked (canonical)
  | 'start-failed'                // subagents.start rejected before a child published (no abort observed)
  | 'blocked-result'              // worker returned a blocked handoff
  | 'failed-result'               // worker returned a failed handoff
  | 'completed'                   // ran to completion (only for status completed)
  | 'violation'                   // ownership-violation (only for status ownership-violation)

interface ParallelNodeResultV1 {
  readonly schemaVersion: 1
  readonly nodeId: string
  readonly requestId: string            // deterministic pre-admission invocation id; derived for every node including not-run
  readonly workerRef?: string           // "w:" + sha256(workerId).slice(0,32); present iff a child was successfully published (after-publication outcomes only)
  readonly status: 'completed' | 'blocked' | 'failed' | 'ownership-violation' | 'not-run'
  readonly reason: NodeOutcomeReasonV1  // one-to-one canonical grammar below; enables payload-reconstructable aggregate status
}

interface OwnershipViolationSummaryV1 {
  readonly nodeId: string
  readonly count: number                          // exact violation count, 1..128 (a worker Handoff changedFiles allows up to 128 entries)
  readonly digest: string                         // sha256 hex over the canonical preimage of the sorted unique violating paths (collision-resistant)
  readonly samplePaths: readonly string[]         // sorted unique, length <= min(MAX_DAG_CHANGED_FILES, count), each whole and <= MAX_AGGREGATE_PATH_BYTES raw
}

interface ParallelAggregateV1 {
  readonly schemaVersion: 1
  readonly dagId: string             // identifies the whole DAG run; durable across same-process service-generation reloads
  readonly scope: 'level' | 'dag'
  readonly fanoutId: string          // level scope: levelId; dag scope: dagId + ":aggregate"
  readonly levelId?: string          // present when scope === 'level'
  readonly levelIndex?: number       // deterministic 0-based level ordinal; present when scope === 'level'
  readonly nodeResults: readonly ParallelNodeResultV1[]   // unique nodeIds and requestIds; deterministic order (level then lexical nodeId); full Handoffs are NOT embedded (they live in worker-finished events and are referenced by requestId)
  readonly aggregateStatus: 'completed' | 'blocked' | 'failed' | 'verification-failed'
  readonly verificationOutcome: VerificationOutcomeV1     // required typed state; parser derives aggregateStatus from nodeResults + this field (never from projectedHandoff prose)
  readonly verification?: readonly VerificationEvidenceV1[]   // aggregate projections, bounded by MAX_AGGREGATE_VERIFICATION_TOTAL_BYTES; canonical form: OMITTED when verificationOutcome is not-run-* or no command was attempted, otherwise present (a present array has >= 1 attempted command evidence)
  readonly ownershipViolations: readonly OwnershipViolationSummaryV1[]   // per-node summaries; bounded by MAX_AGGREGATE_VIOLATION_BYTES
  readonly projectedHandoff: HandoffV1    // deterministic BOUNDED projection (never the full union); bounded by MAX_AGGREGATE_PROJECTED_HANDOFF_BYTES
  readonly projectedHandoffTruncated?: true   // set when the projection dropped content that the full union would have contained
}
```

Canonical status/reason/workerRef grammar (exactly one legal status per reason; parser-enforced):
- status completed ⇒ reason completed, workerRef present;
- status blocked ⇒ reason blocked-result (workerRef present) or cancelled-after-start (workerRef present) — cancelled-after-start maps canonically to blocked, never failed;
- status failed ⇒ reason start-failed (workerRef absent), failed-result (workerRef present), or handoff-payload-too-large (workerRef present; no worker-finished event is emitted for this reason);
- status ownership-violation ⇒ reason violation, workerRef present;
- status not-run ⇒ reason dependency-not-run, zero-worker-constraint, no-route, tool-unauthorized, admission-rejected, level-verification-stopped, or cancelled-before-start — ALL workerRef absent.
workerRef is present for all and only after-publication outcomes (completed, blocked-result, cancelled-after-start, failed-result, violation, handoff-payload-too-large); absent for every pre-publication outcome (all not-run reasons, start-failed, cancelled-before-start). handoff-payload-too-large is the sole after-publication reason with workerRef present but NO worker-finished event (the oversized Handoff is never appended); every other after-publication reason emits exactly one worker-finished. There is no generic cancelled reason.

Cancellation classification (exact race rule, matching the pinned Harness publication boundary): subagents.start() fulfills only with a published run and rejects with cleanup when cancelled before publication. Per node: (a) start() rejects AND the signal is aborted when the rejection is observed → cancelled-before-start; (b) start() rejects with no abort observed → start-failed; (c) start() fulfills → publication has occurred; any later abort or result interruption → cancelled-after-start (with workerRef and exactly one worker-finished); (d) once fulfilled, a node is NEVER retroactively classified as pre-publication. Race tests cover abort-before-call, abort while start() is pending, and abort immediately after fulfillment.

Ownership digest preimage: sha256 over the UTF-8 bytes of JSON.stringify(sortedUniqueCanonicalPaths), where sortedUniqueCanonicalPaths is the sorted array of the node's canonical violating paths. Digest scope is per node (nodeId + digest), so two nodes with identical violating sets remain distinct. count is in 1..128 (never 0 for an ownership-violation node); samplePaths are sorted unique with samplePaths.length <= min(MAX_DAG_CHANGED_FILES, count); summaries are ordered lexically by nodeId.

Deterministic identifiers. dagId = <rootSessionId>:dag:<n> where rootSessionId is ASCII ≤ 48 bytes (otherwise ParallelRunValidationError code INVALID_ROOT_SESSION_ID) and n is a decimal ordinal 1..MAX_DAG_ID_ORDINAL allocated synchronously before any admission; the service appends a bounded dsh-plugin/parallel-started event carrying dagId at allocation time (before any worker starts). Ordinal initialization scans the live session log for parser-valid parallel-started and parallel-finished records whose dagId exactly matches the current root prefix and valid decimal grammar, taking the maximum n; malformed, foreign-root, or invalid records are ignored (never fail-closed, never counted). When n would exceed MAX_DAG_ID_ORDINAL, the service raises ParallelRunValidationError code DAG_ID_EXHAUSTED before parallel-started and before any admission. Overlapping old/new service generations are serialized by requiring old-generation disposal before a replacement allocation (enforced by the service registry); allocation is synchronous under the service lock. workerRef = "w:" + sha256(workerId).slice(0,32) is derived from the full SubagentRun.id (which is never written to a parallel durable payload); workerRef collisions are detected DAG-run-wide by the producer (see Identifier grammar); ParallelRunValidationError code WORKER_REF_COLLISION is raised before the affected level's aggregate is emitted.

workerRef collision-map lifecycle (normative): every active run() owns its collision map in the invocation closure, so no DAG execution ever crosses a service generation. Service disposal aborts and awaits all active runs before a replacement service may register or allocate; the replacement never inherits in-flight run state. Collision state is NEVER reconstructed from worker-finished events, because parallel durable events intentionally lack the full worker id. An acceptance test reloads after a first-level publication and asserts the old generation disposal controller is aborted with generation-disposed, the active run promise settles (rejection or terminal aggregate as specified in Runtime activation), no replacement allocation occurs before settlement, and no later-level publication occurs in the new generation without a fresh run.

Builder guarantees (producer): node order level-then-lexical; node results carry no embedded Handoffs (full Handoffs are emitted in worker-finished events and correlated by requestId); ownership-violation summaries are exact in count and digest with bounded whole samplePaths; projectedHandoff is a deterministic bounded projection (below); verification evidence is projected per command under the sub-budgets with derived truncated and preserves command order; verificationOutcome is set from the typed verification state, never inferred from prose. Producer-only guarantees (not payload-verifiable): whether the configured command count was zero (the payload does not carry the policy); the exact recomputation of violation counts/digests from changedFiles.

Aggregate-size budget (normative, serialized JSON bytes incl. keys, quotes, delimiters, escaping). One ParallelAggregateV1's serialized UTF-8 payload must be ≤ MAX_AGGREGATE_PAYLOAD_BYTES = 131072. The deterministic builder enforces these sub-budgets in fixed order over the exact serialized fragments; the values are the ONLY normative authority:
1. nodeResults + identifiers + envelope ≤ 16384 (16 nodes; each node result fragment is small: nodeId ≤ 32 B, requestId ≤ 94 B, workerRef = 34 B or absent, status/reason ≤ 24 B, keys/escaping bounded; the builder measures each serialized fragment and the section always fits 16 × worst-case ≤ 16384);
2. verification evidence ≤ MAX_AGGREGATE_VERIFICATION_TOTAL_BYTES = 49152 (a hard serialized-section cap): the builder first serializes ALL command metadata records in command order (per command ≤ MAX_AGGREGATE_VERIFICATION_METADATA_SERIALIZED_BYTES = 4096 measured as JSON.stringify UTF-8 of name+args+exitCode+status+durationMs+keys — the 8-arg × 256-byte maximum serializes to ~2.5 KB, within 4096), then measures the remaining section budget and allocates output (combined stdout+stderr) in command order, shortening each output fragment until the complete serialized record fits both its per-command serialized cap and the section cap; because the section cap is hard and measured over serialized bytes, output may retain fewer than MAX_AGGREGATE_VERIFICATION_OUTPUT_BYTES raw bytes when JSON escaping expands; only stdout/stderr are shortened; name/args/exitCode/status/durationMs are preserved; truncated = source.truncated || stdoutWasCut || stderrWasCut; evidence array order equals command order;
3. ownershipViolations summaries ≤ MAX_AGGREGATE_VIOLATION_BYTES = 24576 via a global all-or-none algorithm: (a) serialize count+digest summaries for every violating node (this always fits: 16 × ~150 B << 24576); (b) build the COMPLETE bounded candidate sample set in lexical node-then-path order, omitting any path that cannot be represented whole under MAX_AGGREGATE_PATH_BYTES; (c) serialize the entire section including all candidate samples; (d) if the section fits ≤ 24576, every summary keeps its full candidate samples; otherwise every summary is emitted with samplePaths: [] (count+digest exactness is never affected). There is no incremental retention and no partial-prefix result.
4. projectedHandoff ≤ MAX_AGGREGATE_PROJECTED_HANDOFF_BYTES = 24576 (serialized-budget-aware projection, below);
5. structural/rounding headroom ≤ 16384.
Sum: 16384 + 49152 + 24576 + 24576 + 16384 = 131072 exactly. The v0.4 gate includes a worst-case test with maximum identifiers, JSON-escapable characters in fields that permit them (verification output and Handoff text — node IDs reject the forbidden code points and are covered by rejection tests), maximum verification args/output, and maximum violation counts, asserting the serialized aggregate ≤ 131072 bytes and parses.

projectedHandoff projection rules (deterministic, serialized-budget-aware, always a valid HandoffV1 under the existing 128-item / 16 KB-string ceilings): the builder accumulates the full intended content (summary concatenation, lexically-deduplicated changed-file union, decisions union, blocker list, verification projections), then retains whole items in deterministic order (lexical for changedFiles/decisions/blockers; node order for summary) up to per-field serialized quotas that sum, with the Handoff envelope, to ≤ MAX_AGGREGATE_PROJECTED_HANDOFF_BYTES = 24576; per-field quotas: summary ≤ 4096 B, changedFiles ≤ 8192 B (whole items only), decisions ≤ 4096 B, blockers ≤ 4096 B, verification ≤ 2048 B, envelope/key overhead within the remainder. status maps from aggregateStatus (completed → completed; blocked → blocked; verification-failed → failed with the exact [verification: failed] marker; failed → failed). projectedHandoffTruncated is set whenever any field retained fewer whole items than the full intended content or the summary was cut (trailing [summary truncated] marker). Because item retention is whole-item and lexical, no path identity is ever corrupted by mid-string truncation. When verificationOutcome === 'admission-rejected', the exact [verification: budget-rejected] marker is RESERVED in projectedHandoff.blockers before any ordinary blocker is selected: the builder sets aside one blocker slot and its serialized bytes for the marker (deduplicating if the marker is already present in the intended blocker content), then fills the remaining item/byte capacity with ordinary blockers in the stated lexical order, and sets projectedHandoffTruncated if reserving the marker displaced content. The marker is therefore present UNCONDITIONALLY on admission-rejected aggregates — regardless of aggregate-status precedence and regardless of whether zero commands or some passing commands ran first (node outcomes determine aggregateStatus but never erase truthful verification state), and it can never be dropped by the blockers byte/item quota.

Parser guarantees (parseParallelAggregateV1, enforced from the payload): nodeIds and requestIds unique; workerRef present per the canonical status/reason/workerRef grammar and unique among present values; ownershipViolations summaries reference only ownership-violation nodes, every ownership-violation node has exactly one summary with count in 1..128, and no other node has a summary; digests are 64-hex sha256; summaries ordered lexically by nodeId; scope 'level' has levelId/levelIndex and nodeResults bounded by MAX_PARALLEL_WORKERS; scope 'dag' has no levelId/levelIndex and nodeResults bounded by MAX_DAG_NODES; serialized UTF-8 payload ≤ MAX_AGGREGATE_PAYLOAD_BYTES; projectedHandoff is a parse-valid HandoffV1; verificationOutcome canonical invariants (payload-reconstructable): not-run-no-commands requires omitted verification; not-run-no-accepted-nodes requires no accepted node and omitted verification; passed requires ≥ 1 admitted command with all evidence status passed and verification present; command-failed requires ≥ 1 admitted command whose retained evidence is a canonical stop-on-first-failure sequence — every record before the last has status passed and the last has status failed | timed-out | spawn-error (no record may follow the terminal non-passing record); admission-rejected requires zero or more retained records ALL with status passed (the rejected command itself has no evidence), verification present only if ≥ 1 record exists otherwise omitted, AND the exact [verification: budget-rejected] marker present in projectedHandoff.blockers (a payload whose verificationOutcome is admission-rejected but whose projected Handoff lacks the marker is rejected). No evidence sequence the producer could not emit is accepted: a non-passing record followed by anything (such as [failed, passed]) is rejected. The mapping from verificationOutcome to "zero configured commands" is a producer guarantee (the payload does not carry the policy). aggregateStatus is recomputed from nodeResults + verificationOutcome and must equal the stored value (payload-reconstructable). Exact recomputation of violation counts/digests from changedFiles is a builder guarantee, not a parser guarantee.

Aggregate status derivation (first match wins, exhaustive; derived from node statuses+reasons and verificationOutcome, never from projectedHandoff prose):
1. any node failed → failed;
2. any ownership-violation or blocked node → blocked;
3. any not-run node (ANY not-run reason: dependency-not-run, zero-worker-constraint, no-route, tool-unauthorized, admission-rejected, level-verification-stopped, cancelled-before-start) → blocked; a DAG is completed ONLY when every node has status completed;
4. verificationOutcome === 'admission-rejected' (and no higher-precedence node outcome) → failed;
5. verificationOutcome === 'command-failed' (and no higher-precedence node outcome) → verification-failed;
6. verificationOutcome === 'not-run-no-accepted-nodes' or no accepted node → blocked with an explanatory summary;
7. otherwise (every node completed, verificationOutcome 'passed' or 'not-run-no-commands') → completed.

Node outcomes (failed/blocked/ownership-violation/any not-run) outrank verification admission rejection and verification command failure for aggregateStatus; they do NOT erase the [verification: budget-rejected] marker when verificationOutcome is admission-rejected. completed is reachable only when every node ran to completion (status completed, reason completed) and verificationOutcome is 'passed' or 'not-run-no-commands' (all-completed plus a zero-command policy yields completed).

### DAG-wide final result

Level-scope execution emits one level aggregate per executed level in which at least one worker was admitted (each also emits one parallel-finished event) AND one cumulative scope-dag final aggregate after the whole run (also emitted as a parallel-finished event). A processed level whose entire ready set became not-run before admission (zero-executable) emits NO level aggregate and NO parallel-finished event for that level; its nodes still appear as not-run in the final cumulative aggregate. A level whose fan-out admission was rejected also emits no level aggregate (nothing was admitted). ParallelRunResultV1.aggregates contains every emission (level aggregates in level order, then the final DAG aggregate); finalAggregate is the cumulative scope-dag aggregate whose nodeResults contain every node of the DAG (level-scope node results merged in level-then-lexical order) and whose projectedHandoff is the parent-visible result. All emissions are non-additive for replay/telemetry — a replay consumer MUST reconstruct one final node set from the final scope-dag event, never concatenate node arrays across parallel-finished events (double-counting); only the level aggregates are intermediate snapshots, while finalAggregate is the terminal parent-visible result. Nodes skipped because a non-passing level verification outcome or admission rejection stopped execution are recorded as not-run with the typed reason (level-verification-stopped / admission-rejected) in the final aggregate, and the final aggregate reports blocked per derivation step 3. DAG-scope execution emits exactly one scope-dag aggregate (and one parallel-finished event); aggregates = [finalAggregate].

Level-scope verification fold (normative): each level aggregate carries only that level's verification invocation evidence and outcome. The final cumulative DAG aggregate carries evidence only from the LAST verification invocation that actually ran across the whole DAG; all earlier command evidence remains in the durable verification-finished events and the per-level aggregate events. The final aggregate's verificationOutcome is that last invocation's outcome, with two exceptions: a zero-command policy always yields not-run-no-commands on the final aggregate, and a DAG in which no verification invocation ran at all yields not-run-no-accepted-nodes. Because ANY non-passing level verification outcome stops subsequent levels, every earlier non-passing invocation is necessarily terminal (it is the last invocation that ran) and its outcome is the final outcome. The final verification evidence therefore never exceeds MAX_VERIFICATION_COMMANDS records, so the single four-command / MAX_AGGREGATE_VERIFICATION_TOTAL_BYTES budget applies unchanged to the final aggregate. Multi-level tests must cover: all levels pass, an early level command failure (terminal), an early level admission rejection (terminal), an unaccepted level followed by an independent accepted level that verifies, and the four-level × four-command maximum.

Level-scope behavior after a later fan-out admission rejection (explicit): level scope does NOT verify the rejected level (nothing was admitted) and emits NO level aggregate for it; the final cumulative DAG aggregate folds from the last earlier level-verification invocation that ran, while the rejected level's and all later nodes are not-run (admission-rejected), so the final aggregate status is blocked. Test: three-level level-scope — level 1 accepted and verified, level 2 fan-out rejected, level 3 not run; only level 1 emits a level aggregate, final evidence/outcome folds from level 1, and final status is blocked.

Explicit three-level fold example: under a non-empty level policy, a normally completed ownership-valid level always has accepted nodes and therefore runs level verification. Level 2 is therefore the last invocation only when level 3 has NO accepted nodes, which requires level 3's nodes to be failed, blocked, ownership-violating, or not-run — never completed. The cumulative final aggregate still contains all three levels' node results (level 3's nodes carry their non-completed statuses) and carries only level 2's verification evidence and outcome; "completed with no verification" is illegal under a non-empty level policy.

### Durable events, compatibility, and Orchestrator-local worker-event parsers

Existing per-worker events (schedule-selected target=worker, worker-requested, worker-finished) remain byte-compatible v1 payloads for non-parallel runs. Worker-event types (WorkerSpecV1, WorkerFinishedV1) and append helpers stay Orchestrator-local exactly as today; v0.4 ADDS strict Orchestrator-local parsers for worker-requested and worker-finished (parseWorkerRequestedV1 / parseWorkerFinishedV1) so the old-without-correlation and new-with-correlation shapes are actually enforced by code, and both append helpers and replay consumers must use them. Correlation grammar (normative, consistent everywhere): the triple fanoutId + nodeId + requestId is all-present on parallel worker events and all-absent on old/non-parallel events; a partial triple is rejected by the parsers; the triple is FORBIDDEN on schedule-selected with target root; nodeId follows the node identifier grammar and requestId/fanoutId follow their derived identifier grammars. Bounded parallel payloads (event-specific shapes): parallel worker-requested is WorkerSpecV1 AND CorrelationTripleV1 (no workerRef, no childSessionId, because the run id is not yet known); parallel worker-finished is { schemaVersion, workerRef, handoff } AND CorrelationTripleV1 (no childSessionId); the legacy non-parallel worker-requested shape is the existing WorkerSpecV1 with no correlation; the legacy non-parallel worker-finished shape retains childSessionId plus Handoff with no correlation or workerRef. The parallel parsers enforce these exact event-specific unions: each event accepts its legacy shape or its parallel shape, and rejects a shape carrying both (workerRef plus childSessionId, or a correlation triple plus childSessionId). For parallel runs, v0.4 mandates one design (no fallback). The four complete worker-event unions are, in TypeScript form:

	type CorrelationTripleV1 = { fanoutId: string; nodeId: string; requestId: string }
	type LegacyWorkerRequestedV1 = WorkerSpecV1            // no correlation fields
	type ParallelWorkerRequestedV1 = WorkerSpecV1 & CorrelationTripleV1    // triple is the ONLY extension; the full WorkerSpecV1 remains
	type LegacyWorkerFinishedV1 = { schemaVersion: 1; childSessionId: string; handoff: HandoffV1 }   // no correlation, no workerRef
	type ParallelWorkerFinishedV1 = { schemaVersion: 1; workerRef: string; handoff: HandoffV1 } & CorrelationTripleV1   // no childSessionId

The phrase triple only means the triple is the only parallel correlation/provenance extension; it never means the event contains only those three fields. The correlation fields are REQUIRED on the parallel branch and FORBIDDEN on the legacy branch (never optional additive on a shared shape). Branch discrimination is contextual, never derivable from an uncorrelated standalone payload: a worker record without the triple is byte-for-byte a valid legacy record, because old logs carry no discriminator, so structural parsers interpret it as legacy. Append helpers and the replay validator pass an expectedBranch argument (legacy or parallel). The replay validator derives the expected parallel requestIds from the planned request manifest carried by the parallel-started event for that dagId, and validates replay cardinality against that manifest, where cardinality is derived from each node TERMINAL RESULT (not merely manifest membership): (a) every manifest entry must appear exactly once in the final DAG aggregate; (b) every not-run reason (dependency-not-run, zero-worker-constraint, no-route, tool-unauthorized, admission-rejected, level-verification-stopped, cancelled-before-start) requires ZERO schedule-selected, worker-requested, and worker-finished events; (c) start-failed and cancelled-before-start require exactly one schedule-selected and one worker-requested and zero worker-finished; (d) after-publication results (completed, blocked-result, failed-result, cancelled-after-start, violation) require all three of schedule-selected, worker-requested, and worker-finished; (e) fan-out admission-rejected nodes never have durable schedule-selected or worker-requested events because those are appended only after atomic admission commits. Completed-run replay fixtures cover every not-run reason, not only interrupted prefixes. A worker record whose requestId is in the manifest but which lacks the triple is rejected as a corrupted parallel record; a triple on a record whose requestId is not in the manifest is rejected. Legacy records outside the manifest remain valid, including legacy records interleaved by concurrent non-parallel calls. Interrupted-prefix validation: a parallel-started with a manifest but no parallel-finished is an acceptable incomplete prefix when the missing tail is explained by cancellation, collision, disposal, or process interruption; a worker-requested or schedule-selected whose requestId is in the manifest but which is missing entirely is also an acceptable incomplete prefix; any record that contradicts the manifest (wrong fanoutId for its requestId, duplicate requestId, or a triple on an unplanned requestId) is corruption. Session-level ruling for manifest-less correlated records: at session replay level, any correlated worker or worker-target schedule record not anchored by exactly one preceding parser-valid parallel-started manifest entry is CORRUPTION (a session with no parallel-started, or a correlated record appearing before its parallel-started, is corrupt); only standalone structural parsing without an expectedBranch may accept an uncorrelated correlated record. Fixtures cover no-parallel-started and record-before-parallel-started sessions. Standalone structural parsing without an expectedBranch accepts both shapes (legacy or parallel) and enforces only shape-internal invariants. The same explicit union-plus-context rule applies to ScheduleSelectedV1 (triple allowed on target worker only, forbidden on target root). The replay join key for a worker is requestId (present on schedule-selected, worker-requested, worker-finished, and the node result). Event ordering and cardinality per node: schedule-selected(requestId) → worker-requested(requestId) → child start → worker-finished(requestId) when the child was successfully published. worker-finished exists ONLY after successful child publication: for start-failed and cancelled-before-start nodes there is NO worker-finished event, and replay joins schedule-selected/worker-requested directly to the node result by requestId. A node whose admitted Handoff would push the serialized parallel worker-finished payload over MAX_PARALLEL_WORKER_FINISHED_PAYLOAD_BYTES is deterministically recorded with the replay-visible terminal reason handoff-payload-too-large (status failed, workerRef present, NO worker-finished event); the ceiling check runs immediately after Handoff normalization and before any worker-finished append, and never throws. Replay distinguishes this intentional omission from event loss by the node reason itself, so cardinality is exact for this reason. Per aggregate: parallel-finished after all its workers' terminal events. Level-scope workers carry the level fanoutId; DAG-scope workers carry the DAG aggregate fanoutId. Old logs without the fields and new logs with them both parse; replay covers both shapes. schedule-selected for non-parallel runs remains exactly v0.3. One dsh-plugin/parallel-started event is appended synchronously at dagId allocation (before any worker starts) and carries dagId PLUS the bounded planned request manifest: every expected requestId with its nodeId and fanoutId for the whole DAG (bounded by MAX_DAG_NODES entries, each identifier under its byte ceiling). This manifest is the durable basis for replay branch discrimination and cardinality validation; one aggregate event dsh-plugin/parallel-finished is emitted per constructed ParallelAggregateV1 (including the cumulative final aggregate under level scope). The full per-worker Handoff remains in worker-finished (never embedded in the aggregate), so a replay consumer joins worker-finished by requestId to the aggregate node result.

### ParallelVerificationPolicyV1 and verification authority

```ts
interface ParallelVerificationPolicyV1 {
  readonly schemaVersion: 1
  readonly scope: 'level' | 'dag'     // 'level': verify after each executed level that produced accepted nodes; 'dag': verify once after all runnable levels
  readonly commands: readonly {
    readonly name: string
    readonly args: readonly string[]   // bounded by MAX_VERIFICATION_ARGS and MAX_VERIFICATION_ARG_BYTES (enforced at parseConfig)
  }[]   // ordered; bounded by MAX_VERIFICATION_COMMANDS
}
```

Sole verification authority. The deployment config's optional parallel.verification block is the ONLY source of the policy; ParallelExecutionService captures it at registration from its validated config and run() does NOT accept a policy argument, so a caller cannot bypass the validated command set. The pure contracts package provides parseParallelVerificationPolicyV1(value) for strict structural/bound checks only (shape, ordering, MAX_VERIFICATION_COMMANDS, string bounds, MAX_VERIFICATION_ARGS, MAX_VERIFICATION_ARG_BYTES). Command-existence and allowedArgs validation is Orchestrator config's job: validateParallelVerificationPolicy(policy, verificationConfig) checks every command name exists in the deployment's configured verification.commands and that every arg obeys the command's allowedArgs via the existing argument-policy validator; parseConfig runs it when the parallel block is present.

Semantics: an accepted node means the node completed with a valid, ownership-clean Handoff (independent of whether changedFiles is empty); verification runs at the policy scope when at least one accepted node exists. A non-passing command evidence is any evidence whose status is not passed (failed | timed-out | spawn-error). Scope 'level' verifies after each executed level with at least one accepted node; ANY non-passing level verification outcome — command failure (failed/timed-out/spawn-error) OR admission rejection — stops subsequent levels (remaining nodes become not-run with reason level-verification-stopped). Scope 'dag' verifies once after all runnable levels and therefore cannot prevent earlier level execution; when a later fan-out admission rejection stops execution but at least one accepted node exists from earlier levels, DAG-scope verification STILL RUNS over the accepted changes (subject to normal command admission); the not-run nodes keep the aggregate status blocked per derivation step 3 while verificationOutcome truthfully records passed, command-failed, or admission-rejected. The Orchestrator admits each command directly through the root controller (one targeted_verify action per command) and invokes VerificationService without the model-facing tool wrapper. On admission rejection: exactly the controller's one budget-rejected event is emitted on the root session; the current command is not spawned and no later command runs; evidence from any earlier attempted commands in the same policy run is preserved; verificationOutcome = 'admission-rejected'; the [verification: budget-rejected] marker is present in projectedHandoff.blockers UNCONDITIONALLY (whether zero commands or some passing commands ran first). Commands run in order; stop-on-first-failure maps the aggregate to verification-failed (derivation step 5, verificationOutcome 'command-failed') and emits verification-finished evidence per attempted command. Zero commands means no integrated verification runs (verificationOutcome 'not-run-no-commands'; producer guarantee that the configured count is zero). When no accepted node exists, verification is skipped (verificationOutcome 'not-run-no-accepted-nodes') and the aggregate reports blocked (derivation step 6). Parallel workers do NOT receive targeted_verify in their allowlists in v0.4 (worker-local verification is out of scope; integrated verification is the single verification authority for parallel runs).

Verification-with-partial-failure truth table (scope 'dag'; determines verificationOutcome, whether verification runs, and the aggregate status):

| Node outcomes | VerificationOutcome | Verification runs? | Aggregate status |
| --- | --- | --- | --- |
| all completed-and-ownership-valid (changedFiles may be empty) | passed | yes | completed |
| all completed-and-ownership-valid, a command produced non-passing evidence (failed/timed-out/spawn-error) | command-failed | yes | verification-failed |
| some accepted + some failed | passed, command-failed, or admission-rejected | yes | failed (node failed outranks) |
| some accepted + some blocked | passed, command-failed, or admission-rejected | yes | blocked (node blocked outranks) |
| some accepted + some ownership-violation | passed, command-failed, or admission-rejected | yes | blocked (violation outranks) |
| only not-run / no accepted node | not-run-no-accepted-nodes | no | blocked |
| accepted earlier + later fan-out admission-rejected (not-run) | DAG-scope verification still runs over the accepted nodes: passed, command-failed, or admission-rejected | yes (accepted nodes exist) | blocked (any not-run outranks) |
| accepted + no node failed/blocked/violation + verification admission rejected | admission-rejected | yes, until the rejected command | failed ([verification: budget-rejected] marker present) |
| accepted + node failed/blocked/violation + verification admission rejected | admission-rejected | yes, until the rejected command | failed/blocked per node outcome (node outranks aggregateStatus; marker still present) |
| all completed + zero-command policy | not-run-no-commands | no | completed |

## Runtime activation

v0.4 mandates exactly one activation seam. dsh-orchestrator exports an Orchestrator-internal ParallelExecutionService registered under the named Cordis service parallelExecution, with:

```ts
interface ParallelExecutionService {
  run(request: { dag: TaskDagV1; parent: Agent; signal: AbortSignal }): Promise<ParallelRunResultV1>
}

interface ParallelRunResultV1 {
  readonly dagId: string
  readonly aggregates: readonly ParallelAggregateV1[]   // level scope: per-admitted-level aggregates in level order then the cumulative DAG aggregate; dag scope: exactly one DAG aggregate
  readonly finalAggregate: ParallelAggregateV1          // the cumulative scope-dag aggregate (parent-visible, covers all nodes)
}
```

run does not reparse dag (the caller passes an already-parsed TaskDagV1) but DOES strictly validate the request envelope: it rejects unknown keys (including a stray policy key) with a TypeError before any admission. Runtime validation errors are a named class ParallelRunValidationError with a code discriminant: INVALID_ROOT_SESSION_ID (root session id not ASCII ≤ 48 bytes), DAG_ID_EXHAUSTED (ordinal > MAX_DAG_ID_ORDINAL), WORKER_REF_COLLISION (two distinct worker ids collide in workerRef), INVALID_DAG (carrying a frozen DagValidationIssueV1[]); they are caller-visible thrown errors, never durably appended, and no events or budget counters change before INVALID_ROOT_SESSION_ID / DAG_ID_EXHAUSTED / INVALID_DAG throw (WORKER_REF_COLLISION is raised after that level's budgets and worker events are committed, before the level aggregate is emitted). run validates against the deployment limits, allocates dagId (appending parallel-started), executes level by level under budget, enforces declaration-layer ownership, emits one ParallelAggregateV1 per policy scope boundary plus the cumulative DAG aggregate via the deterministic builder (each emission also emits one parallel-finished event), and returns ParallelRunResultV1 whose finalAggregate is the parent-visible result.

Service-generation lifecycle (normative): each service generation owns a disposal AbortController. Every run() invocation creates its own run controller whose signal is the combination of the caller signal and the generation disposal signal, and the combined signal is passed through scheduling, child startup, child results, and verification. Each invocation promise is tracked in a generation-local set. The async effect disposer aborts with the named internal reason generation-disposed, awaits Promise.allSettled over the active-run set, unregisters the parallelExecution service, and only then permits a replacement generation to register or allocate a dagId. After disposal begins, no new run() is admitted, no new worker starts, and no new dagId is allocated. run() rejects with a named ParallelGenerationDisposedError whose stable code is GENERATION_DISPOSED (never a dependency-specific cancellation wrapper). Precise commit point: if the cumulative scope-dag parallel-finished append completed before disposal began, run() returns the already-built result; otherwise run() rejects with ParallelGenerationDisposedError and does NOT synthesize a final aggregate. Already committed durable events remain individually parseable, and replay treats the run as an interrupted prefix per the interrupted-prefix validation rules. Only the test-only overlay invokes run directly; there is no model-facing parallel tool and no new deployment mode. The overlay registers the service through the real Loader with the scripted subagent provider, proving the Loader — not direct construction — registered the parallel entry point. A profile without the optional parallel config never exposes the service.

## Decision precedence

The Orchestrator owns DAG/ownership/aggregation decisions. Resource decisions keep the v0.3 scheduler precedence, applied per worker capability request; the Scheduler cannot change the DAG, write sets, or worker count beyond the validated DAG and budget. When the Scheduler is absent, the Profile fixed route is used per worker with the configured route-to-tool-filter map. Node constraints narrow but never raise deployment limits.

## Parallel execution model

- The DAG is parsed by the caller, then submitted to ParallelExecutionService.run; the verification policy comes from config.parallel.verification (never a caller argument). No scheduling or budget action occurs before validation succeeds.
- run validates the root-session id, allocates dagId (raising DAG_ID_EXHAUSTED if needed), and appends parallel-started before any worker starts. Per level the Orchestrator runs the dependency-readiness pass (every dependency completed & ownership-valid, else recursive not-run/dependency-not-run), classifies remaining ready nodes through the constraint intersection, forms the executable set, and admits exactly that set (admitFanout only when non-empty); a level completes when every executable worker Handoff is normalized and recorded. subagentMaxDepth = 1; dependency levels are orchestrated by the root, never by recursive worker delegation. An ownership violation blocks only dependent descendants; independent eligible branches continue UNLESS an execution-stopping rejection (fan-out admission rejection or non-passing level verification) stops the whole DAG.
- Each executable worker is a fresh subagents.start('spawn') child with subagentMaxDepth 1, frozen route, and an allow-only tool filter equal to the effective requiredTools of the accepted route (sole tool authority, identical in scheduler and fixed-route fallback). Workers run in the shared working tree (same execution model as Single Worker) and self-report changedFiles; they do not receive targeted_verify.
- Cancellation follows the exact race rule (cancelled-before-start / start-failed / cancelled-after-start), never retroactively reclassifying a published node.
- Declaration-layer ownership: after each worker completes, checkOwnership(changedFiles, writePaths) validates the self-reported changedFiles against declared ownership; any out-of-ownership path marks the node ownership-violation (reason violation, workerRef present) and its Handoff is not aggregated.
- Workers that fail, block, or produce invalid Handoffs do not abort healthy siblings; the aggregate reports each status with its typed reason. A node whose dependency is not completed-and-ownership-valid receives a synthetic not-run result (reason dependency-not-run, no workerRef) and consumes no worker budget. Fan-out admission rejection stops the whole DAG: the rejected executable set and every later node without an already-assigned outcome become not-run (admission-rejected); previously classified outcomes keep their own reasons. A non-passing level verification outcome stops subsequent levels: remaining nodes without an already-assigned outcome become not-run (level-verification-stopped).
- Integrated-result verification runs per the configured ParallelVerificationPolicyV1 scope when at least one accepted node exists (including after a fan-out rejection that stopped execution, under DAG scope), never redundantly per worker.

## Safe degradation

- No Scheduler → per-worker Profile fixed route with the configured route-to-tool-filter map, deterministic and keyless.
- Scheduler invalid/out-of-bound decision → same validation failure and fallback policy as v0.3; never silently expands worker count or provider.
- DAG parse/validation failure → ParallelRunValidationError code INVALID_DAG carrying frozen DagValidationIssueV1[]; caller-visible, no budget consumed, no durable event.
- Declaration-layer ownership violation at runtime → execution budget remains consumed but the node is marked ownership-violation (workerRef present) and its Handoff is not aggregated; only dependent descendants are blocked unless a rejection stops the DAG.
- Fan-out admission rejection at a level → whole DAG stops; the rejected executable set and every later node without an already-assigned outcome become not-run (admission-rejected; previously classified outcomes keep their own reasons) and the cumulative aggregate reports blocked.
- Verification admission rejection → verificationOutcome 'admission-rejected' and the [verification: budget-rejected] marker present unconditionally; aggregate failed when no higher-precedence node outcome exists; no further command runs; earlier command evidence preserved.
- Provider auth/quota/rate-limit errors never trigger silent paid fallback.
- run-started keeps actual-route semantics.

## Evaluation and error handling

Keyless replay covers:

- DAG parser rejections (invalid shape, bad path/identifier syntax incl. each forbidden nodeId code point, empty nodes, over-limit per-node arrays/strings/field bytes, unknown fields) and validator semantic issues (duplicate node, self-dependency, direct-only missing dependency with deterministic transitive omission, cycle via SCC, W/W/W/R/R/W overlap on concurrent nodes only, too-many-nodes/levels, level-width-exceeded, cumulative-worker-limit-exceeded) with the full deterministic comparator and node-eligibility rules.
- Dependency readiness and propagation: A(no-route) → B → C yields B/C dependency-not-run; every non-completed dependency outcome (including all not-run reasons) propagates; a node reachable from multiple non-ready prerequisites is marked once.
- Reason preservation under global stops (mixed-level fixture): a level with one node classified no-route plus one executable node whose admitFanout is rejected, followed by an independent later-level node; expected reasons are respectively no-route (earlier classification retained), admission-rejected (rejected executable set), and admission-rejected (later unclassified node); the analogous level-verification-stopped case is covered for a non-passing level verification outcome.
- Parallel fan-out admission: dependency-readiness → classify-then-admit sequence (executable set only; a zero-executable level consumes no action/worker budget and emits no level aggregate), N workers within width and cumulative bounds, atomic admitFanout rollback on partial failure with exactly one budget-rejected event and deterministic rejection precedence, no child start before admission commits; admission rejection stops the whole DAG and maps the cumulative aggregate to blocked.

- Declaration-layer ownership: checkOwnership containment; violation marked with reason violation and workerRef; in-ownership reports aggregated.
