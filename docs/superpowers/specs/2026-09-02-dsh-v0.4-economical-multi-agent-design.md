# DSH v0.4 Economical Multi-Agent Design

## Goal

Extend the Orchestrator so it can decompose a root task into bounded, independent sub-tasks and run them as parallel Workers whose declared file ownership is enforced at the declaration layer (each worker's self-reported changedFiles must fall inside its declared writePaths; violations fail closed and are never aggregated), then aggregate their Handoffs and verify the integrated result — while preserving the keyless v0.3 safety boundary, deterministic replay, and the single-monorepo plugin ownership model. v0.4 introduces a declarative Task DAG and independence/ownership validation as deterministic pure logic in the Orchestrator, a bounded parallel-worker execution path, declaration-layer ownership enforcement, Handoff aggregation into a strict ParallelAggregateV1, and an integrated-result verification gate. Worker processes run in the shared working tree exactly as today's Single Worker path. Physical execution isolation and trusted write capture are deferred milestones (see Deferred isolation work). No new runtime plugin beyond the Orchestrator is created; the Adaptive Scheduler continues to own resource/affinity selection.

## Scope and non-goals

v0.4 covers: the contracts needed for bounded parallel workers and task graphs; a deterministic, replayable Task DAG representation with file-ownership sets and dependency edges; a parallel fan-out path; declaration-layer ownership enforcement (self-reported changedFiles validated against declared writePaths via the authoritative path grammar in dsh-scheduling-contracts); per-worker Handoff normalization plus a strict ParallelAggregateV1 result; integrated-result verification; and a deterministic keyless replay gate over the v0.3-adaptive profile with a test-only overlay. It does not implement filesystem isolation, per-worker execution cwd binding, trusted per-worker write capture, actual-diff containment, or transactional file integration — all deferred (see below). It does not implement learning-based decomposition, LLM Judge independence approval, mutable warm worker reuse across tasks, cross-session physical worker pooling, recursive worker delegation beyond subagentMaxDepth 1, or any provider/network/real coding-task acceptance. Context-locality/prefix-compatible reuse and all deferred v0.3 roadmap items (hysteresis, shadow Judge, quota adapters) are explicitly deferred beyond v0.4. It does not modify profiles/v0.1, the Direct or Single Worker semantics, HandoffV1 projection semantics, BudgetController admission exclusivity, or the run-started actual-route projection.

## Deferred isolation work (explicitly out of v0.4 scope)

Ownership is enforced at the declaration layer in v0.4: a worker's self-reported changedFiles must be contained by its declared writePaths. This detects a worker that reports an out-of-scope mutation, but it cannot detect a worker that mutates the shared tree without reporting it, and it cannot physically prevent writes. Three stronger mechanisms are deferred to future milestones gated on verified Harness capability (the pinned Harness 0.1.1-rc.2 SubagentStartRequest has no cwd/workspace field, in-process spawn inherits the parent cwd, and per-child fs write attribution is unverified):

1. Per-worker execution cwd binding: each spawned child's process cwd/fs root points at its own isolated copy. Requires a Harness upgrade or a DSH-owned custom subagent provider that stamps child session cwd; a compatibility spike must precede it.
2. Trusted per-worker write capture: an Orchestrator-side journal of actual writes derived from the Harness fs/write-intent and fs/edit-intent event gates, attributed per child session, so ownership can be checked against real writes rather than self-reports. Requires a spike proving child-session attribution.
3. Actual-diff containment and transactional integration over isolated copies. Depends on 1 or 2.

A one-page record of these deferred items is kept in docs/superpowers/specs/2026-09-02-dsh-v0.4a-isolated-workspace-design.md so the boundary and the future seam (prepare/diff/integrate over isolated workspaces) remain documented; no v0.4a implementation is planned in this cycle.

## Baseline and constraints

- Keep DeepSeek Harness pinned at 0.1.1-rc.2 until a separate compatibility review proves an upgrade.
- Preserve Direct mode, Single Worker mode, HandoffV1, plugin-owned budgets, targeted verification, canonical dsh-plugin/ events, and the keyless DISABLED provider smoke.
- The Orchestrator owns task DAG, independence/ownership validation, worker lifecycle, final budget admission, Handoff normalization/aggregation, and event recording. The Scheduler only provides capability-to-schedule decisions.
- Do not fork or modify upstream/deepseek-harness or replace its agent loop.
- All model-visible outputs and all orchestration evidence stay bounded, provenance-carrying, and safe to replay.
- No orchestration decision may bypass the Orchestrator's hard constraints (maxWorkers, maxPluginToolActions, tool allowlist, workspace/verification policy, disjoint ownership).
- Workers run in the shared working tree and self-report changedFiles. Declaration-layer ownership means: self-reported changedFiles outside declared writePaths fail closed (node invalid, not aggregated). Physical containment is not claimed in v0.4.
- Unknown quota, price, or health values are never invented or silently estimated into hard routing decisions.
- No v0.4 profile is added. The parallel path is activated only through a validated test-only overlay over the v0.3-adaptive profile (loader-convention-compatible) plus replay fixtures in tests/replay. Real deployments enabling parallel mode are deferred until execution isolation exists.

## Architecture

The repository keeps the existing packages and adds no new runtime plugin:

```text
packages/
  dsh-scheduling-contracts/   # pure types, JSON schema, parsers; no Cordis runtime. Authority for worker model, DAG, aggregate, path grammar, and bounds
  dsh-orchestrator/           # gains task DAG, independence/ownership validation, parallel fan-out, declaration-layer ownership, aggregation
```

dsh-scheduling-contracts already defines CapabilityRequestV1, RouteDecisionV1, ScheduleDecisionV1, BudgetViewV1, ScheduleFeedbackV1, and ScheduleSelectedV1. v0.4 widens SchedulingConstraintsV1.maxWorkers and BudgetViewV1 bounds, adds the Task DAG, ParallelAggregateV1, ParallelVerificationPolicyV1, and the authoritative path grammar/types/bounds, and keeps the no-Cordis boundary. Worker-event types (WorkerSpecV1, WorkerFinishedV1) remain Orchestrator-local exactly as today; scheduling-contracts does NOT gain worker-event types or parsers (see Durable events).

dsh-orchestrator adds a deterministic pure dag.ts module (DAG parsing/validation, cycle rejection, level/topological ordering, independence check, disjoint ownership validation), a declaration-layer ownership check (changedFiles containment), a ParallelExecutionService seam, and extends the worker path so the parallel fan-out admits and runs N bounded workers with per-worker route selection, enforces declaration-layer ownership, aggregates normalized Handoffs into a ParallelAggregateV1, and runs integrated-result verification. Root route selection remains under the existing Adaptive Scheduler seam.

The execution flow:

```text
root task
  -> ParallelExecutionService.run({ dag, policy, parent, signal })   // Orchestrator-internal; only the test overlay invokes it
  -> parseTaskDagV1 (strict, bounded) + validateTaskDagV1 (semantic): acyclic, disjoint ownership, bounded nodes/levels/width, subagentMaxDepth 1
  -> per-ready-level: per-worker schedule (Adaptive Scheduler, unchanged ScheduleDecisionV1) -> hard validation -> BudgetController.admitFanout (atomic)
  -> parallel subagents.start('spawn') per worker in the shared working tree (same execution model as Single Worker)
  -> per-worker Handoff normalization (self-reported changedFiles)
  -> declaration-layer ownership check: changedFiles ⊆ declared writePaths (grammar containment); violation => node ownership-violation, not aggregated
  -> aggregate ParallelAggregateV1 (per policy scope) + integrated-result verification (ParallelVerificationPolicyV1)
  -> dsh-plugin durable events per worker and aggregate
```

## Contracts

### Constants (authoritative, in dsh-scheduling-contracts)

MAX_PARALLEL_WORKERS = 8 (max ready-level width; distinct from any configured default — config requires explicit maxWorkers); MAX_DAG_NODES = 16 (total nodes in one DAG; the cumulative per-session worker budget ceiling); MAX_DAG_LEVELS = 4; MAX_DAG_PATHS = 32 per node (readPaths and writePaths each); MAX_DAG_DEPS = 8 per node; MAX_AGGREGATE_PAYLOAD_BYTES = 65536 (total UTF-8 payload); MAX_VERIFICATION_COMMANDS = 4 (per parallelVerification policy). All string/array bounds reuse the existing scheduling/handoff byte and item ceilings. Each constant has exact-bound and one-over-bound tests.

### Path grammar

Authoritative in dsh-scheduling-contracts. RepoFilePath: canonical POSIX repository-relative path, no trailing slash. RepoDirectoryPrefix: ends in /. No glob metacharacters, no . or .., drive roots, empty segments, NULs, or backslash. Case-sensitive lexical containment: RepoDirectoryPrefix p/ contains path q when q starts with p/; RepoFilePath p contains only itself. No whole-repository sentinel. write-outside-root is not a pure-validator concern in v0.4: every grammar-valid path is lexically repository-relative, and any deployment subroot restriction is enforced by the declaration-layer ownership check against declared writePaths (the write set itself is the boundary). A normative containment examples table ships with the grammar.

### Task DAG

```ts
interface TaskNodeV1 {
  readonly schemaVersion: 1
  readonly nodeId: string              // unique within the graph
  readonly objective: string
  readonly profile: CapabilityProfileV1
  readonly constraints: SchedulingConstraintsV1
  readonly readPaths: readonly (RepoFilePath | RepoDirectoryPrefix)[]   // repository-relative read declarations
  readonly writePaths: readonly (RepoFilePath | RepoDirectoryPrefix)[]  // repository-relative ownership declarations
  readonly dependsOn: readonly string[]     // nodeIds that must complete first
  readonly requiredTools: readonly string[]
}

interface TaskDagV1 {
  readonly schemaVersion: 1
  readonly rootTaskId: string
  readonly nodes: readonly TaskNodeV1[]
}

interface DagValidationLimitsV1 {
  readonly schemaVersion: 1
  readonly maxNodes: number        // <= MAX_DAG_NODES; deployment/runtime limit, default MAX_DAG_NODES
  readonly maxLevels: number       // <= MAX_DAG_LEVELS; default MAX_DAG_LEVELS
  readonly maxWidth: number        // <= MAX_PARALLEL_WORKERS; default MAX_PARALLEL_WORKERS
  readonly maxCumulativeWorkers: number   // <= MAX_DAG_NODES; equals the session cumulative worker budget being validated against
}
```

parseTaskDagV1(value) is strict and bounded: it validates JSON shape, path grammar, per-field string/array bounds (MAX_DAG_PATHS, MAX_DAG_DEPS, string ceilings), and deep-freezes. It throws TypeError on structural violations only (invalid JSON shape, invalid path syntax, over-limit per-node arrays/strings). Duplicate nodeIds, self-dependency, unknown dependency references, cycle, overlap, and graph-wide limit violations (nodes > maxNodes, levels > maxLevels, width > maxWidth) are SEMANTIC issues returned by validateTaskDagV1, never thrown by the parser. validateTaskDagV1(dag: TaskDagV1, limits: DagValidationLimitsV1) accepts only already-parsed TaskDagV1 and returns DagValidationV1; valid === true only when issues is empty. Dependency chains across levels are allowed; subagentMaxDepth = 1 means each spawned worker is a leaf that never recursively delegates — it is not a graph-depth limit.

```ts
type DagValidationIssueV1 =
  | { code: 'duplicate-node'; nodeId: string }
  | { code: 'self-dependency'; nodeId: string }
  | { code: 'missing-dependency'; nodeId: string; dependsOn: string }
  | { code: 'cycle'; nodeId: string }
  | { code: 'overlapping-access'; nodeA: string; nodeB: string; mode: 'ww' | 'wr' | 'rw' }
  | { code: 'too-many-nodes'; count: number; limit: number }
  | { code: 'too-many-levels'; levelCount: number; limit: number }
  | { code: 'level-width-exceeded'; level: number; width: number; limit: number }

interface DagValidationV1 {
  readonly schemaVersion: 1
  readonly valid: boolean
  readonly issues: readonly DagValidationIssueV1[]   // deterministic order, see comparator below
  readonly levels: readonly (readonly string[])[]
  readonly levelCount: number                        // 0 when a cycle exists (no valid acyclic ordering); otherwise max dependency depth + 1; a graph with no edges has levelCount 1
}
```

Deterministic issue ordering uses a per-code numeric rank in this order: duplicate-node(1), self-dependency(2), missing-dependency(3), cycle(4), overlapping-access(5), too-many-nodes(6), too-many-levels(7), level-width-exceeded(8), then a full comparator key per issue variant: (rank, nodeId, dependsOn) for missing-dependency; (rank, nodeId) for duplicate-node/self-dependency/cycle; (rank, nodeA, nodeB, mode) for overlapping-access; (rank, limit, count) for too-many-nodes/too-many-levels; (rank, level, limit, width) for level-width-exceeded. Cycle membership is defined by strongly connected components (SCC): every node in a non-trivial SCC emits a cycle issue (lexically smallest nodeId first); nodes downstream of a cyclic SCC are omitted from levels; when any cycle exists, levelCount is 0 and levels contains only the acyclic schedulable nodes reachable without passing through a cycle, empty when none exist. Duplicate nodeIds: edges are resolved only against unique nodeIds; a duplicate-node issue is emitted for each duplicated id and the graph is invalid regardless of edges. overlapping-access carries no path (the pair and mode identify it); ordering never references a path for this variant.

### Widened worker model, budgets, and parallel config

SchedulingConstraintsV1.maxWorkers becomes 0..MAX_PARALLEL_WORKERS (per-request worker width). ScheduleDecisionV1 is unchanged: each worker keeps mode single-worker, workerCount 1, and its own route. Parallel execution is an Orchestrator-level execution mode driven by the validated DAG; the Scheduler never emits a batch decision and cannot change the DAG, write sets, or worker count. Existing single-worker/direct fixtures/tests remain valid.

Two distinct limits exist, with distinct bounds:
- maxParallelWorkers (max ready-level width): 0..MAX_PARALLEL_WORKERS (8). This is SchedulingConstraintsV1.maxWorkers and parallel.maxParallelWorkers.
- budgets.maxWorkers (cumulative per-session worker budget) and every worker counter in BudgetViewV1: 0..MAX_DAG_NODES (16). This is the ceiling a whole multi-level DAG runs under.

DAG validation checks max ready-level width (≤ maxParallelWorkers) and total node count (≤ maxCumulativeWorkers in DagValidationLimitsV1, which the caller derives from budgets.maxWorkers). Runtime admission adds an Orchestrator-only atomic admitFanout(workerCount): accounting rule — one delegate_worker plugin action per accepted DAG-level invocation (the root delegation), N cumulative worker admissions, and one targeted_verify action per verification command actually run by the parallelVerification policy. Atomic algorithm: take a pre-admission snapshot, compute requested {workers: N, actions: 1}, and evaluate each counter's post-request slack = limit - (current + requested); if both would overflow, report the rejection with the more negative slack first (tie: worker rejection first); DISPOSED takes precedence over both; exactly one durable budget-rejected event is emitted for an atomic fan-out failure; commit all counters or none through a single internal atomic mutation path (never by composing the side-effecting scalar admit methods, which would double-record rejections). admitFanout is never exposed to the Scheduler. A preflight DAG/ownership failure consumes no budget. A runtime declaration-layer ownership violation (detected after the worker ran) consumes the admitted execution budget but blocks aggregation.

Strict Orchestrator config gains an optional parallel block with this exact shape (added to types/parser under dsh-orchestrator):

```ts
interface ParallelConfigV1 {
  readonly maxParallelWorkers: number       // 0..MAX_PARALLEL_WORKERS; must equal budgets.maxWorkers for a single-level DAG, otherwise <= budgets.maxWorkers
  readonly verification: ParallelVerificationPolicyV1
}
```

parseConfig accepts an optional top-level parallel key with only these fields; a profile without parallel remains direct/single-worker exactly as today. The test-only overlay supplies parallel with bounded values and the fake/scripted provider routing (see Runtime activation).

### Declaration-layer ownership

checkOwnership(changedFiles, writePaths): normalized via the grammar; valid iff every changedFile is contained by some writePath. Returns the sorted unique set of violating paths. A worker whose Handoff changedFiles contains any path outside its declared writePaths is marked ownership-violation; its Handoff is not aggregated and its changes are not reported as accepted. Because workers self-report changedFiles, this cannot detect unreported shared-tree mutations (deferred isolation work), and v0.4 never claims otherwise. ownershipViolations in the aggregate is exactly this sorted unique output: at least one path per ownership-violation node, and no entries for any other node.

### ParallelAggregateV1

```ts
interface ParallelAggregateV1 {
  readonly schemaVersion: 1
  readonly fanoutId: string          // identifies one aggregate emission: per-level emissions share a dagId and carry distinct levelIndex
  readonly dagId: string             // identifies the whole DAG run
  readonly scope: 'level' | 'dag'
  readonly levelId?: string          // present when scope === 'level'
  readonly levelIndex?: number       // deterministic 0-based level ordinal; present when scope === 'level'
  readonly nodeResults: readonly {
    readonly nodeId: string
    readonly requestId: string       // deterministic pre-admission node invocation id, generated for every node including not-run
    readonly workerId?: string
    readonly status: 'completed' | 'blocked' | 'failed' | 'ownership-violation' | 'not-run'
    readonly handoff?: HandoffV1
  }[]     // unique nodeIds and requestIds; deterministic order by level then lexical nodeId
  readonly aggregateStatus: 'completed' | 'blocked' | 'failed' | 'verification-failed'
  readonly verification?: readonly VerificationEvidenceV1[]
  readonly ownershipViolations: readonly { readonly nodeId: string; readonly path: string }[]
  readonly projectedHandoff: HandoffV1    // explicit parent-visible projection, always present
}
```

Invariants enforced by parseParallelAggregateV1: nodeIds and requestIds unique; every node (including not-run) carries a deterministic requestId; status equals handoff.status when a handoff is present (completed/blocked/failed nodes carry a handoff; ownership-violation and not-run nodes carry none); ownershipViolations exactly matches ownership-violation node results (sorted unique checkOwnership output; an integration-conflict concept does not exist in v0.4); scope 'level' has levelId/levelIndex and nodeResults bounded by MAX_PARALLEL_WORKERS; scope 'dag' has no levelId/levelIndex and nodeResults bounded by MAX_DAG_NODES (one aggregate after all runnable levels). MAX_AGGREGATE_PAYLOAD_BYTES caps total payload. Aggregate status derivation is deterministic and covers every node outcome: if any node is failed → failed; else if any node is ownership-violation → blocked; else if any node is blocked → blocked; else if verification failed → verification-failed; else if nothing was accepted (no completed-and-ownership-valid node) → blocked with an explanatory summary; else completed. Resolution order (first match wins): node-level failed maps the aggregate to failed; else any ownership-violation or blocked node maps the aggregate to blocked; else a verification command failure maps the aggregate to verification-failed; else nothing-accepted maps to blocked; else completed. verification-failed therefore applies only when every node is completed-and-ownership-valid or not-run and an integrated verification command failed. projectedHandoff is the deterministic HandoffV1 projection: status maps from aggregateStatus (completed → completed; blocked → blocked; verification-failed → failed with the exact [verification: failed] marker; failed → failed); summary concatenates accepted node summaries; changedFiles is the union of accepted (ownership-valid, completed) node changedFiles; verification carries the integrated evidence; blockers carry ownership violations and blocked/failed node summaries. All concatenations/unions are bounded by a deterministic aggregate builder (see below) so MAX_AGGREGATE_PAYLOAD_BYTES is always satisfiable.

### Deterministic aggregate builder

ParallelAggregateV1 is produced by a deterministic builder before parsing, not by ad-hoc concatenation: node order is level order then lexical nodeId; changedFiles and path unions deduplicate lexically; summary concatenates accepted node summaries in node order, truncated field-first (blockers first, then decisions, then summary) with per-field UTF-8 ceilings reused from the Handoff bounds; when the total still exceeds MAX_AGGREGATE_PAYLOAD_BYTES, the builder truncates embedded node Handoff projections (not the top-level required fields) in node order and discloses truncation via a bounded truncated: true marker on the affected embedded entries. A worst-case 16-node construction test must still produce a parseable bounded aggregate.

### Durable events and compatibility

Existing per-worker events (schedule-selected target=worker, worker-requested, worker-finished) remain byte-compatible v1 payloads for non-parallel runs. Worker-event types (WorkerSpecV1, WorkerFinishedV1), their strict parsers, and append helpers stay Orchestrator-local exactly as today (scheduling-contracts does NOT own worker-event types/parsers; it owns only DAG/path/aggregate/verification-policy contracts). For parallel runs, v0.4 mandates one design (no fallback): optional fanoutId/nodeId correlation fields are added to the Orchestrator-local WorkerSpecV1/WorkerFinishedV1 types and their append helpers, exported from dsh-orchestrator. Old logs without the fields and new logs with them both parse (the Orchestrator-local append helpers accept both shapes); replay covers both. schedule-selected remains exactly as v0.3 (no field added). One new aggregate event dsh-plugin/parallel-finished carries the bounded ParallelAggregateV1 projection (dagId, fanoutId, scope, levelId/levelIndex when level-scoped, per-worker requestIds/nodeIds/statuses, ownershipViolations, aggregateStatus, integrated verification outcome — no raw output, no transcript). Cardinality: one parallel-finished event per emitted ParallelAggregateV1 — scope 'level' policy emits one per executed level, scope 'dag' policy emits one after the whole DAG.

### ParallelVerificationPolicyV1

```ts
interface ParallelVerificationPolicyV1 {
  readonly schemaVersion: 1
  readonly scope: 'level' | 'dag'     // 'level': verify after each accepted level; 'dag': verify once after all runnable levels
  readonly commands: readonly {
    readonly name: string
    readonly args: readonly string[]
  }[]   // ordered; bounded by MAX_VERIFICATION_COMMANDS
}
```

parseParallelVerificationPolicyV1 validates that every command name exists in the deployment's configured verification.commands and that args obey the command's allowedArgs. Semantics: scope 'level' verifies after each level whose integration produced accepted changes; a failure prevents subsequent levels. Scope 'dag' verifies once after all runnable levels and therefore cannot prevent earlier level execution. The Orchestrator admits each command directly through the root controller (one targeted_verify action per command) and invokes VerificationService without the model-facing tool wrapper. On admission rejection: exactly the controller's one budget-rejected event is emitted on the root session; the command is not spawned and no later command runs; the aggregate maps to failed with a fixed bounded blocker/summary marker distinct from [verification: failed] [verification: budget-rejected] because no command ran. Commands run in order; stop-on-first-failure maps the aggregate to verification-failed and emits verification-finished evidence per attempted command. Zero commands means no integrated verification runs. When nothing was accepted, verification is skipped and the aggregate reports blocked. Parallel workers do NOT receive targeted_verify in their allowlists in v0.4 (worker-local verification is out of scope; integrated verification is the single verification authority for parallel runs). The policy is supplied by the test-only overlay or trusted deployment config via the optional parallel.verification block.

## Runtime activation

v0.4 mandates exactly one activation seam. dsh-orchestrator exports an Orchestrator-internal ParallelExecutionService registered under the named Cordis service parallelExecution, with:

```ts
interface ParallelExecutionService {
  run(request: { dag: TaskDagV1; policy: ParallelVerificationPolicyV1; parent: Agent; signal: AbortSignal }): Promise<ParallelAggregateV1>
}
```

run parses nothing (callers pass an already-parsed TaskDagV1), validates against the deployment limits, executes level by level under budget, enforces declaration-layer ownership, aggregates per the policy scope, and appends the durable events. Only the test-only overlay invokes run directly; there is no model-facing parallel tool and no new deployment mode. The overlay (see Evaluation) registers the service through the real Loader with the scripted subagent provider, proving the Loader — not direct construction — registered the parallel entry point. A profile without the optional parallel config never exposes the service.

## Decision precedence

The Orchestrator owns DAG/ownership/aggregation decisions. Resource decisions keep the v0.3 scheduler precedence, applied per worker capability request; the Scheduler cannot change the DAG, write sets, or worker count beyond the validated DAG and budget. When the Scheduler is absent, the Profile fixed route is used per worker.

## Parallel execution model

- The DAG is submitted to ParallelExecutionService.run with an already-parsed TaskDagV1; no scheduling or budget action occurs before parsing and validation succeed.
- A fan-out runs only the ready nodes of one level; a level completes when every worker Handoff is normalized and recorded. subagentMaxDepth = 1; dependency levels are orchestrated by the root, never by recursive worker delegation.
- Each worker is a fresh subagents.start('spawn') child with subagentMaxDepth 1, frozen route, and an allow-only tool filter. Workers run in the shared working tree (same execution model as Single Worker) and self-report changedFiles; they do not receive targeted_verify (integrated verification is the single authority for parallel runs).
- Declaration-layer ownership: after each worker completes, checkOwnership(changedFiles, writePaths) validates the self-reported changedFiles against declared ownership; any out-of-ownership path marks the node ownership-violation and its Handoff is not aggregated.
- Workers that fail, block, or produce invalid Handoffs do not abort healthy siblings; the aggregate reports each status. A node whose dependency failed/blocked/violated receives a synthetic not-run result (no Handoff, deterministic requestId) and consumes no worker budget; the dependency blocker appears in projectedHandoff.blockers.
- Integrated-result verification runs per the ParallelVerificationPolicyV1 scope on the accepted (ownership-valid, completed) node changes, never redundantly per worker.

## Safe degradation

- No Scheduler → per-worker Profile fixed route, deterministic and keyless.
- Scheduler invalid/out-of-bound decision → same validation failure and fallback policy as v0.3; never silently expands worker count or provider.
- DAG parse/validation failure → reject fan-out before admission, record issue, no budget consumed.
- Declaration-layer ownership violation at runtime → execution budget remains consumed but the node is marked ownership-violation and its Handoff is not aggregated.
- Verification admission rejection → aggregate failed with the [verification: budget-rejected] marker, no command spawned, no later command runs.
- Provider auth/quota/rate-limit errors never trigger silent paid fallback.
- run-started keeps actual-route semantics.

## Evaluation and error handling

Keyless replay covers:

- DAG parser rejections (invalid shape, bad path, over-limit per-node arrays/strings) and validator semantic issues (duplicate node, self-dependency, missing dependency, cycle via SCC, W/W/W/R/R/W overlap, too-many-nodes/levels, level-width-exceeded) with the full deterministic comparator.
- Parallel fan-out admission: N workers within width bound and cumulative bound, atomic admitFanout rollback on partial failure with exactly one budget-rejected event and deterministic rejection precedence, no child start before admission commits.
- Per-worker route selection (scheduler-present and profile-fallback).
- Declaration-layer ownership: checkOwnership containment, a worker self-reporting an out-of-ownership path marked ownership-violation and not aggregated; a worker self-reporting only in-ownership paths aggregated.
- ParallelAggregateV1 construction, invariant enforcement, aggregate-status truth table over mixed node outcomes, and projectedHandoff mapping.
- Deterministic aggregate builder: worst-case 16-node construction stays parseable and bounded; truncation disclosure.
- Integrated-result verification under ParallelVerificationPolicyV1 (scope level vs dag timing, ordering, action accounting, stop-on-first-failure, budget-rejection path with the distinct marker, verification-finished evidence, zero-command and nothing-accepted cases, workers without targeted_verify).
- Event provenance: per-worker schedule-selected/worker-requested/worker-finished (both with and without optional correlation fields) plus parallel-finished with correct cardinality per scope; ordering and bounded payloads.
- Runtime activation: the test-only overlay boots through the real Loader, registers parallelExecution, and asserts the final composed scheduler catalog routes the intended keyless test tools (workers request a non-empty tool set that excludes targeted_verify) and that the captured SubagentStartRequest.toolFilter excludes targeted_verify.
- Profile-fallback, invalid-decision, quota/timeout/cooldown, escalation, Direct actual-route, and read-only budget snapshot regressions remain green.

Missing optional services, invalid decisions, quota failures, and unknown provider/model values fail closed or degrade deterministically without provider access. Every timeout/cancellation path releases owned resources. The provider smoke command remains the exact keyless DISABLED check.

### Test-only overlay (exact)

The overlay is a loader-convention-compatible fixture, not a profile: it starts from profiles/v0.3-adaptive/cordis.patch.yml and applies two patches. (1) Orchestrator patch: adds the optional parallel block { maxParallelWorkers, verification: { scope: 'dag', commands: [...] } } and raises budgets.maxWorkers to the DAG node count under test (≤ MAX_DAG_NODES). (2) Adaptive scheduler catalog patch: replaces each catalog entry's toolFilter with the specific keyless test tools the parallel workers request (the file-read/write doubles the scripted harness provides), while keeping targeted_verify out of every spawned worker's allowlist. The replay fixture then asserts the real Loader composed both patches, parallelExecution is registered, a parallel worker request routes to a catalog entry whose toolFilter contains the requested tools, and the captured SubagentStartRequest.toolFilter excludes targeted_verify.

## Acceptance criteria

1. parseTaskDagV1/validateTaskDagV1 are pure, deterministic, bounded, keyless, and reject every listed condition before admission with the full deterministic comparator (including SCC cycle semantics and levelCount 0 on cycles).
2. Parallel fan-out runs N bounded workers under both width (≤ maxParallelWorkers ≤ 8) and cumulative (≤ budgets.maxWorkers ≤ 16) bounds, with per-worker route selection, atomic admitFanout (defined slack formula, deterministic rejection precedence, one rejection event), and no child start before admission commits.
3. Per-worker durable events carry optional correlation fields that parse in both old-without and new-with shapes; parallel-finished events have the correct cardinality per policy scope.
4. Declaration-layer ownership: a worker self-reporting out-of-ownership changedFiles is marked ownership-violation and not aggregated; in-ownership reports aggregate. v0.4 claims only declaration-layer enforcement.
5. A node whose dependencies failed/blocked/violated receives a synthetic not-run result (no Handoff, deterministic requestId) and consumes no worker budget.
6.
