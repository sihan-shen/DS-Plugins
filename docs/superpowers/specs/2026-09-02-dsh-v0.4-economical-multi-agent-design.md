# DSH v0.4 Economical Multi-Agent Design

## Goal

Extend the Orchestrator so it can decompose a root task into bounded, independent sub-tasks and run them as parallel Workers whose declared file ownership is enforced at the declaration layer (each worker's self-reported changedFiles must fall inside its declared writePaths; violations fail closed and are never aggregated), then aggregate their Handoffs and verify the integrated result — while preserving the keyless v0.3 safety boundary, deterministic replay, and the single-monorepo plugin ownership model. v0.4 introduces a declarative Task DAG and independence/ownership validation as deterministic pure logic in the Orchestrator, a bounded parallel-worker execution path, declaration-layer ownership enforcement, Handoff aggregation into a strict ParallelAggregateV1, and an integrated-result verification gate. Worker processes run in the shared working tree exactly as today's Single Worker path. Physical execution isolation and trusted write capture are deferred milestones (see Deferred isolation work). No new runtime plugin beyond the Orchestrator is created; the Adaptive Scheduler continues to own resource/affinity selection.

## Scope and non-goals

v0.4 covers: the contracts needed for bounded parallel workers and task graphs; a deterministic, replayable Task DAG representation with file-ownership sets and dependency edges; a parallel fan-out path; declaration-layer ownership enforcement (self-reported changedFiles validated against declared writePaths via the authoritative path grammar in dsh-scheduling-contracts); per-worker Handoff normalization plus a strict ParallelAggregateV1 result; integrated-result verification; and a deterministic keyless replay gate over the v0.3-adaptive profile with a test-only overlay. It does not implement filesystem isolation, per-worker execution cwd binding, trusted per-worker write capture, actual-diff containment, or transactional file integration — all deferred (see below). It does not implement learning-based decomposition, LLM Judge independence approval, mutable warm worker reuse across tasks, cross-session physical worker pooling, recursive worker delegation beyond subagentMaxDepth 1, or any provider/network/real coding-task acceptance. Context-locality/prefix-compatible reuse and all deferred v0.3 roadmap items (hysteresis, shadow Judge, quota adapters) are explicitly deferred beyond v0.4. It does not modify profiles/v0.1, the Direct or Single Worker semantics, HandoffV1 projection semantics, BudgetController admission exclusivity, or the run-started actual-route projection.

## Deferred isolation work (explicitly out of v0.4 scope)

Ownership is enforced at the declaration layer in v0.4: a worker's self-reported changedFiles must be contained by its declared writePaths. This detects a worker that reports an out-of-scope mutation, but it cannot detect a worker that mutates the shared tree without reporting it, and it cannot physically prevent writes. Three stronger mechanisms are deferred to future milestones gated on verified Harness capability (the pinned Harness 0.1.1-rc.2 SubagentStartRequest has no cwd/workspace field, in-process spawn inherits the parent cwd, and per-child fs write attribution is unverified):

1. Per-worker execution cwd binding: each spawned child's process cwd/fs root points at its own isolated copy. Requires a Harness upgrade or a DSH-owned custom subagent provider that stamps child session cwd; a compatibility spike must precede it.
2. Trusted per-worker write capture: an Orchestrator-side journal of actual writes derived from the Harness fs/write-intent and fs/edit-intent event gates, attributed per child session, so ownership can be checked against real writes rather than self-reports. Requires a spike proving child-session attribution.
3. Actual-diff containment and transactional integration over isolated copies. Depends on 1 or 2.

A one-page record of these deferred items is kept in docs/superpowers/specs/2026-09-02-dsh-v0.4a-isolated-workspace-design.md so the boundary and the future seam (prepare/diff/integrate over isolated workspaces) remain documented; no v0.4a implementation is planned in this cycle.

## Baseline and constraints

- Keep DeepSeek Harness pinned at 0.1.1-rc.2 until a separate compatibility review proves an upgrade.
- Preserve Direct mode, Single Worker mode, HandoffV1, plugin-owned budgets, targeted verification, canonical dsh-plugin/ events, and the keyless DISABLED provider smoke.
- The Orchestrator owns task DAG, independence/ownership validation, worker lifecycle, final budget admission, Handoff normalization/aggregation, and event recording. The Scheduler only provides capability-to-schedule decisions.
- Do not fork or modify upstream/deepseek-harness or replace its agent loop.
- All model-visible outputs and all orchestration evidence stay bounded, provenance-carrying, and safe to replay.
- No orchestration decision may bypass the Orchestrator's hard constraints (maxWorkers, maxPluginToolActions, tool allowlist, workspace/verification policy, disjoint ownership).
- Workers run in the shared working tree and self-report changedFiles. Declaration-layer ownership means: self-reported changedFiles outside declared writePaths fail closed (node invalid, not aggregated). Physical containment is not claimed in v0.4.
- Per-node TaskNodeV1 constraints may only NARROW the deployment limits (max tokens, latency, workers, providers, paid fallback, tool permissions). They never raise or replace them; the effective capability request is the deterministic intersection/projection of deployment constraints and node constraints.
- Unknown quota, price, or health values are never invented or silently estimated into hard routing decisions.
- No v0.4 profile is added. The parallel path is activated only through a validated test-only overlay over the v0.3-adaptive profile (loader-convention-compatible) plus replay fixtures in tests/replay. Real deployments enabling parallel mode are deferred until execution isolation exists.

## Architecture

The repository keeps the existing packages and adds no new runtime plugin:

```text
packages/
  dsh-scheduling-contracts/   # pure types, JSON schema, parsers; no Cordis runtime. Authority for DAG, aggregate, path grammar, bounds, and worker scheduling constraints
  dsh-orchestrator/           # gains task DAG, independence/ownership validation, parallel fan-out, declaration-layer ownership, aggregation, ParallelExecutionService
```

dsh-scheduling-contracts already defines CapabilityRequestV1, RouteDecisionV1, ScheduleDecisionV1, BudgetViewV1, ScheduleFeedbackV1, and ScheduleSelectedV1. v0.4 widens SchedulingConstraintsV1.maxWorkers and BudgetViewV1 bounds, adds the Task DAG, ParallelAggregateV1, ParallelVerificationPolicyV1, and the authoritative path grammar/types/bounds, and keeps the no-Cordis boundary. Worker-event types (WorkerSpecV1, WorkerFinishedV1) and their parsers/append helpers remain Orchestrator-local exactly as today; scheduling-contracts does NOT gain worker-event types or parsers.

dsh-orchestrator adds a deterministic pure dag.ts module (DAG parsing/validation, cycle rejection via SCC, level/topological ordering, independence check, disjoint ownership validation), a declaration-layer ownership check (changedFiles containment), a ParallelExecutionService seam, and extends the worker path so the parallel fan-out admits and runs N bounded workers with per-worker route selection, enforces declaration-layer ownership, aggregates normalized Handoffs into ParallelAggregateV1 emissions, and runs integrated-result verification. Root route selection remains under the existing Adaptive Scheduler seam.

The execution flow:

```text
root task
  -> ParallelExecutionService.run({ dag, parent, signal })   // Orchestrator-internal; only the test overlay invokes it; policy comes from config.parallel.verification
  -> parseTaskDagV1 (strict, bounded) + validateTaskDagV1 (semantic): acyclic, disjoint ownership, bounded nodes/levels/width, subagentMaxDepth 1
  -> per-ready-level: per-worker schedule (Adaptive Scheduler, unchanged ScheduleDecisionV1) -> hard validation -> BudgetController.admitFanout (atomic)
  -> parallel subagents.start('spawn') per worker in the shared working tree (same execution model as Single Worker)
  -> per-worker Handoff normalization (self-reported changedFiles)
  -> declaration-layer ownership check: changedFiles ⊆ declared writePaths (grammar containment); violation => node ownership-violation, not aggregated
  -> deterministic aggregate builder emits ParallelAggregateV1 per policy scope + integrated-result verification (config.parallel.verification)
  -> dsh-plugin durable events per worker and per emitted aggregate
```

## Contracts

### Constants (authoritative, in dsh-scheduling-contracts)

MAX_PARALLEL_WORKERS = 8 (max ready-level width; distinct from any configured default — config requires explicit maxWorkers); MAX_DAG_NODES = 16 (total nodes in one DAG; the cumulative per-session worker budget ceiling); MAX_DAG_LEVELS = 4; MAX_DAG_PATHS = 32 per node (readPaths and writePaths each); MAX_DAG_DEPS = 8 per node; MAX_AGGREGATE_PAYLOAD_BYTES = 65536 (total UTF-8 payload of one ParallelAggregateV1); MAX_AGGREGATE_VERIFICATION_BYTES = 8192 (per-command stdout+stderr retained in an aggregate, truncated); MAX_AGGREGATE_PATH_BYTES = 1024 (per ownership-violation path, truncated); MAX_VERIFICATION_COMMANDS = 4 (per parallelVerification policy). All string/array bounds reuse the existing scheduling/handoff byte and item ceilings. Each constant has exact-bound and one-over-bound tests.

### Path grammar

Authoritative in dsh-scheduling-contracts. RepoFilePath: canonical POSIX repository-relative path, no trailing slash. RepoDirectoryPrefix: ends in /. No glob metacharacters, no . or .., drive roots, empty segments, NULs, or backslash. Case-sensitive lexical containment: RepoDirectoryPrefix p/ contains path q when q starts with p/; RepoFilePath p contains only itself. No whole-repository sentinel. write-outside-root is not a pure-validator concern in v0.4: every grammar-valid path is lexically repository-relative, and any deployment subroot restriction is enforced by the declaration-layer ownership check against declared writePaths (the write set itself is the boundary). A normative containment examples table ships with the grammar.

### Task DAG

```ts
interface TaskNodeV1 {
  readonly schemaVersion: 1
  readonly nodeId: string              // unique within the graph
  readonly objective: string
  readonly profile: CapabilityProfileV1
  readonly constraints: SchedulingConstraintsV1   // sole authority for requiredTools and per-node limits; may only narrow deployment limits
  readonly readPaths: readonly (RepoFilePath | RepoDirectoryPrefix)[]   // repository-relative read declarations
  readonly writePaths: readonly (RepoFilePath | RepoDirectoryPrefix)[]  // repository-relative ownership declarations
  readonly dependsOn: readonly string[]     // nodeIds that must complete first
}

interface TaskDagV1 {
  readonly schemaVersion: 1
  readonly rootTaskId: string
  readonly nodes: readonly TaskNodeV1[]
}

interface DagValidationLimitsV1 {
  readonly schemaVersion: 1
  readonly maxNodes: number        // <= MAX_DAG_NODES; deployment/runtime limit, default MAX_DAG_NODES
  readonly maxLevels: number       // <= MAX_DAG_LEVELS; default MAX_DAG_LEVELS
  readonly maxWidth: number        // <= MAX_PARALLEL_WORKERS; default MAX_PARALLEL_WORKERS
  readonly maxCumulativeWorkers: number   // <= MAX_DAG_NODES; derived from the session cumulative worker budget (budgets.maxWorkers)
}
```

parseTaskDagV1(value) is strict and bounded: it validates JSON shape, path grammar, per-field string/array bounds (MAX_DAG_PATHS, MAX_DAG_DEPS, string ceilings), and deep-freezes. It throws TypeError on structural violations only (invalid JSON shape, invalid path syntax, over-limit per-node arrays/strings, unknown fields). Duplicate nodeIds, self-dependency, unknown dependency references, cycle, overlap, and graph-wide limit violations are SEMANTIC issues returned by validateTaskDagV1, never thrown by the parser. validateTaskDagV1(dag: TaskDagV1, limits: DagValidationLimitsV1) accepts only already-parsed TaskDagV1 and returns DagValidationV1; valid === true only when issues is empty. Dependency chains across levels are allowed; subagentMaxDepth = 1 means each spawned worker is a leaf that never recursively delegates — it is not a graph-depth limit.

```ts
type DagValidationIssueV1 =
  | { code: 'duplicate-node'; nodeId: string }
  | { code: 'self-dependency'; nodeId: string }
  | { code: 'missing-dependency'; nodeId: string; dependsOn: string }
  | { code: 'cycle'; nodeId: string }
  | { code: 'overlapping-access'; nodeA: string; nodeB: string; mode: 'ww' | 'wr' | 'rw' }
  | { code: 'too-many-nodes'; count: number; limit: number }
  | { code: 'too-many-levels'; levelCount: number; limit: number }
  | { code: 'level-width-exceeded'; level: number; width: number; limit: number }
  | { code: 'cumulative-worker-limit-exceeded'; count: number; limit: number }

interface DagValidationV1 {
  readonly schemaVersion: 1
  readonly valid: boolean
  readonly issues: readonly DagValidationIssueV1[]   // deterministic order, see comparator below
  readonly levels: readonly (readonly string[])[]
  readonly levelCount: number                        // 0 when any cycle or malformed node blocks a full acyclic ordering; otherwise max dependency depth + 1; a graph with no edges has levelCount 1
}
```

Node eligibility before topological layering: duplicate-ID declarations are all omitted from levels (each duplicated id emits one duplicate-node issue); nodes with a missing dependency and every node downstream of them are omitted (each emits one missing-dependency issue); a self-dependent node emits exactly one self-dependency issue and is omitted (it does not additionally emit cycle); nodes in a non-trivial strongly connected component (SCC) each emit one cycle issue (all cycle issues ordered lexically by nodeId after rank) and are omitted along with every node downstream of the SCC. levels then contains each eligible unique node exactly once in topological order; when no eligible node remains, levels is empty and levelCount is 0. levelCount is 0 whenever any cycle or malformed-node exclusion occurred; otherwise max dependency depth + 1 (a graph with no edges has levelCount 1).

Deterministic issue ordering uses a per-code numeric rank in this order: duplicate-node(1), self-dependency(2), missing-dependency(3), cycle(4), overlapping-access(5), too-many-nodes(6), too-many-levels(7), level-width-exceeded(8), cumulative-worker-limit-exceeded(9), then a full comparator key per issue variant: (rank, nodeId, dependsOn) for missing-dependency; (rank, nodeId) for duplicate-node/self-dependency/cycle; (rank, nodeA, nodeB, mode) for overlapping-access with nodeA and nodeB canonicalized lexically; (rank, limit, count) for too-many-nodes/cumulative-worker-limit-exceeded; (rank, limit, levelCount) for too-many-levels; (rank, level, limit, width) for level-width-exceeded. overlapping-access carries no path.

Overlap generation: only nodes that may execute concurrently (nodes in the same ready level, i.e. not ordered by a dependency edge) are compared. For each unordered pair the read/write declarations are intersected under the grammar: a write-write, write-read, or read-write overlap on any path emits at most one issue per pair with mode precedence ww < wr < rw (the most severe present mode wins); nodeA/nodeB are canonicalized lexically. Sequential producer-consumer access across dependency-ordered levels is allowed and never emits overlap.

### Widened worker model, budgets, and parallel config

SchedulingConstraintsV1.maxWorkers becomes 0..MAX_PARALLEL_WORKERS (per-request worker width). ScheduleDecisionV1 is unchanged: each worker keeps mode single-worker, workerCount 1, and its own route. Parallel execution is an Orchestrator-level execution mode driven by the validated DAG; the Scheduler never emits a batch decision and cannot change the DAG, write sets, or worker count. Existing single-worker/direct fixtures/tests remain valid. The effective capability request per node is the deterministic intersection of deployment limits and the node's TaskNodeV1.constraints (node may only narrow; it can never raise max tokens, latency, workers, providers, paid fallback, or tool permissions, and requiredTools comes solely from constraints.requiredTools).

Two distinct limits exist, with distinct bounds:
- maxParallelWorkers (max ready-level width): 0..MAX_PARALLEL_WORKERS (8). This is SchedulingConstraintsV1.maxWorkers and parallel.maxParallelWorkers.
- budgets.maxWorkers (cumulative per-session worker budget) and every worker counter in BudgetViewV1: 0..MAX_DAG_NODES (16). This is the ceiling a whole multi-level DAG runs under.

DAG validation checks max ready-level width (≤ maxWidth), total node count (≤ maxCumulativeWorkers via cumulative-worker-limit-exceeded, and ≤ maxNodes via too-many-nodes). Runtime admission adds an Orchestrator-only atomic admitFanout(workerCount): accounting rule — one internal fan-out action charged to the existing delegate_worker plugin-action counter per executed level (the internal parallel service never invokes the model-facing delegate_worker tool; the counter is reused for accounting), N cumulative worker admissions, and one targeted_verify action per verification command actually run by the configured policy. Atomic algorithm: take a pre-admission snapshot, compute requested {workers: N, actions: 1}, and evaluate each counter's post-request slack = limit - (current + requested); if both would overflow, report the rejection with the more negative slack first (tie: worker rejection first); DISPOSED takes precedence over both; exactly one durable budget-rejected event is emitted for an atomic fan-out failure; commit all counters or none through a single internal atomic mutation path (never by composing the side-effecting scalar admit methods, which would double-record rejections). admitFanout is never exposed to the Scheduler. A preflight DAG/ownership failure consumes no budget. A runtime declaration-layer ownership violation (detected after the worker ran) consumes the admitted execution budget but blocks aggregation.

Strict Orchestrator config gains an optional parallel block with this exact shape (added to types/parser under dsh-orchestrator):

```ts
interface ParallelConfigV1 {
  readonly maxParallelWorkers: number       // 0..min(MAX_PARALLEL_WORKERS, budgets.maxWorkers); no coupling to DAG shape
  readonly verification: ParallelVerificationPolicyV1
}
```

parseConfig accepts an optional top-level parallel key with only these fields. Conditional mode/budget semantics: without parallel, mode single-worker requires budgets.maxWorkers === 1 and mode direct requires budgets.maxWorkers === 0 exactly as today; with parallel, the model-facing delegate_worker under mode single-worker remains one-shot while the root controller may carry cumulative budgets.maxWorkers up to MAX_DAG_NODES for the internal parallel service, and mode direct remains incompatible with parallel (parseConfig rejects parallel alongside direct). A profile without parallel stays direct/single-worker exactly as today.

### Declaration-layer ownership

checkOwnership(changedFiles, writePaths): normalized via the grammar; valid iff every changedFile is contained by some writePath. Returns the sorted unique set of violating paths. A worker whose Handoff changedFiles contains any path outside its declared writePaths is marked ownership-violation; its Handoff is not aggregated and its changes are not reported as accepted. Because workers self-report changedFiles, this cannot detect unreported shared-tree mutations (deferred isolation work), and v0.4 never claims otherwise. The builder computes ownershipViolations as exactly this sorted unique output (producer guarantee); ownership-violation node results carry no handoff but the builder retains the violating paths at aggregate level.

### ParallelAggregateV1 and builder/parser guarantees

```ts
interface ParallelNodeResultV1 {
  readonly schemaVersion: 1
  readonly nodeId: string
  readonly requestId: string       // deterministic pre-admission invocation id; derived for every node including not-run
  readonly workerId?: string
  readonly status: 'completed' | 'blocked' | 'failed' | 'ownership-violation' | 'not-run'
  readonly handoff?: HandoffV1     // valid HandoffV1 when present; status equals handoff.status
  readonly handoffTruncated?: true // aggregate-local disclosure; HandoffV1 itself is never modified
}

interface ParallelAggregateV1 {
  readonly schemaVersion: 1
  readonly dagId: string             // identifies the whole DAG run
  readonly scope: 'level' | 'dag'
  readonly fanoutId: string          // level scope: levelId; dag scope: dagId + ":aggregate"
  readonly levelId?: string          // present when scope === 'level'
  readonly levelIndex?: number       // deterministic 0-based level ordinal; present when scope === 'level'
  readonly nodeResults: readonly ParallelNodeResultV1[]   // unique nodeIds and requestIds; deterministic order (level then lexical nodeId)
  readonly aggregateStatus: 'completed' | 'blocked' | 'failed' | 'verification-failed'
  readonly verification?: readonly VerificationEvidenceV1[]   // aggregate projections: stdout/stderr each truncated to MAX_AGGREGATE_VERIFICATION_BYTES per command
  readonly ownershipViolations: readonly { readonly nodeId: string; readonly path: string }[]   // each path truncated to MAX_AGGREGATE_PATH_BYTES
  readonly projectedHandoff: HandoffV1    // explicit parent-visible projection, always present
}
```

Deterministic identifiers. dagId is allocated by the service before any admission from a root-session invocation counter (monotonic per root session with the exact form <rootSessionId>:dag:<n> where <n> is the 1-based run ordinal); requestId = dagId + ":node:" + encodeURIComponent(nodeId); levelId = dagId + ":level:" + levelIndex; fanoutId = levelId for level scope, dagId + ":aggregate" for dag scope. encodeURIComponent prevents delimiter collisions. Repeated runs of the same DAG in one session receive distinct dagIds; across sessions rootSessionId differs.

Builder guarantees (producer): node order level-then-lexical; changedFiles/path unions deduplicate lexically; ownershipViolations is exactly the sorted unique checkOwnership output with at least one entry per ownership-violation node and none for other nodes; projectedHandoff summary concatenates accepted node summaries in node order; verification evidence is projected per command with stdout/stderr truncated to MAX_AGGREGATE_VERIFICATION_BYTES each; every ownership-violation path is truncated to MAX_AGGREGATE_PATH_BYTES.

Parser guarantees (parseParallelAggregateV1, enforced from the payload): nodeIds and requestIds unique; requestId present on every node; status equals handoff.status when a handoff is present; completed/blocked/failed nodes carry a handoff; ownership-violation and not-run nodes carry none; every ownershipViolations entry references an ownership-violation node, every ownership-violation node has at least one entry, and no other node has an entry; entries are lexically ordered and unique; scope 'level' has levelId/levelIndex and nodeResults bounded by MAX_PARALLEL_WORKERS; scope 'dag' has no levelId/levelIndex and nodeResults bounded by MAX_DAG_NODES; total serialized UTF-8 payload ≤ MAX_AGGREGATE_PAYLOAD_BYTES. Exact recomputation of ownershipViolations from changedFiles/writePaths is a builder guarantee, not a parser guarantee (the payload does not carry the raw changedFiles of violation nodes).

Aggregate status derivation (first match wins, exhaustive):
1. any node failed → failed;
2. any ownership-violation or blocked node → blocked;
3. verification admission rejected → failed (see verification semantics);
4. verification command failed → verification-failed;
5. nothing accepted (no completed-and-ownership-valid node) → blocked with an explanatory summary;
6. otherwise completed.

projectedHandoff is the deterministic HandoffV1 projection: status maps from aggregateStatus (completed → completed; blocked → blocked; verification-failed → failed with the exact [verification: failed] marker; failed → failed); summary concatenates accepted node summaries; changedFiles is the union of accepted (ownership-valid, completed) node changedFiles; verification carries the integrated evidence projections; blockers carry ownership violations and blocked/failed node summaries. Node outcomes (failed/blocked/ownership-violation) outrank verification admission rejection and verification command failure in the derivation above.

Aggregate-size satisfiability: every variable-size field has a deterministic ceiling — per-command verification stdout/stderr ≤ MAX_AGGREGATE_VERIFICATION_BYTES (8192 each) and at most MAX_VERIFICATION_COMMANDS commands; per-path ownership violations ≤ MAX_AGGREGATE_PATH_BYTES (1024) and at most MAX_DAG_NODES × MAX_DAG_PATHS entries; per-node embedded handoff projections reuse the existing Handoff field ceilings (16 KB strings, 128-item arrays) and are truncated field-first (blockers, then decisions, then summary, then changedFiles) with handoffTruncated: true on the affected node result, never modifying HandoffV1 itself; projectedHandoff fields reuse the same ceilings. A constructive bound test asserts the worst-case serialized payload (16 nodes × max handoff projection + 4 commands × 8192-byte evidence + 16×32 violation paths × 1024 bytes) stays ≤ 65536 bytes after the deterministic builder's truncation; the test is part of the v0.4 gate.

### Durable events and compatibility

Existing per-worker events (schedule-selected target=worker, worker-requested, worker-finished) remain byte-compatible v1 payloads for non-parallel runs. Worker-event types (WorkerSpecV1, WorkerFinishedV1), their strict parsers, and append helpers stay Orchestrator-local exactly as today (scheduling-contracts does NOT own worker-event types/parsers). For parallel runs, v0.4 mandates one design (no fallback): optional fanoutId/nodeId correlation fields are added to the Orchestrator-local WorkerSpecV1/WorkerFinishedV1 types and their append helpers, exported from dsh-orchestrator. Old logs without the fields and new logs with them both parse; replay covers both. schedule-selected remains exactly as v0.3 (no field added). One aggregate event dsh-plugin/parallel-finished is emitted per constructed ParallelAggregateV1 (cardinality = number of aggregate emissions): scope 'level' policy emits one per executed level, scope 'dag' policy emits one after the whole DAG. The event carries the bounded ParallelAggregateV1 projection (dagId, fanoutId, scope, levelId/levelIndex when level-scoped, per-worker requestIds/nodeIds/statuses, ownershipViolations, aggregateStatus, integrated verification outcome — no raw output, no transcript).

### ParallelVerificationPolicyV1 and verification authority

```ts
interface ParallelVerificationPolicyV1 {
  readonly schemaVersion: 1
  readonly scope: 'level' | 'dag'     // 'level': verify after each executed level that produced accepted changes; 'dag': verify once after all runnable levels
  readonly commands: readonly {
    readonly name: string
    readonly args: readonly string[]
  }[]   // ordered; bounded by MAX_VERIFICATION_COMMANDS
}
```

Sole verification authority. The deployment config's optional parallel.verification block is the ONLY source of the policy; ParallelExecutionService captures it at registration from its validated config and run() does NOT accept a policy argument, so a caller cannot bypass the validated command set. The pure contracts package provides parseParallelVerificationPolicyV1(value) for strict structural/bound checks only (shape, ordering, MAX_VERIFICATION_COMMANDS, string bounds). Command-existence and allowedArgs validation is Orchestrator config's job: validateParallelVerificationPolicy(policy, verificationConfig) checks every command name exists in the deployment's configured verification.commands and that every arg obeys the command's allowedArgs via the existing argument-policy validator; parseConfig runs it when the parallel block is present.

Semantics: scope 'level' verifies after each executed level whose integration produced accepted changes; a failure prevents subsequent levels. Scope 'dag' verifies once after all runnable levels and therefore cannot prevent earlier level execution. The Orchestrator admits each command directly through the root controller (one targeted_verify action per command) and invokes VerificationService without the model-facing tool wrapper. On admission rejection: exactly the controller's one budget-rejected event is emitted on the root session; the command is not spawned and no later command runs; the aggregate maps to failed per derivation step 3 with a fixed bounded blocker/summary marker [verification: budget-rejected] because no command ran. Commands run in order; stop-on-first-failure maps the aggregate to verification-failed (derivation step 4) and emits verification-finished evidence per attempted command. Zero commands means no integrated verification runs. When nothing was accepted, verification is skipped and the aggregate reports blocked (derivation step 5). Parallel workers do NOT receive targeted_verify in their allowlists in v0.4 (worker-local verification is out of scope; integrated verification is the single verification authority for parallel runs).

Verification-with-partial-failure truth table (scope 'dag'; the row determines whether verification runs and which aggregate status wins):

| Node outcomes | Verification runs? | Aggregate status |
| --- | --- | --- |
| all completed-and-ownership-valid | yes | verification-failed if a command fails, else completed |
| some accepted + some failed | yes (accepted changes exist) | failed (node failed outranks) |
| some accepted + some blocked | yes | blocked (node blocked outranks) |
| some accepted + some ownership-violation | yes | blocked (violation outranks) |
| only not-run / nothing accepted | no | blocked |
| mixed with verification admission rejected | yes, until rejection | failed ([verification: budget-rejected]) |

## Runtime activation

v0.4 mandates exactly one activation seam. dsh-orchestrator exports an Orchestrator-internal ParallelExecutionService registered under the named Cordis service parallelExecution, with:

```ts
interface ParallelExecutionService {
  run(request: { dag: TaskDagV1; parent: Agent; signal: AbortSignal }): Promise<ParallelRunResultV1>
}

interface ParallelRunResultV1 {
  readonly dagId: string
  readonly aggregates: readonly ParallelAggregateV1[]   // one per emission: per executed level when scope 'level', one DAG aggregate when scope 'dag'
  readonly finalAggregate: ParallelAggregateV1          // last element of aggregates; the parent-visible result
}
```

run parses nothing (callers pass an already-parsed TaskDagV1), validates against the deployment limits, executes level by level under budget, enforces declaration-layer ownership, emits one ParallelAggregateV1 per policy scope boundary via the deterministic builder (each emission also emits one parallel-finished event), and returns ParallelRunResultV1 whose finalAggregate is the parent-visible result. Only the test-only overlay invokes run directly; there is no model-facing parallel tool and no new deployment mode. The overlay (see Evaluation) registers the service through the real Loader with the scripted subagent provider, proving the Loader — not direct construction — registered the parallel entry point. A profile without the optional parallel config never exposes the service.

## Decision precedence

The Orchestrator owns DAG/ownership/aggregation decisions. Resource decisions keep the v0.3 scheduler precedence, applied per worker capability request; the Scheduler cannot change the DAG, write sets, or worker count beyond the validated DAG and budget. When the Scheduler is absent, the Profile fixed route is used per worker. Node constraints narrow but never raise deployment limits.

## Parallel execution model

- The DAG is submitted to ParallelExecutionService.run with an already-parsed TaskDagV1; the verification policy comes from config.parallel.verification (never a caller argument). No scheduling or budget action occurs before parsing and validation succeed.
- A fan-out runs only the ready nodes of one level; a level completes when every worker Handoff is normalized and recorded. subagentMaxDepth = 1; dependency levels are orchestrated by the root, never by recursive worker delegation.
- Each worker is a fresh subagents.start('spawn') child with subagentMaxDepth 1, frozen route, and an allow-only tool filter derived from the effective constraints.requiredTools (the sole tool authority). Workers run in the shared working tree (same execution model as Single Worker) and self-report changedFiles; they do not receive targeted_verify (integrated verification is the single authority for parallel runs).
- Declaration-layer ownership: after each worker completes, checkOwnership(changedFiles, writePaths) validates the self-reported changedFiles against declared ownership; any out-of-ownership path marks the node ownership-violation and its Handoff is not aggregated.
- Workers that fail, block, or produce invalid Handoffs do not abort healthy siblings; the aggregate reports each status. A node whose dependency failed/blocked/violated receives a synthetic not-run result (no Handoff, deterministic requestId) and consumes no worker budget; the dependency blocker appears in projectedHandoff.blockers.
- Integrated-result verification runs per the configured ParallelVerificationPolicyV1 scope on the accepted (ownership-valid, completed) node changes, never redundantly per worker.

## Safe degradation

- No Scheduler → per-worker Profile fixed route, deterministic and keyless.
- Scheduler invalid/out-of-bound decision → same validation failure and fallback policy as v0.3; never silently expands worker count or provider.
- DAG parse/validation failure → reject fan-out before admission, record issue, no budget consumed.
- Declaration-layer ownership violation at runtime → execution budget remains consumed but the node is marked ownership-violation and its Handoff is not aggregated.
- Verification admission rejection → aggregate failed with the [verification: budget-rejected] marker, no command spawned, no later command runs.
- Provider auth/quota/rate-limit errors never trigger silent paid fallback.
- run-started keeps actual-route semantics.

## Evaluation and error handling

Keyless replay covers:

- DAG parser rejections (invalid shape, bad path, over-limit per-node arrays/strings, unknown fields) and validator semantic issues (duplicate node, self-dependency, missing dependency, cycle via SCC, W/W/W/R/R/W overlap on concurrent nodes only, too-many-nodes/levels, level-width-exceeded, cumulative-worker-limit-exceeded) with the full deterministic comparator and node-eligibility rules.
- Parallel fan-out admission: N workers within width and cumulative bounds, atomic admitFanout rollback on partial failure with exactly one budget-rejected event and deterministic rejection precedence, no child start before admission commits.
- Per-worker route selection (scheduler-present and profile-fallback), with effective constraints as the deployment∩node intersection.
- Declaration-layer ownership: checkOwnership containment; a worker self-reporting an out-of-ownership path marked ownership-violation and not aggregated; in-ownership reports aggregated.
- ParallelAggregateV1 construction: builder guarantees (exact ownershipViolations) and parser guarantees (payload-enforced invariants); aggregate-status truth table over mixed node/verification outcomes; deterministic identifier derivation; projectedHandoff mapping.
- Aggregate-size satisfiability: worst-case construction (16 nodes + 4 commands + max violation paths) stays parseable and ≤ 65536 bytes; truncation disclosure via handoffTruncated.
- Integrated-result verification under the configured policy (scope level vs dag timing, ordering, action accounting, stop-on-first-failure, budget-rejection path with the distinct marker, verification-finished evidence, zero-command and nothing-accepted cases, partial-failure truth table, workers without targeted_verify).
- Event provenance: per-worker schedule-selected/worker-requested/worker-finished (both with and without optional correlation fields) plus parallel-finished with cardinality equal to aggregate emissions; ordering and bounded payloads.
- Runtime activation: the test-only overlay boots through the real Loader, registers parallelExecution, run() rejects a caller-supplied policy shape (no such parameter exists), and asserts the final composed scheduler catalog routes the intended keyless test tools (workers request a non-empty tool set that excludes targeted_verify) and that the captured SubagentStartRequest.toolFilter excludes targeted_verify.
- Profile-fallback, invalid-decision, quota/timeout/cooldown, escalation, Direct actual-route, and read-only budget snapshot regressions remain green.

Missing optional services, invalid decisions, quota failures, and unknown provider/model values fail closed or degrade deterministically without provider access. Every timeout/cancellation path releases owned resources. The provider smoke command remains the exact keyless DISABLED check.

### Test-only overlay (exact)

The overlay is a loader-convention-compatible fixture, not a profile: it starts from profiles/v0.3-adaptive/cordis.patch.yml and applies two patches. (1) Orchestrator patch: mode stays single-worker (model-facing delegate_worker remains one-shot), adds the optional parallel block { maxParallelWorkers, verification: { scope: 'dag', commands: [...] } }, and raises budgets.maxWorkers to the DAG node count under test (≤ MAX_DAG_NODES); parseConfig accepts this under the conditional rule that parallel requires single-worker mode with cumulative budgets.maxWorkers ≤ MAX_DAG_NODES. (2) Adaptive scheduler catalog patch: replaces each catalog entry's toolFilter with the specific keyless test tools the parallel workers request (the file-read/write doubles the scripted harness provides), while keeping targeted_verify out of every spawned worker's allowlist. The replay fixture then asserts the real Loader composed both patches, parallelExecution is registered, a parallel worker request routes to a catalog entry whose toolFilter contains the requested tools, and the captured SubagentStartRequest.toolFilter excludes targeted_verify.
